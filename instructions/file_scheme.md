## 1. Как читать этот документ: пометки

Рядом с папками и файлами стоят короткие пометки.

| Пометка | Что значит |
|---|---|
| **[РАБОТА]** | Нужно, чтобы сервис запустился и работал. Без этого он не стартует. |
| **[РАЗРАБОТКА]** | Нужно разработчикам и исследователям: тесты, эксперименты, заметки. Для работы сервиса не нужно. |
| **[ПДн]** | Здесь лежат или могут лежать персональные данные (тексты обращений граждан, ФИО, адреса). В Git не попадает и попадать не должно. |
| **[ГЕНЕРИРУЕТСЯ]** | Появляется само при установке или запуске. Не правьте руками, не коммитьте. |

## 2. Верхний уровень: дерево папок

Ниже показаны только верхние папки и важные файлы. Каждый пункт разобран в своём разделе.

```

│   ├── api/                  веб-интерфейс и HTTP API
│   ├── classifier/           логика классификации
│   ├── queueing/             очереди и задачи Celery
│   ├── worker/               запуск воркера
│   ├── storage/              работа с базой данных
│   ├── training/             дообучение модели
│   ├── integrations/         связь с Directum RX, чтение файлов
│   ├── core/                 настройки и общие мелочи
│   └── cli/                  консольные утилиты
├── scripts/                  скрипты: база данных, установка, эксперименты
├── tests/                    [РАЗРАБОТКА] автотесты
├── data/                     классификатор, векторная база, наборы для экспериментов
├── models/                   [ГЕНЕРИРУЕТСЯ] файлы моделей (в Git почти пусто)
├── deploy/                   [РАБОТА] настройки PostgreSQL и RabbitMQ для Docker
├── docs/                     [РАЗРАБОТКА] прежняя документация, планы, отчёты
├── instructions/             инструкции для людей (этот документ тут же)
├── Template/                 [РАЗРАБОТКА] шаблон нового прототипа, к сервису не относится
├── .hypothesis/              [РАЗРАБОТКА] артефакты процесса разработки прототипа
├── .claude/                  [РАЗРАБОТКА] настройки ИИ-помощника для разработчиков
├── docker-compose.yml        [РАБОТА] описание всех контейнеров
├── Dockerfile                [РАБОТА] сборка образа сервиса
├── requirements.txt          [РАБОТА] список Python-библиотек
├── .env.example              [РАБОТА] шаблон файла настроек
├── install.* / launch.*      [РАБОТА] установка и запуск
├── start.* / stop.*          [РАБОТА] запуск и остановка стека
│
│   Не хранятся в Git, создаются на вашей машине:
├── .env                      [ПДн] [ГЕНЕРИРУЕТСЯ] ваши настройки и секреты (ключи доступа)
├── venv/                     [ГЕНЕРИРУЕТСЯ] виртуальное окружение Python
├── run/                      [ПДн] [ГЕНЕРИРУЕТСЯ] логи и pid-файлы локального запуска
├── models/e5-finetuned-vN/   [ГЕНЕРИРУЕТСЯ] дообученные версии модели
├── node_modules/             [ГЕНЕРИРУЕТСЯ] библиотеки для браузерных тестов
├── offline_bundle/           [ГЕНЕРИРУЕТСЯ] комплект для установки без интернета
├── logs/, test-results/,
│   playwright-report/        [ГЕНЕРИРУЕТСЯ] логи и результаты прогонов
```

Часть этих папок появляется не сразу. Например, `run/` создаётся только при локальном запуске (`start.cmd local` или `./start.sh local`), а `offline_bundle/` только если вы собирали комплект для установки без интернета.

## 3. Папка src/: код сервиса

`src/` — корень всего кода. Модули внутри импортируются «сверху», например `import config`, `queueing.celery_app`, поэтому любой процесс должен знать, что `src` нужно искать в пути импорта (переменная окружения `PYTHONPATH`). Скрипты запуска и Docker-образ делают это сами. Если вы запускаете что-то руками, запускайте из корня проекта.

Код разложен по пакетам по ролям. Пакет — это просто папка с Python-файлами и файлом `__init__.py`. Тест `tests/test_src_layout.py` следит, чтобы эта раскладка не ломалась.

Главное правило: процесс API (`src/api/`) никогда не подгружает модель и библиотеки `torch`, `sentence_transformers`, `classifier_agent`. Тяжёлую работу делают воркеры.

### 3.1. src/api/ — веб-интерфейс и HTTP API [РАБОТА]

Это «входная дверь» сервиса: сюда приходят запросы от Directum RX и от людей в браузере. Процесс лёгкий, модели в нём нет. Он принимает запрос, записывает карточку обращения и задание в базу, отправляет задание в очередь и отдаёт результат.

| Файл | За что отвечает |
|---|---|
| `api_server.py` | Главное приложение FastAPI (запускается командой `uvicorn api.api_server:app --app-dir src`). Адреса `/classify`, `/health`, страницы веб-интерфейса и бэк-офиса, приём файлов. Файл исторических обращений на время разбора кладёт в `data/temp_upload/`. |
| `integration_api.py` | Адреса для Directum RX: RX присылает текст обращения или идентификатор документа, сервис возвращает результат классификации. |
| `job_api.py` | Общая логика «поставить задание в очередь и дождаться результата» для адресов `/classify`, `/classify/file`, `/classifier/search`. Здесь же ожидание ответа воркера и превышение времени ожидания (код 504). |
| `responses.py` | Общие формы запросов и ответов (модели pydantic). Нужны и API, и воркеру, поэтому лежат отдельно и не тянут тяжёлые библиотеки. |

### 3.2. src/api/static/ — страницы и стили [РАБОТА]

Это то, что браузер получает от API: готовые HTML, JavaScript и CSS. Отдельной сборки нет, файлы отдаются как есть.

| Файл | За что отвечает |
|---|---|
| `index.html`, `app.js` | Главная страница: поле для ввода текста обращения или загрузки файла и показ результата классификации. |
| `backoffice.html`, `backoffice.js` | Бэк-офис: работа оператора (проверка результатов, дообучение) и экран настроек. |
| `settings.js` | Часть бэк-офиса: настройки LLM и Directum RX. |
| `historical.html`, `historical.js` | Страница импорта исторических обращений. |
| `base.css`, `tokens.css`, `styles.css`, `appeal.css` | Стили: общие основы, цвета и размеры (токены), стили страниц, стили карточки обращения. |
| `logo.svg`, `logo-directum.svg` | Логотипы. |

### 3.3. src/classifier/ — логика классификации [РАБОТА]

Здесь «мозг» сервиса. Пакет подгружается только воркером классификации.

| Файл | За что отвечает |
|---|---|
| `classifier_agent.py` | Главный класс `ClassifierAgent`. Принимает текст обращения и делает два шага: поиск кандидатов в классификаторе по смыслу (векторный поиск в PostgreSQL), затем выбор лучшего кода с помощью LLM. Возвращает результат классификации. |
| `hierarchy.py` | Работа с кодами классификатора: код имеет вид `XXXX.XXXX.XXXX.XXXX`, файл умеет определять раздел, родителя, уровень. |
| `section_router.py` | Грубая «маршрутизация» по разделам классификатора перед точным выбором, чтобы кандидаты не прыгали между далёкими разделами. |
| `reranker.py` | Переупорядочивание кандидатов (cross-encoder) для повышения точности. |
| `llm_schemas.py` | Схемы JSON, которым должен соответствовать ответ LLM (строгий формат ответа). |
| `llm_check.py` | Проверка связи с LLM-сервером: отвечает ли он и есть ли нужная модель. Используется в настройках. |
| `fio_extractor.py` | Достаёт ФИО заявителя из текста обращения. |
| `email_extractor.py` | Достаёт адрес электронной почты заявителя из текста. |

### 3.4. src/queueing/ — очереди и задачи [РАБОТА]

Очередь — это «почтовый ящик с заданиями»: API кладёт туда задание, а воркер забирает и выполняет. Очередью служит RabbitMQ, а библиотека Celery позволяет воркерам брать задания из неё.

| Файл | За что отвечает |
|---|---|
| `celery_app.py` | Настройка Celery: адрес RabbitMQ, очереди `classify_sync`, `classify`, `training`, подтверждение задания после выполнения. |
| `tasks.py` | Сами задачи: классификация, поиск по классификатору, расчёт вектора для разметки, дообучение. |
| `dispatcher.py` | Сторона API: отправка задания в очередь (в тестах есть «локальный» вариант без брокера). |
| `waiter.py` | Сторона API: ожидание готового результата. Слушает уведомление `job_done` от PostgreSQL. |
| `warmup.py` | Прогрев воркера: модель загружается один раз при старте процесса, а не на каждое задание. |
| `webhook.py` | Отправка результата на внешний адрес (вебхук) с подписью и повторными попытками. Работает только для разрешённых хостов. |

### 3.5. src/worker/ — запуск воркера [РАБОТА]

| Файл | За что отвечает |
|---|---|
| `worker_main.py` | Старт процесса воркера: создаёт один `ClassifierAgent` на процесс, подхватывает новую версию модели без перезапуска и перечитывает `.env` на лету. |

### 3.6. src/storage/ — работа с базой данных [РАБОТА]

Слой хранения: всё, что читается из PostgreSQL и пишется в него, проходит здесь. Остальной код не пишет SQL напрямую.

| Файл | За что отвечает |
|---|---|
| `schema.sql` | Главное описание таблиц базы (схема). Его точная копия лежит в `deploy/db/init/002_schema.sql`, и тест следит, чтобы они совпадали. |
| `db.py` | Подключение к PostgreSQL: пул соединений, поддержка векторов (расширение pgvector). |
| `base.py` | Описание интерфейсов хранилища: что должны уметь любые реализации. |
| `models.py` | Простые структуры данных, которыми обмениваются части хранилища. |
| `factory.py` | Выбор реализации хранилища по настройке `STORAGE_BACKEND` (`postgres` или `memory`). |
| `pg.py` | Реализация хранилища на PostgreSQL (боевая). |
| `memory.py` | Реализация «в памяти» для тестов. Данные пропадают при выходе. |
| `appeal_common.py` | Общий код хранения обращений для обеих реализаций. |
| `appeals_logger.py` | Журнал обращений: карточки, вопросы и проверки оператора (`pending`, `confirmed`, `corrected`, `rejected`). |
| `annotations_storage.py` | Пользовательские пояснения к кодам классификатора; для них считаются векторы, поэтому поиск «знает» о пояснениях. |

### 3.7. src/training/ — дообучение модели [РАБОТА, если нужно дообучение]

Дообучение улучшает модель на данных, которые подтвердили операторы. Выполняется воркером очереди `training`.

| Файл | За что отвечает |
|---|---|
| `finetune_model.py` | Дообучение модели на проверенных и исторических данных; сохраняет `models/e5-finetuned-vN/`, считает векторы новой версии, регистрирует её (включает, только если качество выросло). |
| `build_vectordb.py` | Расчёт векторов классификатора для версии модели и запись их в базу. |
| `auto_finetune.py` | Проверяет, накопилось ли достаточно данных (порог `FINETUNE_THRESHOLD`), и ставит задание дообучения в очередь. Можно запустить вручную: `python src/training/auto_finetune.py [--force]`. |
| `auto_import_historical.py` | Автоматический импорт исторических обращений из папки `data/historical/`. |
| `historical_loader.py` | Чтение и проверка файлов с историческими обращениями. |

### 3.8. src/integrations/ — внешние системы [РАБОТА]

| Файл | За что отвечает |

## 4. Папка scripts/: вспомогательные скрипты

Скрипты запускаются руками из корня проекта и не входят в боевой процесс. Условно их три группы.

### 4.1. scripts/db/ — база данных [РАБОТА]

| Файл | За что отвечает |
|---|---|
| `init_db.py` | Создаёт схему базы (таблицы). Безопасно запускать повторно. |
| `migrate_from_files.py` | Однократный перенос данных из файлового хранилища в PostgreSQL (классификатор, векторы и запись версии 0, исторические размеченные обращения; прошлые обращения и журналы не переносятся). Повторный запуск ничего не дублирует. Завершается с кодом 1, если итоги не сходятся. |
| `verify_search_parity.py` | Проверяет, что поиск по базе даёт тот же результат, что прежний поиск по файлам. |

В Docker эти скрипты выполняет контейнер `migrate` при каждом запуске.

### 4.2. Установка и подготовка стенда [РАБОТА при установке]

| `setup_infra_env.py` | Находит свободные порты для PostgreSQL и RabbitMQ и записывает их в `.env`. |
| `check_offline.py` | Проверка готовности стенда без интернета (до и после установки). |
| `make_offline_bundle.py` | Собирает комплект для установки без интернета: библиотеки, модель, готовая база. |
| `make_hf_cache.py` | Готовит кэш Hugging Face с моделью эмбеддингов для стенда без сети. |
| `classify_folder_to_xlsx.py` | Утилита: классифицирует пачку файлов из папки и складывает результат в Excel. |
| `anonymize_xlsx.py` | Утилита: обезличивает Excel-файл с обращениями перед тем, как показывать его кому-то ещё. |

### 4.3. Инструменты экспериментов [РАЗРАБОТКА]

Эти скрипты нужны исследователям качества: пробовали другие модели, переранжирование, обучение на наборе «ii25». В боевом сервисе они не используются, и запускать их для работы системы не нужно. Результаты экспериментов лежат в `data/` и `docs/`.

| Файл | Что делает |
|---|---|
| `import_ii25_dataset.py` | Превращает набор документов «ii25» (DOCX, метки в именах файлов) в файлы JSONL для обучения и проверки. |
| `generate_hard_negatives.py` | Подбирает «трудные» неправильные кандидаты для обучения. |
| `encode_queries.py` | Заранее считает векторы запросов из набора и сохраняет в `data/` (в Git не идут). |
| `train_adapter.py`, `apply_adapter.py` | Обучение и применение «адаптера», лёгкой надстройки над векторами. |
| `build_ltr_dataset.py`, `train_ltr.py` | Набор данных и обучение модели ранжирования (Learning to Rank). |
| `finetune_reranker.py`, `finetune_ce_direct.py` | Дообучение переранжирующей модели (cross-encoder). |

## 11. Персональные данные: что никогда не идёт в Git

В обращениях граждан есть персональные данные (ФИО, адреса, телефоны), на них распространяется 59-ФЗ. Поэтому следующие места не должны попадать в Git, в письма и в общие чаты.

| Где | Что там | Почему важно |
|---|---|---|
| Том Docker `pgdata` | Вся база: тексты обращений, результаты, проверки операторов, реестр моделей. | Основное хранилище. Не удаляйте том (`docker compose down -v` запрещено) и не выкладывайте дамп. |
| `.env` | Ключи доступа к LLM, пароли PostgreSQL и RabbitMQ, настройки RX. | Секреты. Образец для общего пользования только `.env.example`. |
| `run/` | Логи и pid-файлы локального запуска. | В логах встречаются тексты обращений. |
| `data/temp_upload/` | Файл исторических обращений на время разбора (потом удаляется). | Это настоящие документы. |
| `data/historical/` (кроме `README.md` и примера) | Файлы исторических обращений для импорта. | Реальные обращения. |
| `data/appeals_log.jsonl`, `data/request_log.jsonl`, `data/jobs/`, `data/historical_verified.jsonl`, `data/classifier_annotations.json` | Остатки прежнего файлового хранилища. | Исключены через `.gitignore`. |
| `logs/` | Логи запуска сервиса. | Могут содержать фрагменты обращений. |

Практическое правило: перед коммитом посмотрите `git status`. Если видите незнакомые файлы в `data/`, `run/`, `logs/` или любой `.env`, не добавляйте их. В тестах и примерах используйте только придуманные тексты, например: «Прошу отремонтировать дорогу во дворе дома №5».
