## 1. Из чего состоит сервис

Сервис получает текст обращения гражданина и подбирает для него коды Общероссийского
классификатора вопросов обращений. Он состоит из нескольких процессов. Знать их нужно, чтобы
понимать, что запускается и что может сломаться.

| Часть | Что это и зачем |
|---|---|
| **API** | Веб-сервер на FastAPI. Принимает запросы от RX и из браузера, отдаёт веб-страницы. Сам ничего не классифицирует. |
| **RabbitMQ** | Брокер сообщений. API кладёт в него задачи, воркеры их забирают. **Очередь** — это список задач, ждущих обработки; их три: `classify_sync`, `classify`, `training`. |
| **Воркер классификации** | Отдельный процесс (Celery), который берёт задачу из очереди и классифицирует обращение. **Воркер** — это просто программа-исполнитель, их может быть несколько. |
| **Воркер дообучения** | Необязательный процесс, который дообучает модель поиска на проверенных оператором данных. |
| **PostgreSQL + pgvector** | База данных. Хранит классификатор, обращения, результаты, задачи, версии модели. pgvector — расширение для хранения **векторов**. |
| **Модель эмбеддингов** | `intfloat/multilingual-e5-base`. Превращает текст в **вектор** (эмбеддинг) — набор из 768 чисел, по которому ищутся похожие пункты классификатора. Скачивается с Hugging Face. |
| **LLM** | Большая языковая модель (Qwen у Ario, модель Заказчика через vLLM и т. п.). Получает текст обращения и кандидатов из поиска и выбирает коды. Работает на внешнем сервере, к которому сервис обращается по HTTP. |

PostgreSQL и RabbitMQ всегда работают в Docker. API и воркеры работают либо тоже в Docker
(режим «docker»), либо как обычные процессы Python из виртуального окружения `venv`
(режим «local»). Подробнее — в [arch.md](arch.md).

## 2. Требования

### Операционная система и программы

| Что | Требование |
|---|---|
| ОС | Windows 10/11 или Windows Server с Docker Desktop; Linux x86_64 с Docker Engine |
| Docker | **Docker Desktop** (Windows) или **Docker Engine** (Linux) с плагином **Docker Compose v2** — команда `docker compose version` должна работать |
| Python | **3.11** (на нём работает прод) или **3.13** (проверен полным прогоном тестов). 3.12 установщик принимает, но тестами она не проверялась. **3.14 не подходит**: с ней несовместима библиотека `sentence-transformers` |
| Git | Нужен для получения и обновления кода |

Python нужен для режима «local», для установщиков и служебных скриптов. В режиме «docker»
интерпретатор берётся из образа (по умолчанию Python 3.11).

Библиотека `numpy` выбирается автоматически по версии Python: на 3.11 ставится 1.x, на 3.12 и
новее — 2.x (так записано в `requirements.txt`). Ничего делать не нужно.

### Ресурсы

Цифры ниже — ориентиры из документации развёртывания, а не строгие пределы.

| Ресурс | Ориентир |
|---|---|
| Диск | около 3 ГБ: библиотека `torch` для CPU и окружение `venv` (~1,3 ГБ), модель эмбеддингов (~1,1 ГБ на диске), образы Docker. Сборка `torch` с CUDA заметно тяжелее |
| Память | около 1,5 ГБ на каждый процесс воркера с загруженной моделью. С двумя воркерами классификации, API, PostgreSQL и RabbitMQ закладывайте 4–6 ГБ |
| Процессор | Подходит обычный CPU. Видеокарта нужна только для ускорения дообучения |

### Сеть

| Куда | Зачем | Когда обязательно |
|---|---|---|
| `huggingface.co` | Скачать модель эмбеддингов при первом запуске воркера | Если модели ещё нет в кеше. Без интернета — см. [раздел 5](#5-установка-без-интернета) |
| PyPI и `download.pytorch.org` | Установить библиотеки Python, собрать образ Docker | При установке и при сборке образа |
| Docker Hub | Скачать образы `pgvector/pgvector:pg16` и `rabbitmq:3.13-management` | При первой установке |
| Адрес LLM | Классификация. Например, `https://llm.ario.directum360.ru/v1` (Ario, доступен из корпоративной сети или по VPN) или адрес vLLM Заказчика в его сети | Всегда |
| OData Directum RX | Забрать текст документа по его номеру | Только если RX вызывает сервис по `document_id` без текста |
| Входящие подключения на порт API (8010) | RX и пользователи обращаются к сервису | Всегда |

## 3. Установка на Windows

Установка выполняется один раз скриптом `install.bat` в корне проекта. Он задаёт вопросы в
консоли и в конце сам поднимает базу и брокер.

### Подготовка

1. Установите Python 3.11 или 3.13 с python.org. В установщике отметьте **Add Python to PATH**.
   Проверка: в новой консоли `py -3.11 --version` (или `py -3.13 --version`) печатает версию.
2. Установите Docker Desktop и запустите его. Дождитесь надписи **Engine running**.
   Проверка: `docker compose version` и `docker info` выполняются без ошибок.
3. Получите код проекта, например:
   ```bat
   git clone https://github.com/nikitakorotaevnikita-sudo/Class-OG-Final.git
   cd Class-OG-Final
   ```
4. Подготовьте ответы на вопросы установщика: какой провайдер LLM использовать, его адрес и ключ;
   при вызове RX по номеру документа — адрес OData RX, логин и пароль.

### Шаги установщика

Запустите `install.bat` двойным щелчком или из консоли в корне проекта. Он проходит шесть шагов.

**[1/6] Поиск Python.** Скрипт ищет Python 3.13, 3.12, 3.11 — сначала через `py`, потом среди
`python3.13`, `python3.12`, `python3.11`, `python` в PATH. Вы увидите `OK: Python 3.11.9` или
похожую строку. Если Python не найден, скрипт покажет ссылки на загрузку и остановится —
установите Python с флажком «Add Python to PATH» и запустите `install.bat` снова.

**[2/6] Виртуальное окружение.** Создаётся папка `venv` — отдельная копия Python с библиотеками
проекта. Если папка уже есть, шаг пропускается. Папку `venv` нельзя копировать с другой машины:
она привязана к пути к интерпретатору.

**[3/6] Зависимости.** Ставятся библиотеки из `requirements.txt`. Шаг занимает несколько минут и
требует интернета. При ошибке появится `ERROR: pip install failed` — обычно это нет доступа к PyPI
или прокси. Проверьте сеть и запустите `install.bat` снова: готовое окружение не пересоздаётся.

**[4/6] Настройки `.env`.** Если файла `.env` нет, он создаётся копией `.env.example`. Затем
скрипт задаёт вопросы:

1. `Select LLM provider` — выбор провайдера LLM:

   | Ответ | Провайдер | Что спросит дальше |
   |---|---|---|
   | `1` (или Enter, или любой другой ответ) | `ario` — Directum360, основной для проекта | `ARIO_API_KEY` (токен) и `ARIO_BASE_URL` |
   | `2` | `custom` — свой OpenAI-совместимый сервер Заказчика (vLLM) | `CUSTOM_LLM_BASE_URL` (например `http://10.0.0.5:8000/v1`), `CUSTOM_LLM_MODEL`, `CUSTOM_LLM_API_KEY` (Enter — без ключа) |
   | `3` | `ollama` — локальная модель | ничего; напомнит установить Ollama и выполнить `ollama pull qwen2.5-14b` |
   | `4` | `groq` — облако | `GROQ_API_KEY` (вида `gsk_...`) |
   | `5` | `gemini` — облако, 20 запросов в сутки бесплатно | `GEMINI_API_KEY` |

   Для Ario в квадратных скобках предлагается адрес `https://llm.ario.directum360.ru/v1`; Enter
   принимает его. Если вам выдали другой адрес, введите его. Если ключ не ввести, скрипт напишет
   `SKIPPED` — ключ можно вписать в `.env` позже.

2. `RX OData URL`, `RX User`, `RX Password` — подключение к Directum RX. Нужны **только** если RX
   будет вызывать сервис по номеру документа без текста. Enter оставляет предложенные значения
   адреса и пользователя. Пароль по умолчанию не подставляется: при пустом пароле появится
   `WARN: RX password empty - calls by document_id will fail with 502`. Это нормально, если RX
   присылает текст обращения в запросе.

**[5/6] Векторная база.** Только сообщение: векторы классификатора лежат в Git (папка
`data/vector_db_adapted_v3`) и на шаге 6 переносятся в PostgreSQL. Ничего не строится.

**[6/6] PostgreSQL и RabbitMQ в Docker, перенос данных.** Скрипт вызывает
`scripts\setup_infra.cmd`, который делает три вещи:

1. **Выбирает порты** с помощью `scripts\setup_infra_env.py` и пишет их в `.env`. Для каждого
   порта на машине (PostgreSQL — `POSTGRES_PORT`, RabbitMQ — `RABBITMQ_PORT`, веб-консоль
   RabbitMQ — `RABBITMQ_MGMT_PORT`) правило такое:
   - значение уже задано в `.env` и порт свободен (или его занимает контейнер этого же
     проекта) — остаётся как есть;
   - не задано — берётся стандартный порт (5432, 5672, 15672), если он свободен;
   - стандартный порт занят, например «родным» PostgreSQL, — берётся первый свободный из запасных:
     5434, 5435, … для PostgreSQL (5433 пропускается — его занимает тестовая база), 5673, … для
     RabbitMQ, 15673, … для веб-консоли;
   - в `.env` вписан нестандартный порт, а он занят чужой программой — ошибка с именем ключа.
     Исправьте значение или очистите его (`POSTGRES_PORT=`), и установщик подберёт порт сам.

   Вместе с портами в `.env` записываются `DATABASE_URL` и `RABBITMQ_URL` на `localhost` с этими
   портами и логинами-паролями из `POSTGRES_*` и `RABBITMQ_DEFAULT_*`. Если `DATABASE_URL` или
   `RABBITMQ_URL` указывает на другую машину, он не трогается. Вы увидите строки вида:
   ```
     POSTGRES_PORT=5434  (5432 is busy, picked first free fallback 5434)
     RABBITMQ_PORT=5672  (default, free)
     DATABASE_URL -> localhost:5434  (credentials from POSTGRES_*)
     OK: ports and URLs written to .env
   ```
   Скрипт можно безопасно запускать повторно: `venv\Scripts\python.exe scripts\setup_infra_env.py`
   (с ключом `--dry-run` он только покажет план, не меняя файл).

2. **Запускает контейнеры**: `docker compose up -d --wait postgres rabbitmq`. Команда ждёт, пока
   обе службы пройдут проверку готовности. Успех — строка
   `OK: PostgreSQL and RabbitMQ are running`.

3. **Выполняет миграцию**: `start.cmd migrate`. **Миграция** — создание таблиц в базе и разовый
   перенос данных из файлов проекта (классификатор, векторы, журналы) в PostgreSQL. Успех —
   `OK: database schema and data import are ready`. При повторной установке перенос пропускается:
   в базе уже есть отметка о нём.

Если Docker не установлен или не запущен, это **не ошибка установки**: скрипт напишет `NOTE: ...`
и подскажет выполнить `start.cmd migrate` позже. Можно и сразу запустить `launch.bat server` —
он поднимет PostgreSQL и RabbitMQ сам.

В конце вы увидите `Installation complete! Run launch.bat to start.` Если шаг 6 не прошёл —
`Installation finished, but the infrastructure step failed - see above.` и код выхода 1.

### Что проверить после установки

1. В корне появились папка `venv` и файл `.env`.
2. `docker compose ps` показывает `postgres` и `rabbitmq` в состоянии `running (healthy)`.
3. `launch.bat check` проверяет установку (импорты, загрузку модели, поиск) и печатает итог.

Есть также `setup.ps1` — альтернативный установщик на PowerShell. Шаг инфраструктуры он не
выполняет: после него запустите `start.cmd migrate` или сразу `launch.bat server`.

## 4. Установка на Linux

На Linux то же делает `./install.sh` (общие функции — в `scripts/install_common.sh`).

### Подготовка

1. Python 3.11, 3.12 или 3.13 с модулем `venv`. На Debian/Ubuntu:
   `sudo apt install python3.11 python3.11-venv`.
2. Docker Engine с плагином Compose v2. Пользователь, от которого идёт установка, должен иметь
   доступ к Docker (`docker info` без `sudo`).
3. Запускайте установку **не от root** — иначе файлы проекта получат владельца root. Скрипт
   предупредит об этом.

### Запуск

```bash
./install.sh                    # обычная установка, torch для CPU
./install.sh --gpu              # torch с CUDA (для машины с видеокартой)
./install.sh --non-interactive  # без вопросов, значения из переменных окружения
./install.sh --port 9000        # порт, который будет показан в подсказках в конце
```

Ключ `--systemd` не поддерживается: скрипт сообщит об этом и завершится. Службы systemd для
нового состава процессов не сделаны — используйте `./start.sh`.

### Шаги

| Шаг | Что происходит |
|---|---|
| `[1/7]` | Поиск Python 3.13 / 3.12 / 3.11 (`python3.13`, …, `python3`, `python`) |
| `[2/7]` | Создание `venv`. Нерабочее окружение (например, скопированное с другой машины) пересоздаётся |
| `[3/7]` | `torch` для CPU с `download.pytorch.org` (около 200 МБ вместо ~2,5 ГБ сборки с CUDA), затем `requirements.txt` |
| `[4/7]` | `.env` из `.env.example`, вопросы о провайдере LLM (`1`–`5`, по умолчанию `1` = ario) и его адресе/ключе, затем о RX. Файл получает права `600` — в нём ключи |
| `[5/7]` | Проверка файлов векторов в `VECTOR_DB_DIR` |
| `[6/7]` | Проверка установки: `scripts/check_offline.py --stage post --online` |
| `[7/7]` | Порты, контейнеры PostgreSQL и RabbitMQ, миграция — так же, как шаг 6 на Windows |

Отличия от Windows: провайдер `ollama` спрашивает `OLLAMA_BASE_URL`; для RX значения по
умолчанию пустые — если RX присылает текст обращения, просто нажимайте Enter.

В режиме `--non-interactive` скрипт берёт значения из переменных окружения с теми же именами:
`LLM_PROVIDER`, `ARIO_API_KEY`, `ARIO_BASE_URL`, `CUSTOM_LLM_BASE_URL`, `CUSTOM_LLM_MODEL`,
`CUSTOM_LLM_API_KEY`, `OLLAMA_BASE_URL`, `RX_ODATA_URL`, `RX_USER`, `RX_PASSWORD`, `PORT`.
Например:

```bash
LLM_PROVIDER=custom CUSTOM_LLM_BASE_URL=http://10.0.0.5:8000/v1 \
CUSTOM_LLM_MODEL=openai/gpt-oss-20b ./install.sh --non-interactive
```

В конце скрипт печатает, как запустить (`./launch.sh server 8010`), остановить
(`./stop.sh local`) и проверить сервис (`curl http://127.0.0.1:8010/health`).

## 5. Установка без интернета

Для стенда без интернета есть `install_offline.bat` и `./install_offline.sh`. Они ставят всё из
заранее собранного комплекта `offline_bundle/` (библиотеки, модель эмбеддингов, готовые векторы).

Коротко:

1. На машине **с интернетом** соберите комплект под ту версию Python, что стоит **на стенде**:
   ```bash
   python scripts/make_offline_bundle.py --python-version 3.11            # для Windows-стенда
   python scripts/make_offline_bundle.py --python-version 3.11 --linux    # для Linux-стенда
   ```
2. Там же скачайте и сохраните образы базы и брокера:
   ```bash
   docker pull pgvector/pgvector:pg16
   docker pull rabbitmq:3.13-management
   docker save -o infra-images.tar pgvector/pgvector:pg16 rabbitmq:3.13-management
   ```
3. Перенесите проект на стенд **без папки `venv`**, вместе с `offline_bundle/` и
   `infra-images.tar`. На стенде загрузите образы: `docker load -i infra-images.tar`.
4. Запустите `install_offline.bat` (или `./install_offline.sh`). Установщик проверит, подходят ли
   библиотеки к вашему Python, поставит их без сети, пропишет в `.env` флаг `HF_HUB_OFFLINE=1` и
   путь к локальной модели `EMBEDDING_MODEL=offline_bundle/models/multilingual-e5-base`.
5. LLM на изолированном стенде — только `custom` (vLLM Заказчика в его сети) или `ollama`.
   Установщик предлагает их первыми.

Подробности и частые ошибки — в [../docs/OFFLINE-INSTALL.md](../docs/OFFLINE-INSTALL.md). Учтите,
что раздел «Ход установки» там описывает старый вариант из шести шагов и ручной запуск
`uvicorn`; сейчас установщик делает семь шагов, последний — PostgreSQL, RabbitMQ и миграция, а
запускается сервис через `launch.bat server` (`start.cmd local`). Режим «docker» на стенде без
интернета не подходит: образ приложения собирается командой `docker compose up --build`, которой
нужен доступ к PyPI.

## 6. Запуск, остановка и проверка

### Два режима работы

| Режим | Что где работает | Когда выбирать |
|---|---|---|
| **docker** | Всё в контейнерах: PostgreSQL, RabbitMQ, миграция, API, воркеры | Сервер с Docker и интернетом для сборки образа. Самый простой в сопровождении |
| **local** | PostgreSQL и RabbitMQ в Docker, API и воркеры — процессы Python из `venv` | Рабочая станция, стенд без интернета, отладка |

### Команды

| Windows | Linux | Что делает |
|---|---|---|
| `start.cmd` | `./start.sh` | Режим docker: `docker compose up -d --build`, затем ожидание готовности (до 2 минут) |
| `start.cmd --training` | `./start.sh --training` | То же плюс воркер дообучения |
| `start.cmd local` | `./start.sh local` | Режим local: контейнеры базы и брокера, миграция, затем API и воркеры |
| `start.cmd local --port 9100` | `./start.sh local --port 9100` | Режим local на другом порту. В режиме docker `--port` не действует — порт там задаёт `HOST_PORT` |
| `start.cmd migrate` | `./start.sh migrate` | Только создание таблиц и перенос данных из файлов (база должна быть запущена) |
| `stop.cmd` | `./stop.sh` | Остановить режим docker: `docker compose --profile training down`. Контейнеры удаляются, **данные в томе `pgdata` остаются** |
| `stop.cmd local` | `./stop.sh local` | Остановить API и воркеры режима local, затем `docker compose stop postgres rabbitmq` |
| `launch.bat` | `./launch.sh` | Меню (см. ниже) |
| `launch.bat server [порт]` | `./launch.sh server [порт]` | То же, что `start.* local --port …` |

Если файла `.env` нет, `start.*` создаёт его из `.env.example` и предупреждает: впишите ключи LLM
и пароли, затем перезапустите.

**Как выглядит режим local.** На Windows открываются отдельные окна: `classifier-api` и
`classifier-worker-1`, `classifier-worker-2` (их число — `CLASSIFY_WORKERS`), при `--training`
ещё `classifier-worker-training`. Окна не закрывайте: в них работают процессы и видны их сообщения.
Если процесс упал, окно остаётся открытым, и ошибку можно прочитать. На Linux процессы
работают в фоне, номера процессов и журналы лежат в папке `run/`.

Ход запуска виден по шагам `[1/4]`…`[4/4]`: контейнеры, схема базы, перенос данных, API и
воркеры. В конце появляется строка
`OK: API is up, database and broker reachable: http://localhost:8010/health` и адрес бэк-офиса.

**Режимы docker и local одновременно на одном порту не работают.** Оба по умолчанию используют
порт 8010. Если порт занят, `start.* local` останавливается с ошибкой `port 8010 is already in use`.
Остановите другой режим (`stop.cmd`) или выберите порт: `start.cmd local --port 9100`.

### Меню `launch.bat`

```
[1] Start API server (port 8010)      — запуск режима local
[2] Start API server on another port
[3] Verify the installation           — проверка установки
[4] Run tests
[5] Classify manually (type appeal text)
[6] Operator mode  (verify + fine-tuning)
[7] Select LLM provider               — переключает только LLM_PROVIDER в .env
```

Порт режима local выбирается так: аргумент запуска → `API_PORT` в `.env` → 8010.
У `./launch.sh` меню короче (пункты 1–6, без выбора провайдера).

### Проверка готовности

Откройте в браузере или выполните:

```bash
curl http://localhost:8010/health
```

Ответ работающего сервиса:

```json
{"status":"ok","agent_ready":true,"classifier_entries":2108,"db":true,"broker":true}
```

| Поле | Что значит | Если не так |
|---|---|---|
| `db` | API достучался до PostgreSQL | `false` — база недоступна, см. [раздел 12](#12-неполадки-и-что-с-ними-делать) |
| `broker` | API достучался до RabbitMQ | `false` — брокер недоступен |
| `agent_ready` | Хотя бы один воркер слушает очередь классификации | `false` — воркеры не запущены или ещё стартуют |
| `classifier_entries` | Сколько пунктов классификатора в базе | Должно быть 2108. `0` — миграция не прошла |

Адрес `/health` всегда отвечает кодом 200, поэтому смотрите на поля, а не на код ответа.

Другие адреса: форма классификации — `http://localhost:8010/`, бэк-офис —
`http://localhost:8010/backoffice`, описание API — `http://localhost:8010/docs`.

Первая классификация после запуска идёт дольше обычного: воркер загружает модель эмбеддингов, а
если её нет в кеше — скачивает (около 1 ГБ).

## 7. Важные настройки

Все настройки лежат в файле `.env` в корне проекта. Это обычный текстовый файл вида
`КЛЮЧ=значение`, одна настройка на строку; строки с `#` — комментарии. Шаблон со всеми
ключами и пояснениями — `.env.example`. Значения ниже взяты из `.env.example`; если ключа в
`.env` нет, действует значение по умолчанию из `src/core/config.py`.

Сохраняйте `.env` в кодировке UTF-8. Файл содержит пароли и ключи: в Git он не попадает, не
пересылайте его.

### 7.1. Провайдер LLM

| Ключ | Пример | Что задаёт |
|---|---|---|
| `LLM_PROVIDER` | `ario` | Какая LLM отвечает: `ario`, `custom`, `ollama`, `groq`, `gemini` |
| `ARIO_BASE_URL` | `https://llm.ario.directum360.ru/v1` | Адрес Ario |
| `ARIO_MODEL` | `Qwen/Qwen3.8-27B-Ario` | Имя модели на Ario |
| `ARIO_API_KEY` | — | Токен Ario |
| `CUSTOM_LLM_BASE_URL` | `http://10.0.0.5:8000/v1` | Адрес OpenAI-совместимого сервера Заказчика (vLLM, LM Studio) |
| `CUSTOM_LLM_MODEL` | `openai/gpt-oss-20b` | Имя модели, точно как его отдаёт сервер |
| `CUSTOM_LLM_API_KEY` | пусто | Ключ. Пусто — заголовок авторизации не отправляется |
| `OLLAMA_BASE_URL` | `http://localhost:11434/v1` | Адрес Ollama |
| `OLLAMA_MODEL` | `qwen2.5-14b` | Модель Ollama |
| `GROQ_API_KEY`, `GROQ_MODEL` | `llama-3.3-70b-versatile` | Ключ и модель Groq |
| `GEMINI_API_KEY` | — | Ключ Gemini |

**Какой провайдер выбрать.** `ario` — основной: на нём сделаны замеры точности, доступен из
корпоративной сети или по VPN. `custom` — модель Заказчика в его сети; единственный вариант на
стенде без интернета. `ollama` — модель на этой же машине. `groq` и `gemini` — облачные, для
проверки без корпоративного доступа.

**Имя модели должно совпадать с тем, что отдаёт сервер.** Набор моделей на Ario меняется без
предупреждения, а vLLM обычно отдаёт имя с префиксом (`openai/gpt-oss-20b`, а не `gpt-oss-20b`).
На неизвестное имя сервер отвечает `404`, и это легко принять за неверный адрес. Список моделей:
`GET <base_url>/models` или кнопка **«Проверить связь с LLM»** в бэк-офисе на вкладке
**«Настройки»** — она показывает проверенный адрес и список моделей.

**Ollama и Docker.** Внутри контейнера `localhost` — это сам контейнер, а не ваш сервер. В режиме
docker укажите `OLLAMA_BASE_URL=http://host.docker.internal:11434/v1` (то же для vLLM на этой же
машине). Имя `host.docker.internal` прописано в `docker-compose.yml` для API и воркеров.

### 7.2. PostgreSQL и RabbitMQ: порты, адреса, пароли

| Ключ | Пример | Что задаёт |
|---|---|---|
| `POSTGRES_PORT` | пусто → 5432 | Порт PostgreSQL на этой машине. Установщик подбирает свободный сам |
| `RABBITMQ_PORT` | пусто → 5672 | Порт RabbitMQ (протокол AMQP) на этой машине |
| `RABBITMQ_MGMT_PORT` | пусто → 15672 | Порт веб-консоли RabbitMQ |
| `DATABASE_URL` | пусто | Адрес базы для режима local, вида `postgresql://classifier:classifier@localhost:5434/classifier` |
| `RABBITMQ_URL` | пусто | Адрес брокера для режима local, вида `amqp://classifier:classifier@localhost:5672//` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `classifier` | Логин, пароль и имя базы в контейнере PostgreSQL |
| `RABBITMQ_DEFAULT_USER`, `RABBITMQ_DEFAULT_PASS` | `classifier` | Логин и пароль в контейнере RabbitMQ |

**Как выбираются и сохраняются порты.** Установщик (`scripts/setup_infra_env.py`) выбирает
свободные порты и пишет их в `.env` вместе с `DATABASE_URL` и `RABBITMQ_URL` (правило — в
[разделе 3](#шаги-установщика)). Уже записанные порты при повторной установке не меняются, если
свободны. Если `DATABASE_URL` / `RABBITMQ_URL` пустые, их собирают из `POSTGRES_*`,
`RABBITMQ_DEFAULT_*` и портов и `start.*`, и сам сервис.

**Порт в адресе и порт в `*_PORT` должны совпадать.** Если вы вручную поменяли `POSTGRES_PORT`,
поменяйте порт и в `DATABASE_URL` (или очистите `DATABASE_URL`). Иначе `start.* local`
остановится с ошибкой `DATABASE_URL points to port …, but POSTGRES_PORT=…` — это защита от
подключения к чужой базе. То же для `RABBITMQ_PORT` и `RABBITMQ_URL`.

**В режиме docker** `DATABASE_URL` и `RABBITMQ_URL` из `.env` не используются: внутри контейнеров
адреса заменяются на служебные имена `postgres:5432` и `rabbitmq:5672` (см. `docker-compose.yml`).

**Пароли.** Стандартные пароли `classifier` годятся только для машины, на которой база доступна
лишь локально. Задайте свои **до первого запуска**: PostgreSQL запоминает пароль при создании тома
`pgdata`, и смена `POSTGRES_PASSWORD` позже на уже существующую базу не подействует — придётся
менять пароль и в самой базе:

```bash
docker compose exec postgres psql -U classifier -d classifier -c "ALTER USER classifier PASSWORD 'новый_пароль'"
```

**Не используйте в паролях символы `@`, `/`, `:`, `#`.** Установщик и сервис экранируют их в
собираемых адресах, но внутри docker compose и в адресах, которые собирают сами `start.*`, пароль
подставляется как есть, и адрес ломается.

### 7.3. Порт API

| Ключ | По умолчанию | Где действует |
|---|---|---|
| `API_PORT` | 8010 | Режим local (`start.* local`, `launch.* server`). Аргумент `--port` важнее |
| `API_HOST` | `0.0.0.0` | Режим local: на каком адресе слушать. `0.0.0.0` — на всех интерфейсах |
| `HOST_PORT` | 8010 | Режим docker: порт на машине, который ведёт на порт 8005 внутри контейнера `api` |

Порт 8010 — тот адрес, который передан разработчикам RX. Меняйте его только вместе с настройкой
на стороне RX.

### 7.4. Бэк-офис

| Ключ | Пример | Что задаёт |
|---|---|---|
| `BACKOFFICE_USER` | `admin` | Логин бэк-офиса |
| `BACKOFFICE_PASSWORD` | `CHANGE_ME` | Пароль бэк-офиса. Если ключа нет совсем, действует `password` — обязательно задайте свой |

**Важно.** В текущей версии логин и пароль запрашиваются только при активации версии модели
(кнопка **«Активировать»** в разделе **«Модели»** бэк-офиса). Сама страница

ограничьте доступ к нему файрволом: пускайте только сервер RX и рабочие места сотрудников.

### 7.5. Directum RX

| Ключ | Пример | Что задаёт |
|---|---|---|
| `RX_ODATA_URL` | `http://172.16.96.98/integration/odata` | Адрес сервиса интеграции RX (OData) |
| `RX_USER` | `Administrator` | Пользователь RX |
| `RX_PASSWORD` | — | Пароль. Хранится только в `.env` |

Эти три ключа нужны **только** когда RX вызывает сервис по `document_id` без текста — тогда сервис
сам забирает документ из RX. Если RX присылает текст обращения в запросе (основной способ), их
можно не заполнять. При пустом пароле вызов по `document_id` вернёт `502`. Проверить подключение —
кнопкой **«Проверить подключение к RX»** на вкладке **«Настройки»** бэк-офиса.

Эти ключи обычно менять не нужно. В таблицах — значение из `.env.example`, а в скобках — значение

### 8.1. Поиск и качество

| Ключ | Значение | Что делает |

| `ENABLE_ANNOTATION_VECTORS` | `false` | Учитывать в поиске аннотации оператора к кодам |
| `VECTOR_DB_DIR` | `data/vector_db_adapted_v3` | Файлы векторов, которые миграция переносит в базу как версию модели 0 |
| `EMBEDDING_MODEL` | `intfloat/multilingual-e5-base` | Модель эмбеддингов (имя на Hugging Face или путь к папке) |
| `LLM_TIMEOUT_SEC` | `360` | Сколько секунд ждать ответа LLM |
| `LLM_MAX_RETRIES` | `5` | Сколько раз повторять запрос к LLM при таймауте, ограничении частоты, ошибке 5xx или битом ответе |

### 8.2. Очереди и воркеры

| Ключ | Значение | Что делает |
|---|---|---|
| `CLASSIFY_CONCURRENCY` | `2` | Сколько обращений один воркер классифицирует параллельно (режим docker и Linux) |
| `CLASSIFY_WORKERS` | `2` | Сколько процессов-воркеров открывает `start.cmd local` на Windows. Там один процесс = одна классификация за раз |
| `SYNC_WAIT_TIMEOUT_SEC` | `1800` | Сколько секунд синхронный запрос ждёт результат. Потом ответ `504`, а задача продолжает выполняться |
| `JOB_MAX_ATTEMPTS` | `2` | Сколько раз пробовать задачу, если воркер упал или пропала связь с базой/брокером |

| `BROKER_HEARTBEAT_SEC` | `0` | Проверка связи с RabbitMQ. `0` — выключена, и так надо: иначе брокер разрывает соединение во время долгой классификации |
| `DB_POOL_MAX` | `10` | Сколько соединений с базой держит один процесс |
| `STORAGE_BACKEND` | `postgres` | Хранилище. `memory` — только для тестов |

Чтобы ускорить обработку в режиме docker, добавьте воркеров:
`docker compose up -d --scale worker-classify=3`. Каждый воркер — это ещё ~1,5 ГБ памяти.

**Webhook** — обратный вызов: когда задача готова, сервис сам отправляет результат POST-запросом
на адрес, который указал вызывающий.

| Ключ | Значение | Что делает |
|---|---|---|
| `WEBHOOK_ALLOWED_HOSTS` | пусто | Хосты, на которые разрешено отправлять webhook: точные имена через запятую, без `http://` и масок. `host:port` разрешает только этот порт, имя без порта — любой. Пусто — webhook выключены. Пример: `rx.local,172.16.96.98:8443` |
| `WEBHOOK_SECRET` | пусто | Если задан, тело подписывается заголовком `X-Signature: sha256=<HMAC>` |

### 8.5. Прокси, Hugging Face, сеть Docker

| Ключ | Значение | Что делает |
|---|---|---|
| `RX_VIA_PROXY` | `auto` | Ходить ли в RX через системный прокси (`HTTP_PROXY`/`HTTPS_PROXY`). `auto` — внутренние адреса напрямую, внешние через прокси. `true` / `false` — всегда через прокси / всегда напрямую |
| `LLM_VIA_PROXY` | `auto` | То же для LLM. Webhook всегда работает по правилу `auto` |
| `HF_CACHE_DIR` | пусто | Папка кеша моделей Hugging Face на машине для режима docker. Пусто — `./.hf-cache` в папке проекта |

(`%USERPROFILE%\.cache\huggingface` или `~/.cache/huggingface`).

### 8.6. Несколько машин

Сервис проверен на одной машине. Схема для нескольких машин описана, но не проверялась:

1. PostgreSQL и RabbitMQ остаются на одной машине. На ней задайте `POSTGRES_BIND=0.0.0.0` и
   `RABBITMQ_BIND=0.0.0.0` (или адрес нужного сетевого интерфейса) — **только после смены**
   `POSTGRES_PASSWORD` и `RABBITMQ_DEFAULT_PASS`. Ограничьте доступ к портам файрволом: в базе
   персональные данные.
2. На каждой машине с воркерами — свой `.env`, где `DATABASE_URL` и `RABBITMQ_URL` указывают на
   общую машину, а не на `localhost`.
3. Папка `models/` должна быть общей сетевой папкой с одинаковым путём на всех машинах:
   дообученные модели не передаются ни через базу, ни через брокер.
4. Настройки из бэк-офиса меняют `.env` только на машине с API. На остальных правьте вручную.

## 9. Как меняются настройки и когда нужен перезапуск

Есть три способа поменять настройку.

**1. Вкладка «Настройки» в бэк-офисе** (`http://localhost:8010/backoffice#settings`). Там
редактируются только такие ключи:

- группа **«Модель LLM»**: `LLM_PROVIDER`, `ARIO_MODEL`, `ARIO_BASE_URL`, `ARIO_API_KEY`,
  `CUSTOM_LLM_BASE_URL`, `CUSTOM_LLM_MODEL`, `CUSTOM_LLM_API_KEY`, `GROQ_MODEL`, `GROQ_API_KEY`,
  `GEMINI_API_KEY`, `OLLAMA_MODEL`, `OLLAMA_BASE_URL`;
- группа **«Directum RX»**: `RX_ODATA_URL`, `RX_USER`, `RX_PASSWORD`;
- группа **«Очередь»**: `SYNC_WAIT_TIMEOUT_SEC`.

Кнопка **«Сохранить»** записывает значения в `.env` (рядом остаётся копия
`.env.bak-settings-<дата-время>`) и сразу применяет их в API. Ключи и пароли на форме показаны
звёздочками; пустое поле секрета означает «не менять».

**2. Пункт `[7] Select LLM provider` в `launch.bat`** — меняет только `LLM_PROVIDER`.

**3. Правка `.env` в редакторе.**

**Когда изменения подхватываются без перезапуска.** Воркеры перед каждой задачей проверяют, не
изменился ли `.env`, и применяют у себя новые значения — **только тех ключей, что перечислены в
пункте 1**. Поэтому у API и воркеров должен быть один и тот же файл `.env`: в режиме docker он
подключён во все контейнеры, в режиме local все процессы работают из одной папки.

**Когда нужен перезапуск.** Все остальные ключи (порты, пароли, флаги поиска, параметры очередей,
`BACKOFFICE_*`, `WEBHOOK_*`) читаются только при старте процесса. После их изменения:

- режим docker — снова `start.cmd` (`./start.sh`): `docker compose up` пересоздаст контейнеры с
  новыми значениями. Простого `docker compose restart` недостаточно — переменные из `.env`
  передаются контейнеру при его создании;
- режим local — `stop.cmd local`, затем `start.cmd local`.

## 10. Интеграция с Directum RX

RX обращается к сервису по HTTP на порт 8010. Все адреса начинаются с `/integration`. Код —
[../src/api/integration_api.py](../src/api/integration_api.py).

### Адреса

| Метод и адрес | Что делает |
|---|---|
| `POST /integration/classify-document` | Синхронный вызов: ответ приходит, когда классификация закончена |
| `POST /integration/classify-document-async` | Асинхронный вызов: сразу возвращает номер задачи, результат забирается опросом или приходит webhook-ом |
| `GET /integration/jobs/{job_id}` | Статус задачи и результат, когда он готов |
| `GET /integration/jobs?limit=20` | Сводка по очереди для диагностики, в том числе `worker_alive` |

Тело запроса для обоих вызовов:

```json
{"appeal_text": "Прошу отремонтировать дорогу во дворе дома №5", "document_id": 26}
```

- `appeal_text` — текст обращения. Основной способ.
- `document_id` — номер документа в RX. Возвращается в ответе как есть. Если текста нет, сервис
  сам забирает документ из RX по OData (нужны настройки из [раздела 7.5](#75-directum-rx)).
- `webhook_url` — только для асинхронного вызова: адрес, куда прислать результат.

### Синхронный вызов

```bash
curl -X POST http://localhost:8010/integration/classify-document \
  -H "Content-Type: application/json" \
  -d '{"appeal_text": "Прошу отремонтировать дорогу во дворе дома №5", "document_id": 26}'
```

Ответ содержит `document_id`, `applicant_fio`, `applicant_email`, `summary`, `reasoning` и список
`questions` с полями `code` и `question`. Описание полей — в [User_manual.md](User_manual.md).

Классификация длится от десятков секунд до нескольких минут, и всё это время соединение открыто.
Если результата нет за `SYNC_WAIT_TIMEOUT_SEC` (1800 секунд), приходит `504` с номером задачи
в тексте ошибки. Задача при этом **продолжает выполняться**, её результат можно забрать через
`GET /integration/jobs/{job_id}`.

### Асинхронный вызов

```bash
curl -X POST http://localhost:8010/integration/classify-document-async \
  -H "Content-Type: application/json" \
  -d '{"appeal_text": "Прошу отремонтировать дорогу во дворе дома №5", "document_id": 26}'
```

Ответ приходит сразу с кодом `202`:

```json
{"job_id": "47ecfc0e2ca64d31b94bce1828cb1422", "status": "queued",
 "queue_position": 2, "poll_url": "/integration/jobs/47ecfc0e2ca64d31b94bce1828cb1422"}
```

Затем RX опрашивает `GET /integration/jobs/<job_id>`, разумный интервал — 5 секунд. Поле `status`
принимает значения `queued` (ждёт), `running` (обрабатывается), `done` (готово, результат в
`result`) и `error` (текст ошибки в `error`). Результат хранится `JOB_TTL_HOURS` (24 часа), потом
опрос вернёт `404`.

**Webhook.** Если в асинхронном запросе передан `webhook_url`, после завершения задачи (`done` или
`error`) воркер отправит на этот адрес POST с тем же телом, что отдаёт опрос статуса. Делается до
трёх попыток, перенаправления (3xx) не выполняются. Хост адреса должен быть в
`WEBHOOK_ALLOWED_HOSTS`, иначе запрос сразу отклоняется с кодом `400`. При заданном
`WEBHOOK_SECRET` в заголовке `X-Signature` приходит подпись тела `sha256=<HMAC>`, по которой RX
может проверить отправителя.

### Коды ответов

| Код | Когда | Что делать |
|---|---|---|
| `200` | Синхронный вызов выполнен | — |
| `202` | Асинхронный вызов принят | Опрашивать `poll_url` |
| `400` | Пустой текст; нет ни текста, ни `document_id`; документ без текста (скан, битый файл); `webhook_url` не разрешён | Исправить запрос. Повтор не поможет |
| `404` | Документ не найден в RX; задача не найдена или срок её хранения истёк | Проверить номер |
| `429` | Очередь асинхронного приёма заполнена (`JOB_MAX_QUEUED`) | Повторить позже |
| `500` | Ошибка классификации, в том числе недоступна LLM | Повторить; при повторении — смотреть журналы воркера |
| `502` | Не удалось получить документ из RX | Проверить адрес OData, пароль, сеть |
| `503` | Недоступна база данных или RabbitMQ | Проверить `/health`, см. [раздел 12](#12-неполадки-и-что-с-ними-делать) |
| `504` | Синхронный вызов не дождался результата | Забрать результат по `job_id` из текста ошибки |

Перед отправкой документов RX стоит проверять `GET /health`: `agent_ready: true` значит, что
воркеры готовы.

## 11. Эксплуатация

### Данные и тома Docker

Все данные — тексты обращений, результаты, проверки оператора, задачи, версии модели — хранятся
в PostgreSQL, в томе Docker `pgdata` (полное имя видно в `docker volume ls`, обычно
`<папка-проекта>_pgdata`). **Тексты обращений — персональные данные по 59-ФЗ.**

- `stop.cmd` / `./stop.sh` выполняют `docker compose down` **без** ключа `-v`, том остаётся.
- **Никогда не выполняйте `docker compose down -v`** и `docker volume rm` для этого тома без
  резервной копии: это удалит все данные безвозвратно.
- У RabbitMQ в `docker-compose.yml` нет именованного тома. Задачи, которые ещё лежат в очереди
  в момент `stop.cmd`, могут не пережить пересоздание контейнера брокера. Перед плановой
  остановкой дождитесь, пока очереди опустеют (см. веб-консоль RabbitMQ ниже).

### Резервное копирование PostgreSQL

Копия делается внутри контейнера и затем копируется на машину:

```bash
docker compose exec postgres pg_dump -U classifier -d classifier -Fc -f /tmp/classifier.dump
docker compose cp postgres:/tmp/classifier.dump ./classifier-2026-11-16.dump
docker compose exec postgres rm /tmp/classifier.dump
```

Если вы меняли `POSTGRES_USER` или `POSTGRES_DB`, подставьте свои значения. Храните копии в
защищённом месте: в них персональные данные. Восстановление в пустую базу:

```bash
docker compose cp ./classifier-2026-11-16.dump postgres:/tmp/classifier.dump
docker compose exec postgres pg_restore -U classifier -d classifier --clean --if-exists /tmp/classifier.dump
```

Перед восстановлением остановите API и воркеры.

### Журналы

| Режим | Где смотреть |
|---|---|
| docker | `docker compose logs -f api`, `docker compose logs -f worker-classify`, `docker compose logs migrate`, `docker compose logs postgres rabbitmq` |
| local, Windows | Окна `classifier-api`, `classifier-worker-N`, `classifier-worker-training` |
| local, Linux | Файлы `run/api.log`, `run/worker-classify.log`, `run/worker-training.log` |

Папка `run/` в Git не попадает: в журналах могут быть фрагменты обращений.

### Веб-консоль RabbitMQ

Откройте `http://localhost:15672` (или порт из `RABBITMQ_MGMT_PORT` в `.env`), логин и пароль —
`RABBITMQ_DEFAULT_USER` / `RABBITMQ_DEFAULT_PASS`. На вкладке **Queues** видны очереди
`classify_sync`, `classify`, `training`: сколько сообщений ждёт и сколько воркеров подключено
(столбец Consumers). По умолчанию консоль доступна только с этой машины (`RABBITMQ_BIND=127.0.0.1`).

### Зависшие задачи

Автоматической уборки нет. Если PostgreSQL или RabbitMQ были недоступны долго, часть задач может
навсегда остаться в статусе `queued` или `running`. Найти и закрыть их:

```bash
docker compose exec postgres psql -U classifier -d classifier
```

```sql
SELECT id, job_type, status, created_at FROM jobs
 WHERE status IN ('queued','running') AND created_at < now() - interval '1 hour';

UPDATE jobs SET status='error', error='прервана сбоем инфраструктуры', finished_at=now()
 WHERE status IN ('queued','running') AND created_at < now() - interval '1 hour';
```

RX по такой задаче получит `status: error` и сможет отправить документ повторно. Интервал
`1 hour` подберите сами: дообучение может идти часами, его задачи (`job_type = 'finetune'`)
не закрывайте, пока работает воркер дообучения.

### Воркер дообучения и версии модели

**Дообучение** — дополнительная тренировка модели эмбеддингов на обращениях, проверенных
оператором. Им занимается отдельный воркер, который запускается только по ключу `--training`:
`start.cmd --training` или `start.cmd local --training`. Без него задачи дообучения будут ждать
в очереди `training`.

Запустить дообучение можно из интерфейса (см. [User_manual.md](User_manual.md)) или командой:

```bash
venv\Scripts\python.exe src\training\auto_finetune.py            # проверит порог FINETUNE_THRESHOLD
venv\Scripts\python.exe src\training\auto_finetune.py --force    # без проверки порога
```

Одновременно может идти только одно дообучение (повторный запуск получит ответ `409`).

Каждое дообучение создаёт новую версию модели со своими векторами. Активна всегда одна версия:

- если дообучали от исходной версии 0, новая версия **никогда не включается сама** — проверьте
  качество и активируйте её вручную;
- если от дообученной версии (1 и выше) — новая включается сама, только если улучшился
  показатель recall@5.

Активация и откат — в бэк-офисе, раздел **«Модели»**, кнопка **«Активировать»** (браузер спросит
логин и пароль бэк-офиса). Воркеры переключаются на новую версию перед следующей задачей, без
перезапуска.

### Долгие задачи и «родной» RabbitMQ

Сервис подтверждает задачу брокеру только после её выполнения. По умолчанию RabbitMQ через
30 минут считает такую задачу зависшей и отдаёт её другому воркеру. В контейнер из
`docker-compose.yml` уже подключён файл `deploy/rabbitmq/rabbitmq.conf` со строкой
`consumer_timeout = 86400000` (24 часа). Если вы используете свой RabbitMQ, не из этого
проекта, добавьте ту же строку в его `rabbitmq.conf` и перезапустите брокер.

### Обновление приложения

1. Предупредите пользователей и дождитесь, пока очереди опустеют.
2. Сделайте резервную копию базы (см. выше).
3. Получите новый код: `git pull`.
4. Режим docker: `start.cmd` (`./start.sh`). Образ пересоберётся (`--build`), сервис `migrate`
   догонит схему базы, затем стартуют API и воркеры.
5. Режим local: `stop.cmd local`; если менялся `requirements.txt` —
   `venv\Scripts\python.exe -m pip install -r requirements.txt`; затем `start.cmd local`.
6. Проверьте `http://localhost:8010/health`.

Схема базы применяется при каждом запуске, повторно — без вреда. Перенос данных из файлов
выполняется один раз: после успешного переноса в таблицу `schema_meta` пишется отметка
`files_migrated`, и следующие запуски печатают «Данные из файлов уже перенесены …» и ничего не
трогают. Повторить перенос вручную (уже перенесённое пропускается):

```bash
venv\Scripts\python.exe scripts\db\migrate_from_files.py --force
```

## 12. Неполадки и что с ними делать

### Движок Docker не отвечает

Сообщение `ERROR: the Docker engine does not respond` (Linux: «движок Docker не отвечает»).
Docker установлен, но движок остановлен или завис.

1. Запустите Docker Desktop. Если он уже запущен — меню **Troubleshoot → Restart**.
2. Дождитесь надписи **Engine running**. Проверка: `docker info` выполняется без ошибки.
3. На Linux: `sudo systemctl start docker`; если ошибка про права на `docker.sock` — добавьте
   пользователя в группу `docker`.
4. Повторите команду запуска.

### Порт занят

- `ERROR: port 8010 is already in use` при `start.cmd local`. Обычно уже работает режим docker
  или прежний режим local. Выполните `stop.cmd` или `stop.cmd local`, либо запустите на другом
  порту: `start.cmd local --port 9100`.
- `ERROR: POSTGRES_PORT in .env: port … is busy` от установщика. Порт, вписанный вручную, занят
  чужой программой. Очистите значение (`POSTGRES_PORT=`) и запустите
  `venv\Scripts\python.exe scripts\setup_infra_env.py` — он подберёт свободный.
- `docker compose up` пишет `port is already allocated`. Порт из `.env` заняли после установки.
  Выполните `setup_infra_env.py` ещё раз и снова запустите сервис.
- `DATABASE_URL points to port …, but POSTGRES_PORT=…`. Порты в адресе и в отдельном ключе
  разошлись. Исправьте одно из значений в `.env` или очистите `DATABASE_URL`.

### В `/health` `db: false`

API не может подключиться к PostgreSQL.

1. `docker compose ps` — контейнер `postgres` должен быть `running (healthy)`. Если нет:
   `docker compose logs postgres`.
2. Режим local: проверьте, что порт в `DATABASE_URL` совпадает с `POSTGRES_PORT`, а пароль — с
   `POSTGRES_PASSWORD`. Ошибка `password authentication failed` после смены пароля в `.env`
   значит, что том помнит старый пароль (см. [раздел 7.2](#72-postgresql-и-rabbitmq-порты-адреса-пароли)).
3. Режим docker: если упал `migrate`, API не стартует — `docker compose logs migrate`. Код выхода
   1 у миграции значит, что сверка «файл → база» не сошлась: таблица сверки — в этом журнале.

### В `/health` `broker: false`

API не может подключиться к RabbitMQ.

1. `docker compose ps` — контейнер `rabbitmq` должен быть `healthy`. Брокер стартует до минуты.
2. `docker compose logs rabbitmq`.
3. Режим local: проверьте порт и пароль в `RABBITMQ_URL`.

### `agent_ready: false`

Ни один воркер классификации не слушает очередь.

- Режим docker: `docker compose ps worker-classify` и `docker compose logs worker-classify`.
- Режим local на Windows: посмотрите окна `classifier-worker-N`. На Linux — `run/worker-classify.log`.
- Сразу после запуска это нормально: подождите минуту.

### Синхронный вызов отвечает `504`

Классификация не уложилась в `SYNC_WAIT_TIMEOUT_SEC`. Задача не потеряна — заберите результат по
`job_id` из текста ошибки: `GET /integration/jobs/<job_id>`. Если `504` повторяется:

1. Проверьте `agent_ready` в `/health` — возможно, воркеры не работают и задачи копятся.
2. Проверьте очередь: `GET /integration/jobs` или веб-консоль RabbitMQ.
3. Проверьте связь с LLM кнопкой **«Проверить связь с LLM»** в бэк-офисе. Медленная LLM — частая
   причина.
4. При большой нагрузке добавьте воркеров или переведите RX на асинхронный вызов.

### Ответы `503`

База данных или RabbitMQ недоступны. Проверьте `/health` и действуйте по пунктам выше.

### Ответы `500` с текстом про LLM

LLM недоступна или отвечает ошибкой. Проверьте адрес, имя модели и ключ кнопкой
**«Проверить связь с LLM»**. На стенде без интернета `ario`, `groq` и `gemini` не работают —
переключитесь на `custom` или `ollama`. Если нужен прокси, проверьте `LLM_VIA_PROXY`.

### Воркеры постоянно перезапускаются

Контейнеры в `docker-compose.yml` перезапускаются автоматически (`restart: unless-stopped`),
поэтому падение выглядит как бесконечный перезапуск.

1. Посмотрите причину: `docker compose logs --tail 100 worker-classify`.
2. `Killed` или нехватка памяти — уменьшите `CLASSIFY_CONCURRENCY` или число воркеров, либо
   добавьте памяти. В Docker Desktop на Windows память ограничена настройками WSL2.
3. Ошибки загрузки модели (`Couldn't reach huggingface.co`, `FileMetadataError`) — нет доступа к
   Hugging Face. Откройте доступ, задайте `HF_ENDPOINT` с зеркалом или подготовьте модель офлайн
   ([раздел 5](#5-установка-без-интернета)).
4. Ошибки подключения к базе или брокеру — см. пункты про `db: false` и `broker: false`.

### Изменение в `.env` не подействовало

Без перезапуска подхватываются только ключи, которые есть на вкладке **«Настройки»** бэк-офиса
(см. [раздел 9](#9-как-меняются-настройки-и-когда-нужен-перезапуск)). Для остальных перезапустите
сервис: режим docker — `start.cmd`, режим local — `stop.cmd local` и `start.cmd local`. Также
проверьте, что файл называется именно `.env` (а не `.env.txt`) и сохранён в UTF-8.
