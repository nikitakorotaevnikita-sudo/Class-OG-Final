# Установка и настройка сервиса классификации обращений

## Для кого и о чём этот документ

Документ для системного администратора, который ставит сервис на сервер или рабочую станцию.
Предполагается, что вы знаете Windows или Linux и основы Docker, но этот проект видите впервые.
Здесь описано, что нужно заранее, как установить и запустить сервис, какие настройки важны,

Как пользоваться сервисом (форма классификации, верификация, бэк-офис) — в
[User_manual.md](User_manual.md). Устройство системы — в [arch.md](arch.md), таблицы базы — в

## 1. Из чего состоит сервис

Сервис получает текст обращения гражданина и подбирает для него коды Общероссийского
классификатора вопросов обращений. Он состоит из нескольких процессов. Знать их нужно, чтобы
понимать, что запускается и что может сломаться.

| Часть | Что это и зачем |
|---|---|
| **API** | Веб-сервер на FastAPI. Принимает запросы от RX и из браузера, отдаёт веб-страницы. Сам ничего не классифицирует. |
| **PostgreSQL + pgvector** | База данных. Хранит классификатор, обращения, результаты, версии модели и **очередь задач**. pgvector — расширение для хранения **векторов**. |
| **Очередь задач** | Таблица `jobs` в той же базе. **Очередь** — это список задач, ждущих обработки. API записывает туда задачу, воркер забирает её, выполняет и пишет туда же результат. Видов очереди три (это поле задачи): `classify_sync` — синхронные запросы, `classify` — фоновые, `training` — дообучение. Отдельного сервиса очередей нет. |
| **Воркер классификации** | Отдельный процесс Python (`python -m worker.run`), который берёт задачу из очереди и классифицирует обращение. **Воркер** — это просто программа-исполнитель. Один процесс выполняет одну задачу за раз, поэтому их запускают несколько (по умолчанию 2), в том числе на других машинах. |
| **Воркер дообучения** | Необязательный процесс, который дообучает модель поиска на проверенных оператором данных. |
| **Модель эмбеддингов** | `intfloat/multilingual-e5-base`. Превращает текст в **вектор** (эмбеддинг) — набор из 768 чисел, по которому ищутся похожие пункты классификатора. Скачивается с Hugging Face. |
| **LLM** | Большая языковая модель (Qwen у Ario, модель Заказчика через vLLM и т. п.). Получает текст обращения и кандидатов из поиска и выбирает коды. Работает на внешнем сервере, к которому сервис обращается по HTTP. |

PostgreSQL всегда работает в Docker. API и воркеры работают либо тоже в Docker (режим
`docker`), либо как обычные процессы Python из виртуального окружения `venv` (режим `all` —
основной). Воркеры можно вынести на другие машины: они подключаются к той же базе (режимы `api`
и `worker`, см. [раздел 6](#6-запуск-остановка-и-проверка) и
[раздел 8.6](#86-воркеры-на-других-машинах)). Подробнее — в [arch.md](arch.md).

Вариант с RabbitMQ развивается в ветке `Database_Rabbit`.

## 2. Требования

### Операционная система и программы

| Что | Требование |
|---|---|
| ОС | Windows 10/11 или Windows Server с Docker Desktop; Linux x86_64 с Docker Engine |
| Docker | **Docker Desktop** (Windows) или **Docker Engine** (Linux) с плагином **Docker Compose v2** — команда `docker compose version` должна работать |
| Python | **3.11** (на нём работает прод) или **3.13** (проверен полным прогоном тестов). 3.12 установщик принимает, но тестами она не проверялась. **3.14 не подходит**: с ней несовместима библиотека `sentence-transformers` |
| Git | Нужен для получения и обновления кода |

Python нужен для режимов `all`, `api` и `worker`, для установщиков и служебных скриптов. В
режиме `docker` интерпретатор берётся из образа (по умолчанию Python 3.11). Машине, где работают
только воркеры, Docker не нужен.

Библиотека `numpy` выбирается автоматически по версии Python: на 3.11 ставится 1.x, на 3.12 и
новее — 2.x (так записано в `requirements.txt`). Ничего делать не нужно.

### Ресурсы

Цифры ниже — ориентиры из документации развёртывания, а не строгие пределы.

| Ресурс | Ориентир |
|---|---|
| Диск | около 3 ГБ: библиотека `torch` для CPU и окружение `venv` (~1,3 ГБ), модель эмбеддингов (~1,1 ГБ на диске), образы Docker. Сборка `torch` с CUDA заметно тяжелее |
| Память | около 1,5 ГБ на каждый процесс воркера с загруженной моделью. С двумя воркерами классификации, API и PostgreSQL закладывайте 4–6 ГБ |
| Процессор | Подходит обычный CPU. Видеокарта нужна только для ускорения дообучения |

### Сеть

| Куда | Зачем | Когда обязательно |
|---|---|---|
| `huggingface.co` | Скачать модель эмбеддингов при первом запуске воркера | Если модели ещё нет в кеше. Без интернета — см. [раздел 5](#5-установка-без-интернета) |
| PyPI и `download.pytorch.org` | Установить библиотеки Python, собрать образ Docker | При установке и при сборке образа |
| Docker Hub | Скачать образ `pgvector/pgvector:pg16` | При первой установке |
| Адрес LLM | Классификация. Например, `https://llm.ario.directum360.ru/v1` (Ario, доступен из корпоративной сети или по VPN) или адрес vLLM Заказчика в его сети | Всегда |
| OData Directum RX | Забрать текст документа по его номеру | Только если RX вызывает сервис по `document_id` без текста |
| Входящие подключения на порт API (8010) | RX и пользователи обращаются к сервису | Всегда |
| Входящие подключения на порт PostgreSQL | Воркеры других машин работают с базой | Только если воркеры вынесены на другие машины ([раздел 8.6](#86-воркеры-на-других-машинах)) |

## 3. Установка на Windows

Установка выполняется один раз скриптом `install.bat` в корне проекта. Он задаёт вопросы в
консоли и в конце сам поднимает базу данных. Машину, где будут работать только воркеры,
ставит тот же скрипт — см. [«Машина только для воркеров»](#машина-только-для-воркеров) ниже.

### Подготовка

1. Установите Python 3.11 или 3.13 с python.org. В установщике отметьте **Add Python to PATH**.
   Проверка: в новой консоли `py -3.11 --version` (или `py -3.13 --version`) печатает версию.
2. Установите Docker Desktop и запустите его. Дождитесь надписи **Engine running**.
   Проверка: `docker compose version` и `docker info` выполняются без ошибок.
3. Получите код проекта, например:
   ```bat
   git clone https://github.com/nikitakorotaevnikita-sudo/Class-OG-Final.git
   cd Class-OG-Final
   ```
4. Подготовьте ответы на вопросы установщика: какой провайдер LLM использовать, его адрес и ключ;
   при вызове RX по номеру документа — адрес OData RX, логин и пароль.

### Шаги установщика

Запустите `install.bat` двойным щелчком или из консоли в корне проекта. Он проходит шесть шагов.

**[1/6] Поиск Python.** Скрипт ищет Python 3.13, 3.12, 3.11 — сначала через `py`, потом среди
`python3.13`, `python3.12`, `python3.11`, `python` в PATH. Вы увидите `OK: Python 3.11.9` или
похожую строку. Если Python не найден, скрипт покажет ссылки на загрузку и остановится —
установите Python с флажком «Add Python to PATH» и запустите `install.bat` снова.

**[2/6] Виртуальное окружение.** Создаётся папка `venv` — отдельная копия Python с библиотеками
проекта. Если папка уже есть, шаг пропускается. Папку `venv` нельзя копировать с другой машины:
она привязана к пути к интерпретатору.

**[3/6] Зависимости.** Ставятся библиотеки из `requirements.txt`. Шаг занимает несколько минут и
требует интернета. При ошибке появится `ERROR: pip install failed` — обычно это нет доступа к PyPI
или прокси. Проверьте сеть и запустите `install.bat` снова: готовое окружение не пересоздаётся.

**[4/6] Настройки `.env`.** Если файла `.env` нет, он создаётся копией `.env.example`. Затем
скрипт задаёт вопросы:

0. `Is this machine only for workers? [y/N]` — на главном сервере нажмите Enter (ответ «нет»).
   Ответ `y` — установка машины только для воркеров, см.
   [ниже](#машина-только-для-воркеров).

1. `Select LLM provider` — выбор провайдера LLM:

   | Ответ | Провайдер | Что спросит дальше |
   |---|---|---|
   | `1` (или Enter, или любой другой ответ) | `ario` — Directum360, основной для проекта | `ARIO_API_KEY` (токен) и `ARIO_BASE_URL` |
   | `2` | `custom` — свой OpenAI-совместимый сервер Заказчика (vLLM) | `CUSTOM_LLM_BASE_URL` (например `http://10.0.0.5:8000/v1`), `CUSTOM_LLM_MODEL`, `CUSTOM_LLM_API_KEY` (Enter — без ключа) |
   | `3` | `ollama` — локальная модель | ничего; напомнит установить Ollama и выполнить `ollama pull qwen2.5-14b` |
   | `4` | `groq` — облако | `GROQ_API_KEY` (вида `gsk_...`) |
   | `5` | `gemini` — облако, 20 запросов в сутки бесплатно | `GEMINI_API_KEY` |

   Для Ario в квадратных скобках предлагается адрес `https://llm.ario.directum360.ru/v1`; Enter
   принимает его. Если вам выдали другой адрес, введите его. Если ключ не ввести, скрипт напишет
   `SKIPPED` — ключ можно вписать в `.env` позже.

2. `RX OData URL`, `RX User`, `RX Password` — подключение к Directum RX. Нужны **только** если RX
   будет вызывать сервис по номеру документа без текста. Enter оставляет предложенные значения
   адреса и пользователя. Пароль по умолчанию не подставляется: при пустом пароле появится
   `WARN: RX password empty - calls by document_id will fail with 502`. Это нормально, если RX
   присылает текст обращения в запросе.

**[5/6] Векторная база.** Только сообщение: векторы классификатора лежат в Git (папка
`data/vector_db_adapted_v3`) и на шаге 6 переносятся в PostgreSQL. Ничего не строится.

**[6/6] PostgreSQL в Docker, перенос данных.** Скрипт вызывает `scripts\setup_infra.cmd`,
который делает три вещи:

1. **Выбирает порт PostgreSQL** с помощью `scripts\setup_infra_env.py` и пишет его в `.env`
   (ключ `POSTGRES_PORT`). Правило такое:
   - значение уже задано в `.env` и порт свободен (или его занимает контейнер этого же
     проекта) — остаётся как есть;
   - не задано — берётся стандартный порт 5432, если он свободен;
   - 5432 занят, например «родным» PostgreSQL, — берётся первый свободный из запасных 5434,
     5435, … (5433 пропускается — его занимает тестовая база);
   - в `.env` вписан нестандартный порт, а он занят чужой программой — ошибка с именем ключа.
     Исправьте значение или очистите его (`POSTGRES_PORT=`), и установщик подберёт порт сам.

   Вместе с портом в `.env` записывается `DATABASE_URL` на `localhost` с этим портом и
   логином-паролем из `POSTGRES_*`. Если `DATABASE_URL` указывает на другую машину, он не
   трогается. Вы увидите строки вида:
   ```
     POSTGRES_PORT=5434  (5432 is busy, picked first free fallback 5434)
     DATABASE_URL -> localhost:5434  (credentials from POSTGRES_*)
     OK: ports and URLs written to .env
   ```
   Скрипт можно безопасно запускать повторно: `venv\Scripts\python.exe scripts\setup_infra_env.py`
   (с ключом `--dry-run` он только покажет план, не меняя файл).

2. **Запускает контейнер базы**: `docker compose up -d --wait postgres`. Команда ждёт, пока
   база пройдёт проверку готовности. Успех — строка `OK: PostgreSQL is running`.

3. **Выполняет миграцию**: `start.cmd migrate`. **Миграция** — создание таблиц в базе и разовый
   перенос из файлов проекта в PostgreSQL того, без чего сервис не работает: классификатора,
   векторов и записи о версии модели 0, а также исторических размеченных обращений, если файл
   `data/historical_verified.jsonl` есть. Прошлые обращения, журналы и задачи не переносятся —
   эти таблицы создаются пустыми и заполняются в работе. Успех —
   `OK: database schema and data import are ready`. При повторной установке перенос пропускается:
   в базе уже есть отметка о нём.

Если Docker не установлен или не запущен, это **не ошибка установки**: скрипт напишет `NOTE: ...`
и подскажет выполнить `start.cmd migrate` позже. Можно и сразу запустить `launch.bat server` —
он поднимет PostgreSQL сам.

В конце вы увидите `Installation complete! Run launch.bat to start.` Если шаг 6 не прошёл —
`Installation finished, but the infrastructure step failed - see above.` и код выхода 1.

### Что проверить после установки

1. В корне появились папка `venv` и файл `.env`.
2. `docker compose ps` показывает `postgres` в состоянии `running (healthy)`.
3. `launch.bat check` проверяет установку (импорты, загрузку модели, поиск) и печатает итог.

Есть также `setup.ps1` — альтернативный установщик на PowerShell. Шаг инфраструктуры он не
выполняет: после него запустите `start.cmd migrate` или сразу `launch.bat server`.

### Машина только для воркеров

Так ставится дополнительная машина, на которой работают только воркеры, а база и API — на
главном сервере. Сначала подготовьте главный сервер по [разделу 8.6](#86-воркеры-на-других-машинах):
база должна принимать подключения с этой машины.

1. Подготовка — как выше, но Docker на этой машине не нужен.
2. Запустите `install.bat`. На вопрос `Is this machine only for workers? [y/N]` ответьте `y`.
3. Скрипт спросит адрес базы главного сервера **без пароля**:
   `Address without the password, postgresql://user@host:port/db`. Пример:
   `postgresql://classifier@192.168.10.5:5434/classifier` — здесь `192.168.10.5` — адрес главного
   сервера, `5434` — значение `POSTGRES_PORT` из его `.env`.
4. Затем `Password (hidden): ` — введите пароль базы (`POSTGRES_PASSWORD` главного сервера).
   Ввод не отображается. Скрипт сам закодирует особые символы пароля и запишет готовый
   `DATABASE_URL` в `.env` этой машины. Вы увидите
   `OK: DATABASE_URL saved to .env (database 192.168.10.5:5434)`. Сам адрес с паролем на экран
   не выводится.
5. Скрипт сразу проверит связь: `OK: PostgreSQL 192.168.10.5:5434 answers`. Если вместо этого
   `ERROR: PostgreSQL …: <причина>` — это только предупреждение, установка продолжится.
   Проверьте настройки главного сервера и адрес, затем повторите проверку командой
   `start.cmd worker`.
6. Дальше — те же вопросы о провайдере LLM и RX: воркеры обращаются к LLM сами, поэтому
   ключи LLM здесь нужны такие же, как на главном сервере.
7. Шаг `[6/6]` пропускается: `Worker-only machine: PostgreSQL is not started here`.
8. В конце: `Worker machine: start.cmd worker (launch.bat item 3), stop: stop.cmd worker` и
   напоминание про `MODELS_DIR` (см. [раздел 8.6](#86-воркеры-на-других-машинах)).

Офлайн-установщик `install_offline.bat` задаёт тот же вопрос и работает так же.

## 4. Установка на Linux

На Linux то же делает `./install.sh` (общие функции — в `scripts/install_common.sh`).

### Подготовка

1. Python 3.11, 3.12 или 3.13 с модулем `venv`. На Debian/Ubuntu:
   `sudo apt install python3.11 python3.11-venv`.
2. Docker Engine с плагином Compose v2. Пользователь, от которого идёт установка, должен иметь
   доступ к Docker (`docker info` без `sudo`).
3. Запускайте установку **не от root** — иначе файлы проекта получат владельца root. Скрипт
   предупредит об этом.

### Запуск

```bash
./install.sh                    # обычная установка, torch для CPU
./install.sh --gpu              # torch с CUDA (для машины с видеокартой)
./install.sh --non-interactive  # без вопросов, значения из переменных окружения
./install.sh --port 9000        # порт, который будет показан в подсказках в конце
./install.sh --worker-only      # машина только для воркеров: спросит адрес базы главного сервера
```

Ключ `--systemd` не поддерживается: скрипт сообщит об этом и завершится. Службы systemd для
нового состава процессов не сделаны — используйте `./start.sh`.

### Шаги

| Шаг | Что происходит |
|---|---|
| `[1/7]` | Поиск Python 3.13 / 3.12 / 3.11 (`python3.13`, …, `python3`, `python`) |
| `[2/7]` | Создание `venv`. Нерабочее окружение (например, скопированное с другой машины) пересоздаётся |
| `[3/7]` | `torch` для CPU с `download.pytorch.org` (около 200 МБ вместо ~2,5 ГБ сборки с CUDA), затем `requirements.txt` |
| `[4/7]` | `.env` из `.env.example`, вопросы о провайдере LLM (`1`–`5`, по умолчанию `1` = ario) и его адресе/ключе, затем о RX. Файл получает права `600` — в нём ключи |
| `[5/7]` | Проверка файлов векторов в `VECTOR_DB_DIR` |
| `[6/7]` | Проверка установки: `scripts/check_offline.py --stage post --online` |
| `[7/7]` | Порт и контейнер PostgreSQL, миграция — так же, как шаг 6 на Windows. С `--worker-only` — только проверка связи с базой главного сервера |

Отличия от Windows: провайдер `ollama` спрашивает `OLLAMA_BASE_URL`; для RX значения по
умолчанию пустые — если RX присылает текст обращения, просто нажимайте Enter.

В режиме `--non-interactive` скрипт берёт значения из переменных окружения с теми же именами:
`LLM_PROVIDER`, `ARIO_API_KEY`, `ARIO_BASE_URL`, `CUSTOM_LLM_BASE_URL`, `CUSTOM_LLM_MODEL`,
`CUSTOM_LLM_API_KEY`, `OLLAMA_BASE_URL`, `RX_ODATA_URL`, `RX_USER`, `RX_PASSWORD`, `PORT`, а с
`--worker-only` — ещё `DATABASE_URL` (адрес базы главного сервера целиком, с паролем).
Например:

```bash
LLM_PROVIDER=custom CUSTOM_LLM_BASE_URL=http://10.0.0.5:8000/v1 \
CUSTOM_LLM_MODEL=openai/gpt-oss-20b ./install.sh --non-interactive
```

В конце скрипт печатает, как запустить (`./launch.sh server 8010`), остановить (`./stop.sh`) и
проверить сервис (`curl http://127.0.0.1:8010/health`). С `--worker-only` — `./start.sh worker` и
`./stop.sh worker`; вопрос об адресе базы и пароле — как на Windows
([«Машина только для воркеров»](#машина-только-для-воркеров)).

## 5. Установка без интернета

Для стенда без интернета есть `install_offline.bat` и `./install_offline.sh`. Они ставят всё из
заранее собранного комплекта `offline_bundle/` (библиотеки, модель эмбеддингов, готовые векторы).

Коротко:

1. На машине **с интернетом** соберите комплект под ту версию Python, что стоит **на стенде**:
   ```bash
   python scripts/make_offline_bundle.py --python-version 3.11            # для Windows-стенда
   python scripts/make_offline_bundle.py --python-version 3.11 --linux    # для Linux-стенда
   ```
2. Там же скачайте и сохраните образ базы:
   ```bash
   docker pull pgvector/pgvector:pg16
   docker save -o infra-images.tar pgvector/pgvector:pg16
   ```
3. Перенесите проект на стенд **без папки `venv`**, вместе с `offline_bundle/` и
   `infra-images.tar`. На стенде загрузите образы: `docker load -i infra-images.tar`.
4. Запустите `install_offline.bat` (или `./install_offline.sh`). Установщик проверит, подходят ли
   библиотеки к вашему Python, поставит их без сети, пропишет в `.env` флаг `HF_HUB_OFFLINE=1` и
   путь к локальной модели `EMBEDDING_MODEL=offline_bundle/models/multilingual-e5-base`.
5. LLM на изолированном стенде — только `custom` (vLLM Заказчика в его сети) или `ollama`.
   Установщик предлагает их первыми.

Подробности и частые ошибки — в [../docs/OFFLINE-INSTALL.md](../docs/OFFLINE-INSTALL.md). Учтите,
что раздел «Ход установки» там описывает старый вариант из шести шагов и ручной запуск
`uvicorn`; сейчас установщик делает семь шагов, последний — PostgreSQL и миграция, а
запускается сервис через `launch.bat server` (`start.cmd all`). Режим `docker` на стенде без
интернета не подходит: образ приложения собирается командой `docker compose up --build`, которой
нужен доступ к PyPI.

## 6. Запуск, остановка и проверка

### Режимы запуска

Режим выбирается первым аргументом `start.cmd` (Linux — `./start.sh`). Без аргумента
запускается `all`.

| Режим | Что поднимается | Когда выбирать |
|---|---|---|
| **`all`** (по умолчанию; прежнее имя `local` тоже работает) | PostgreSQL в Docker, миграция, API и `CLASSIFY_WORKERS` воркеров из `venv` | «Всё из коробки» на одной машине. Основной вариант: рабочая станция, стенд без интернета |
| **`api`** | PostgreSQL в Docker, миграция, API — **без воркеров** | Главный сервер, когда воркеры работают на других машинах. Задачи копятся в очереди, пока не подключится воркер; `/health` показывает `agent_ready: false` |
| **`worker`** | Только воркеры из `venv`. Без Docker, миграции и API | Дополнительная машина для обработки ([раздел 8.6](#86-воркеры-на-других-машинах)). Адрес базы — `DATABASE_URL` из `.env` этой машины |
| **`docker`** | Всё в контейнерах: PostgreSQL, миграция, API, воркеры | Сервер с Docker и интернетом для сборки образа. С `--no-workers` — без контейнеров воркеров (как `api`) |
| **`migrate`** | Только создание таблиц и перенос данных из файлов | Обслуживание. База должна быть запущена |

Ключ `--training` добавляет воркер дообучения (режимы `all`, `worker`, `docker`).

### Команды

| Windows | Linux | Что делает |
|---|---|---|
| `start.cmd` или `start.cmd all` | `./start.sh` или `./start.sh all` | Режим `all`: контейнер базы, схема и перенос данных, затем API и воркеры. Ждёт готовности воркера (до 5 минут: воркер загружает модель) |
| `start.cmd all --training` | `./start.sh all --training` | То же плюс воркер дообучения |
| `start.cmd all --port 9100` | `./start.sh all --port 9100` | На другом порту (так же для `api`). В режиме `docker` `--port` не действует — порт там задаёт `HOST_PORT` |
| `start.cmd api` | `./start.sh api` | Режим `api`: база и API без воркеров. Ждёт только базу и предупреждает, что воркеров нет |
| `start.cmd worker` | `./start.sh worker` | Режим `worker`: проверяет связь с базой (печатает только адрес и порт базы), затем запускает воркеры |
| `start.cmd docker` | `./start.sh docker` | Режим `docker`: `docker compose up -d --build`, затем ожидание готовности |
| `start.cmd docker --no-workers` | `./start.sh docker --no-workers` | Только контейнеры `postgres`, `migrate`, `api` |
| `start.cmd migrate` | `./start.sh migrate` | Только схема и перенос данных |
| `stop.cmd` (или `stop.cmd all`, `stop.cmd api`, `stop.cmd local`) | `./stop.sh` | Остановить API и воркеры этой папки проекта, затем все контейнеры проекта: `docker compose stop`. Контейнеры и **данные в томе `pgdata` остаются** |
| `stop.cmd worker` | `./stop.sh worker` | Остановить только воркеры этой папки проекта. API и Docker не трогаются |
| `stop.cmd docker` | `./stop.sh docker` | `docker compose --profile training down`: контейнеры удаляются, том `pgdata` остаётся |
| `launch.bat` | `./launch.sh` | Меню (см. ниже) |
| `launch.bat server [порт]` | `./launch.sh server [порт]` | То же, что `start.* all --port …` |
| `launch.bat api [порт]` | `./launch.sh api [порт]` | То же, что `start.* api --port …` |
| `launch.bat worker` | `./launch.sh worker` | То же, что `start.* worker` |

Если файла `.env` нет, `start.*` создаёт его из `.env.example` и предупреждает: впишите ключи LLM
и пароли, затем перезапустите.

**Как выглядят режимы `all`, `api`, `worker`.** На Windows открываются отдельные окна:
`classifier-api` и `classifier-worker-1`, `classifier-worker-2` (их число — `CLASSIFY_WORKERS`),
при `--training` ещё `classifier-worker-training`. Окна не закрывайте: в них работают процессы и
видны их сообщения. Если процесс упал, окно остаётся открытым, и ошибку можно прочитать; после
этого закройте его вручную. На Linux процессы работают в фоне, номера процессов и журналы лежат
в папке `run/` (`run/api.log`, `run/worker-classify-1.log`, `run/worker-training.log`).

Ход запуска `all` и `api` виден по шагам `[1/4]`…`[4/4]`: контейнер базы, схема, перенос
данных, API и воркеры. В конце режима `all` появляется строка
`OK: API is up, database reachable, a classify worker is ready: http://localhost:8010/health` и
адрес бэк-офиса. В режиме `api` вместо неё:

```
  OK: API is up, database reachable: http://localhost:8010/health
  WARNING: no workers are running - jobs wait in the queue until a
           worker connects (start.cmd worker on a worker machine).
```

Режим `worker` печатает `OK: PostgreSQL <адрес>:<порт> answers`, затем открывает окна воркеров и
пишет `Worker windows: classifier-worker-*    Stop: stop.cmd worker`. Если окна воркеров этой
папки уже открыты, новые добавляются к ним — скрипт предупредит об этом; чтобы перезапустить
начисто, сначала `stop.cmd worker`.

**Как останавливаются воркеры.** `stop.cmd` завершает процессы сразу. `./stop.sh` сначала
просит процесс остановиться — воркер доделывает текущую задачу — и через 30 секунд завершает его
принудительно. Задача, которую воркер не успел доделать, не теряется: через `JOB_LEASE_SEC` (60 с) после остановки её возьмёт другой
работающий воркер, а если работающих нет — первый воркер после следующего запуска.

**Режимы `docker` и `all` одновременно на одном порту не работают.** Оба по умолчанию
используют порт 8010. Если порт занят, `start.cmd all` останавливается с ошибкой
`port 8010 is already in use`. Остановите другой режим (`stop.cmd docker` или `stop.cmd`) или
выберите порт: `start.cmd all --port 9100`.

### Меню `launch.bat`

```
[1] Start everything: API + workers (port 8010)       — режим all
[2] Start without workers: API only (port 8010)       — режим api
[3] Start workers only (DB = DATABASE_URL in .env)    — режим worker
[4] Start everything on another port                  — режим all, спросит порт
[5] Verify the installation                           — проверка установки
[6] Run tests
[7] Classify manually (type appeal text)
[8] Operator mode  (verify + fine-tuning)
[9] Select LLM provider                               — переключает только LLM_PROVIDER в .env
```

Порт выбирается так: аргумент запуска → `API_PORT` в `.env` → 8010. У `./launch.sh` те же
пункты в том же порядке, надписи на русском.

### Проверка готовности

Откройте в браузере или выполните:

```bash
curl http://localhost:8010/health
```

Ответ работающего сервиса:

```json
{"status":"ok","agent_ready":true,"classifier_entries":2108,"db":true}
```

| Поле | Что значит | Если не так |
|---|---|---|
| `db` | API достучался до PostgreSQL (в ней же очередь задач) | `false` — база недоступна, см. [раздел 12](#12-неполадки-и-что-с-ними-делать) |
| `agent_ready` | Хотя бы один воркер классификации подключён к базе и слушает очередь — на этой или на другой машине. API видит воркеры по их соединениям с базой | `false` — воркеры не запущены, ещё стартуют или это режим `api` без внешних воркеров |
| `classifier_entries` | Сколько пунктов классификатора в базе | Должно быть 2108. `0` — миграция не прошла |

Адрес `/health` всегда отвечает кодом 200, поэтому смотрите на поля, а не на код ответа.

Другие адреса: форма классификации — `http://localhost:8010/`, бэк-офис —
`http://localhost:8010/backoffice`, описание API — `http://localhost:8010/docs`.

Первая классификация после запуска идёт дольше обычного: воркер загружает модель эмбеддингов, а
если её нет в кеше — скачивает (около 1 ГБ).

## 7. Важные настройки

Все настройки лежат в файле `.env` в корне проекта. Это обычный текстовый файл вида
`КЛЮЧ=значение`, одна настройка на строку; строки с `#` — комментарии. Шаблон со всеми
ключами и пояснениями — `.env.example`. Значения ниже взяты из `.env.example`; если ключа в
`.env` нет, действует значение по умолчанию из `src/core/config.py`.

Сохраняйте `.env` в кодировке UTF-8. Файл содержит пароли и ключи: в Git он не попадает, не
пересылайте его.

### 7.1. Провайдер LLM

| Ключ | Пример | Что задаёт |
|---|---|---|
| `LLM_PROVIDER` | `ario` | Какая LLM отвечает: `ario`, `custom`, `ollama`, `groq`, `gemini` |
| `ARIO_BASE_URL` | `https://llm.ario.directum360.ru/v1` | Адрес Ario |
| `ARIO_MODEL` | `Qwen/Qwen3.8-27B-Ario` | Имя модели на Ario |
| `ARIO_API_KEY` | — | Токен Ario |
| `CUSTOM_LLM_BASE_URL` | `http://10.0.0.5:8000/v1` | Адрес OpenAI-совместимого сервера Заказчика (vLLM, LM Studio) |
| `CUSTOM_LLM_MODEL` | `openai/gpt-oss-20b` | Имя модели, точно как его отдаёт сервер |
| `CUSTOM_LLM_API_KEY` | пусто | Ключ. Пусто — заголовок авторизации не отправляется |
| `OLLAMA_BASE_URL` | `http://localhost:11434/v1` | Адрес Ollama |
| `OLLAMA_MODEL` | `qwen2.5-14b` | Модель Ollama |
| `GROQ_API_KEY`, `GROQ_MODEL` | `llama-3.3-70b-versatile` | Ключ и модель Groq |
| `GEMINI_API_KEY` | — | Ключ Gemini |

**Какой провайдер выбрать.** `ario` — основной: на нём сделаны замеры точности, доступен из
корпоративной сети или по VPN. `custom` — модель Заказчика в его сети; единственный вариант на
стенде без интернета. `ollama` — модель на этой же машине. `groq` и `gemini` — облачные, для
проверки без корпоративного доступа.

**Имя модели должно совпадать с тем, что отдаёт сервер.** Набор моделей на Ario меняется без
предупреждения, а vLLM обычно отдаёт имя с префиксом (`openai/gpt-oss-20b`, а не `gpt-oss-20b`).
На неизвестное имя сервер отвечает `404`, и это легко принять за неверный адрес. Список моделей:
`GET <base_url>/models` или кнопка **«Проверить связь с LLM»** в бэк-офисе на вкладке
**«Настройки»** — она показывает проверенный адрес и список моделей.

**Ollama и Docker.** Внутри контейнера `localhost` — это сам контейнер, а не ваш сервер. В режиме
docker укажите `OLLAMA_BASE_URL=http://host.docker.internal:11434/v1` (то же для vLLM на этой же
машине). Имя `host.docker.internal` прописано в `docker-compose.yml` для API и воркеров.

### 7.2. PostgreSQL: порт, адрес, пароль

| Ключ | Пример | Что задаёт |
|---|---|---|
| `POSTGRES_PORT` | пусто → 5432 | Порт PostgreSQL на этой машине. Установщик подбирает свободный сам |
| `DATABASE_URL` | пусто | Адрес базы для процессов из `venv`, вида `postgresql://classifier:classifier@localhost:5434/classifier`. На машине только с воркерами — адрес базы главного сервера |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `classifier` | Логин, пароль и имя базы в контейнере PostgreSQL |
| `POSTGRES_BIND` | `127.0.0.1` | На каком адресе машины открыт порт PostgreSQL. `0.0.0.0` — только для воркеров на других машинах ([раздел 8.6](#86-воркеры-на-других-машинах)) |

**Как выбирается и сохраняется порт.** Установщик (`scripts/setup_infra_env.py`) выбирает
свободный порт и пишет его в `.env` вместе с `DATABASE_URL` (правило — в
[разделе 3](#шаги-установщика)). Уже записанный порт при повторной установке не меняется, если
свободен. Если `DATABASE_URL` пустой, его собирают из `POSTGRES_*` и порта и `start.*`, и сам
сервис.

**Порт в адресе и `POSTGRES_PORT` должны совпадать.** Если вы вручную поменяли `POSTGRES_PORT`,
поменяйте порт и в `DATABASE_URL` (или очистите `DATABASE_URL`). Иначе `start.* all` и
`start.* api` остановятся с ошибкой `DATABASE_URL points to port …, but POSTGRES_PORT=…` — это
защита от подключения к чужой базе. В режиме `worker` эта проверка не делается: там адрес
задан явно и обычно указывает на другую машину.

**В режиме `docker`** `DATABASE_URL` из `.env` не используется: внутри контейнеров адрес
заменяется на служебное имя `postgres:5432` (см. `docker-compose.yml`).

**Пароли.** Стандартный пароль `classifier` годится только для машины, на которой база доступна
лишь локально. Задайте свой **до первого запуска**: PostgreSQL запоминает пароль при создании тома
`pgdata`, и смена `POSTGRES_PASSWORD` позже на уже существующую базу не подействует — придётся
менять пароль и в самой базе:

```bash
docker compose exec postgres psql -U classifier -d classifier -c "ALTER USER classifier PASSWORD 'новый_пароль'"
```

**Не используйте в паролях символы `@`, `/`, `:`, `#`.** Установщик и сервис экранируют их в
собираемых адресах, но внутри docker compose и в адресах, которые собирают сами `start.*`, пароль
подставляется как есть, и адрес ломается. Если `DATABASE_URL` вы пишете вручную, особые символы
пароля заменяйте кодами: `@` → `%40`, `%` → `%25`, `$` → `%24`. Сочетание `${` в
`DATABASE_URL` запрещено: при чтении `.env` оно понимается как подстановка переменной, и
`start.cmd worker` откажется работать с подсказкой `percent-encode $ as %24`.

### 7.3. Порт API

| Ключ | По умолчанию | Где действует |
|---|---|---|
| `API_PORT` | 8010 | Режимы `all` и `api` (`start.* all`, `launch.* server`). Аргумент `--port` важнее |
| `API_HOST` | `0.0.0.0` | Режимы `all` и `api`: на каком адресе слушать. `0.0.0.0` — на всех интерфейсах |
| `HOST_PORT` | 8010 | Режим `docker`: порт на машине, который ведёт на порт 8005 внутри контейнера `api` |

Порт 8010 — тот адрес, который передан разработчикам RX. Меняйте его только вместе с настройкой
на стороне RX.

### 7.4. Бэк-офис

| Ключ | Пример | Что задаёт |
|---|---|---|
| `BACKOFFICE_USER` | `admin` | Логин бэк-офиса |
| `BACKOFFICE_PASSWORD` | `CHANGE_ME` | Пароль бэк-офиса. Если ключа нет совсем, действует `password` — обязательно задайте свой |

**Важно.** В текущей версии логин и пароль запрашиваются только при активации версии модели
(кнопка **«Активировать»** в разделе **«Модели»** бэк-офиса). Сама страница
`/backoffice`, вкладка **«Настройки»** (где видны и меняются адреса и ключи LLM и RX) и
остальные адреса API паролем не защищены. Поэтому не открывайте порт API в интернет и
ограничьте доступ к нему файрволом: пускайте только сервер RX и рабочие места сотрудников.

### 7.5. Directum RX

| Ключ | Пример | Что задаёт |
|---|---|---|
| `RX_ODATA_URL` | `http://172.16.96.98/integration/odata` | Адрес сервиса интеграции RX (OData) |
| `RX_USER` | `Administrator` | Пользователь RX |
| `RX_PASSWORD` | — | Пароль. Хранится только в `.env` |

Эти три ключа нужны **только** когда RX вызывает сервис по `document_id` без текста — тогда сервис
сам забирает документ из RX. Если RX присылает текст обращения в запросе (основной способ), их
можно не заполнять. При пустом пароле вызов по `document_id` вернёт `502`. Проверить подключение —
кнопкой **«Проверить подключение к RX»** на вкладке **«Настройки»** бэк-офиса.

## 8. Дополнительные настройки

Эти ключи обычно менять не нужно. В таблицах — значение из `.env.example`, а в скобках — значение
по умолчанию из `config.py`, если ключа в `.env` нет и оно отличается.

### 8.1. Поиск и качество

| Ключ | Значение | Что делает |
|---|---|---|
| `TOP_K_CANDIDATES` | `50` (по умолчанию `10`) | Сколько кандидатов из поиска получает LLM |
| `MIN_CONFIDENCE` | `0.65` | Ниже этой уверенности результат помечается как требующий проверки оператором |
| `ENABLE_HEURISTIC_RERANKER` | `false` (по умолчанию `true`) | Эвристическая пересортировка кандидатов. Выключена: по замерам ухудшает точность |
| `ENABLE_FULL_CLASSIFIER_FALLBACK` | `false` | Повторный запрос к LLM со всем классификатором, если поиск не нашёл близких кодов. Дорогой: большой запрос к LLM |
| `FULL_FALLBACK_SIM_THRESHOLD` | `0.15` (по умолчанию `0.40`) | Порог сходства для повторного запроса. Для базы `vector_db_adapted_v3` нужен 0.15, иначе повторный запрос будет на каждом обращении |
| `ENABLE_REPEAT_DETECTION` | `false` | Распознавать повторное обращение и добавлять код `0001.0002.0027.0125` |
| `ENABLE_WITHDRAWAL_DETECTION` | `false` | Распознавать просьбу прекратить рассмотрение и добавлять код `0001.0002.0027.0131` |
| `ENABLE_EMBEDDING_ADAPTER` | `false` | Адаптер векторов запроса. Включать только вместе с пересборкой векторов под тот же адаптер |
| `ENABLE_ANNOTATION_VECTORS` | `false` | Учитывать в поиске аннотации оператора к кодам |
| `VECTOR_DB_DIR` | `data/vector_db_adapted_v3` | Файлы векторов, которые миграция переносит в базу как версию модели 0 |
| `EMBEDDING_MODEL` | `intfloat/multilingual-e5-base` | Модель эмбеддингов (имя на Hugging Face или путь к папке) |
| `LLM_TIMEOUT_SEC` | `360` | Сколько секунд ждать ответа LLM |
| `LLM_MAX_RETRIES` | `5` | Сколько раз повторять запрос к LLM при таймауте, ограничении частоты, ошибке 5xx или битом ответе |

В `config.py` есть и другие экспериментальные флаги (`ENABLE_CROSS_ENCODER_RERANKER`,
`ENABLE_SECTION_ROUTING`, `ENABLE_LTR_RERANKER` и др.). Все они по умолчанию выключены; включать
их на рабочем сервисе не нужно.

### 8.2. Очередь и воркеры

| Ключ | Значение | Что делает |
|---|---|---|
| `CLASSIFY_WORKERS` | `2` | Сколько процессов-воркеров классификации поднимают режимы `all` и `worker` (и сколько контейнеров `worker-classify` в режиме `docker`). Один процесс = одна классификация за раз. Рассчитано на несколько воркеров на всех машинах вместе (до пяти) |
| `QUEUE_POLL_SEC` | `5` | Как часто (в секундах) свободный воркер сам заглядывает в очередь. Обычно о новой задаче он узнаёт сразу — по уведомлению из базы; проверка по таймеру ловит пропущенные уведомления, отложенные повторы и задачи пропавших воркеров |
| `JOB_LEASE_SEC` | `60` | **Аренда** задачи: сколько секунд задача закреплена за взявшим её воркером. Воркер продлевает аренду каждую треть срока (20 с), пока работает. Если воркер пропал, по истечении аренды задачу берёт другой воркер. Дообучение в этом случае не перезапускается, а завершается ошибкой |
| `JOB_MAX_ATTEMPTS` | `2` | Сколько раз пробовать задачу, если воркер пропал или пропала связь с базой. После сбоя связи повтор идёт с паузой 5, 10, 20… секунд (не больше 60) |
| `JOB_DELIVERED_GRACE_SEC` | `600` | Сколько секунд хранить задачу после того, как результат забрали (синхронный ответ, опрос статуса, webhook). Запас нужен, чтобы RX мог повторить опрос после сбоя сети |
| `JOB_TTL_HOURS` | `24` | Сколько часов хранить завершённую задачу, результат которой не забрали. Задачи дообучения хранятся именно столько, даже если результат прочитан |
| `JOB_MAX_QUEUED` | `100` | Сколько задач может ждать в очереди асинхронного приёма. Сверх этого — ответ `429` |
| `SYNC_WAIT_TIMEOUT_SEC` | `1800` | Сколько секунд синхронный запрос ждёт результат. Потом ответ `504`, а задача продолжает выполняться |
| `DB_POOL_MAX` | `10` | Сколько соединений с базой держит один процесс |
| `STORAGE_BACKEND` | `postgres` | Хранилище. `memory` — только для тестов |

Чтобы ускорить обработку, добавьте воркеров: увеличьте `CLASSIFY_WORKERS` и перезапустите, или
поднимите воркеры на другой машине ([раздел 8.6](#86-воркеры-на-других-машинах)). Каждый
воркер — это ещё ~1,5 ГБ памяти.

### 8.3. Webhook

**Webhook** — обратный вызов: когда задача готова, сервис сам отправляет результат POST-запросом
на адрес, который указал вызывающий.

| Ключ | Значение | Что делает |
|---|---|---|
| `WEBHOOK_ALLOWED_HOSTS` | пусто | Хосты, на которые разрешено отправлять webhook: точные имена через запятую, без `http://` и масок. `host:port` разрешает только этот порт, имя без порта — любой. Пусто — webhook выключены. Пример: `rx.local,172.16.96.98:8443` |
| `WEBHOOK_SECRET` | пусто | Если задан, тело подписывается заголовком `X-Signature: sha256=<HMAC>` |

### 8.4. Дообучение

| Ключ | Значение | Что делает |
|---|---|---|
| `FINETUNE_THRESHOLD` | `50` | Сколько проверенных оператором карточек нужно для запуска дообучения |
| `MODELS_DIR` | папка `models` в проекте | Где лежат дообученные модели (`e5-finetuned-vN`). Дообучение сохраняет новую версию сюда, а каждый воркер ищет версию как `MODELS_DIR/<имя папки>`. Ключа нет в `.env.example` — дописывайте его, когда воркеры работают на других машинах ([раздел 8.6](#86-воркеры-на-других-машинах)) |

### 8.5. Прокси, Hugging Face, сеть Docker

| Ключ | Значение | Что делает |
|---|---|---|
| `RX_VIA_PROXY` | `auto` | Ходить ли в RX через системный прокси (`HTTP_PROXY`/`HTTPS_PROXY`). `auto` — внутренние адреса напрямую, внешние через прокси. `true` / `false` — всегда через прокси / всегда напрямую |
| `LLM_VIA_PROXY` | `auto` | То же для LLM. Webhook всегда работает по правилу `auto` |
| `HF_CACHE_DIR` | пусто | Папка кеша моделей Hugging Face на машине для режима docker. Пусто — `./.hf-cache` в папке проекта |
| `HF_ENDPOINT` | не задан | Зеркало Hugging Face, если прямой доступ закрыт. Например `https://hf-mirror.com` |
| `HF_HUB_OFFLINE` | не задан | `1` — запретить обращения к Hugging Face (стенд без интернета). Ставит офлайн-установщик |
| `POSTGRES_BIND` | `127.0.0.1` | На каком адресе машины открыт порт PostgreSQL (см. [раздел 7.2](#72-postgresql-порт-адрес-пароль)) |

«Внутренними» считаются частные IP-адреса (10.x, 172.16–31.x, 192.168.x), `localhost`, имена без
точки и имена на `.local`, `.localdomain`, `.lan`, `.internal`, `.intranet`, `.corp`, `.home`,
`.test`.

В режимах `all` и `worker` модель скачивается в обычный кеш Hugging Face пользователя
(`%USERPROFILE%\.cache\huggingface` или `~/.cache/huggingface`).

### 8.6. Воркеры на других машинах

Если одной машины не хватает, воркеры можно запустить ещё на нескольких. База данных и API
остаются на одной машине — **главном сервере**; на остальных работают только воркеры. Воркер
сам подключается к базе главного сервера, забирает из неё задачи и пишет туда результаты. API о
воркерах ничего настраивать не нужно: `/health` увидит их по подключению к базе.

**На главном сервере.**

1. Смените пароль базы: задайте свой `POSTGRES_PASSWORD` в `.env` (на уже созданной базе — ещё и
   командой `ALTER USER`, см. [раздел 7.2](#72-postgresql-порт-адрес-пароль)). Стандартный пароль
   `classifier` при открытой наружу базе недопустим: в ней персональные данные.
2. Откройте базу для сети: `POSTGRES_BIND=0.0.0.0` в `.env` (или адрес нужного сетевого
   интерфейса).
3. Разрешите в файрволе входящие подключения на порт `POSTGRES_PORT` — только с адресов машин
   воркеров.
4. Запустите сервис без воркеров — `start.cmd api` (`launch.bat` → [2]) — или со своими
   воркерами — `start.cmd all`. После смены `POSTGRES_BIND` контейнер базы должен
   пересоздаться: `stop.cmd`, затем снова `start.cmd …` (`docker compose up` пересоздаёт
   контейнер с новыми настройками).
5. Проверьте с машины воркеров, что порт доступен (например, `Test-NetConnection 192.168.10.5 -Port 5434`
   в PowerShell или `nc -zv 192.168.10.5 5434` на Linux).

**На каждой машине воркеров.**

1. Установите проект как [машину только для воркеров](#машина-только-для-воркеров): установщик
   спросит адрес базы и пароль и запишет `DATABASE_URL` в `.env` этой машины.
2. Настройте модели (см. ниже) и, при необходимости, `CLASSIFY_WORKERS` — сколько воркеров
   запускать на этой машине.
3. Запустите воркеры: `start.cmd worker` (`launch.bat` → [3]; Linux — `./start.sh worker`). С
   ключом `--training` здесь же запустится воркер дообучения — держите его только на одной
   машине.
4. Убедитесь, что главный сервер видит воркер: `http://<главный-сервер>:8010/health` показывает
   `agent_ready: true`.
5. Остановка — `stop.cmd worker` (`./stop.sh worker`): останавливаются только воркеры.

**Модели.** Исходная модель (версия 0, `intfloat/multilingual-e5-base`) каждая машина берёт сама
— из интернета или из своего кеша Hugging Face (на стенде без интернета — из офлайн-комплекта).
Дообученные версии сохраняются на той машине, где работал воркер дообучения, в папку
`MODELS_DIR/e5-finetuned-vN`. В базе хранится только имя папки, а каждый воркер ищет её в своей
`MODELS_DIR`. Чтобы воркеры других машин нашли новую версию, выберите один из способов:

- **общая сетевая папка**: `MODELS_DIR` на всех машинах указывает на одну и ту же папку
  (например, `MODELS_DIR=\\fileserver\classifier-models` или смонтированный каталог на Linux);
- **копирование**: после каждого дообучения скопируйте папку `models\e5-finetuned-vN` с машины
  дообучения в `MODELS_DIR` каждой машины воркеров (по умолчанию — папка `models` в проекте).

Если папки активной версии на машине нет, воркер не берёт задачи классификации и пишет в окно
(журнал) ошибку `нет папки модели vN в MODELS_DIR=…: ожидается … Скопируйте папку дообученной
модели на эту машину.` Скопируйте папку — воркер подхватит её сам при следующей проверке очереди.

**Настройки.** Воркер читает все настройки (адрес базы, LLM, ключи, пороги) из `.env` своей
машины. Бэк-офис меняет `.env` только на главном сервере. Поэтому после каждого изменения на
вкладке «Настройки» бэк-офиса перенесите те же значения в `.env` машин воркеров. Ключи из
бэк-офиса (LLM, RX, `SYNC_WAIT_TIMEOUT_SEC`) воркер подхватит сам перед следующей задачей,
остальные — после перезапуска воркеров (`stop.cmd worker`, `start.cmd worker`).

## 9. Как меняются настройки и когда нужен перезапуск

Есть три способа поменять настройку.

**1. Вкладка «Настройки» в бэк-офисе** (`http://localhost:8010/backoffice#settings`). Там
редактируются только такие ключи:

- группа **«Модель LLM»**: `LLM_PROVIDER`, `ARIO_MODEL`, `ARIO_BASE_URL`, `ARIO_API_KEY`,
  `CUSTOM_LLM_BASE_URL`, `CUSTOM_LLM_MODEL`, `CUSTOM_LLM_API_KEY`, `GROQ_MODEL`, `GROQ_API_KEY`,
  `GEMINI_API_KEY`, `OLLAMA_MODEL`, `OLLAMA_BASE_URL`;
- группа **«Directum RX»**: `RX_ODATA_URL`, `RX_USER`, `RX_PASSWORD`;
- группа **«Очередь»**: `SYNC_WAIT_TIMEOUT_SEC`.

Кнопка **«Сохранить»** записывает значения в `.env` (рядом остаётся копия
`.env.bak-settings-<дата-время>`) и сразу применяет их в API. Ключи и пароли на форме показаны
звёздочками; пустое поле секрета означает «не менять».

**2. Пункт `[9] Select LLM provider` в `launch.bat`** — меняет только `LLM_PROVIDER`.

**3. Правка `.env` в редакторе.**

**Когда изменения подхватываются без перезапуска.** Воркеры перед каждой задачей проверяют, не
изменился ли `.env`, и применяют у себя новые значения — **только тех ключей, что перечислены в
пункте 1**. Поэтому у API и воркеров одной машины должен быть один и тот же файл `.env`: в
режиме `docker` он подключён во все контейнеры, в режиме `all` все процессы работают из одной
папки. У машин, где работают только воркеры, `.env` свой: бэк-офис его не меняет, правки
переносите туда вручную ([раздел 8.6](#86-воркеры-на-других-машинах)).

**Когда нужен перезапуск.** Все остальные ключи (порты, пароли, флаги поиска, параметры очередей,
`BACKOFFICE_*`, `WEBHOOK_*`) читаются только при старте процесса. После их изменения:

- режим `docker` — снова `start.cmd docker` (`./start.sh docker`): `docker compose up`
  пересоздаст контейнеры с новыми значениями. Простого `docker compose restart` недостаточно —
  переменные из `.env` передаются контейнеру при его создании;
- режимы `all` и `api` — `stop.cmd`, затем `start.cmd all` (или `start.cmd api`);
- машина воркеров — `stop.cmd worker`, затем `start.cmd worker`.

## 10. Интеграция с Directum RX

RX обращается к сервису по HTTP на порт 8010. Все адреса начинаются с `/integration`. Код —
[../src/api/integration_api.py](../src/api/integration_api.py).

### Адреса

| Метод и адрес | Что делает |
|---|---|
| `POST /integration/classify-document` | Синхронный вызов: ответ приходит, когда классификация закончена |
| `POST /integration/classify-document-async` | Асинхронный вызов: сразу возвращает номер задачи, результат забирается опросом или приходит webhook-ом |
| `GET /integration/jobs/{job_id}` | Статус задачи и результат, когда он готов |
| `GET /integration/jobs?limit=20` | Сводка по очереди для диагностики, в том числе `worker_alive` |

Тело запроса для обоих вызовов:

```json
{"appeal_text": "Прошу отремонтировать дорогу во дворе дома №5", "document_id": 26}
```

- `appeal_text` — текст обращения. Основной способ.
- `document_id` — номер документа в RX. Возвращается в ответе как есть. Если текста нет, сервис
  сам забирает документ из RX по OData (нужны настройки из [раздела 7.5](#75-directum-rx)).
- `webhook_url` — только для асинхронного вызова: адрес, куда прислать результат.

### Синхронный вызов

```bash
curl -X POST http://localhost:8010/integration/classify-document \
  -H "Content-Type: application/json" \
  -d '{"appeal_text": "Прошу отремонтировать дорогу во дворе дома №5", "document_id": 26}'
```

Ответ содержит `document_id`, `applicant_fio`, `applicant_email`, `summary`, `reasoning` и список
`questions` с полями `code` и `question`. Описание полей — в [User_manual.md](User_manual.md).

Классификация длится от десятков секунд до нескольких минут, и всё это время соединение открыто.
Если результата нет за `SYNC_WAIT_TIMEOUT_SEC` (1800 секунд), приходит `504` с номером задачи
в тексте ошибки. Задача при этом **продолжает выполняться**, её результат можно забрать через
`GET /integration/jobs/{job_id}`.

### Асинхронный вызов

```bash
curl -X POST http://localhost:8010/integration/classify-document-async \
  -H "Content-Type: application/json" \
  -d '{"appeal_text": "Прошу отремонтировать дорогу во дворе дома №5", "document_id": 26}'
```

Ответ приходит сразу с кодом `202`:

```json
{"job_id": "47ecfc0e2ca64d31b94bce1828cb1422", "status": "queued",
 "queue_position": 2, "poll_url": "/integration/jobs/47ecfc0e2ca64d31b94bce1828cb1422"}
```

Затем RX опрашивает `GET /integration/jobs/<job_id>`, разумный интервал — 5 секунд. Поле `status`
принимает значения `queued` (ждёт), `running` (обрабатывается), `done` (готово, результат в
`result`) и `error` (текст ошибки в `error`). Когда опрос отдал конечный статус (`done` или
`error`), задача хранится ещё `JOB_DELIVERED_GRACE_SEC` (600 секунд) — повторный опрос в это время
вернёт тот же ответ, — а затем удаляется, и опрос вернёт `404`. Незабранный результат хранится
`JOB_TTL_HOURS` (24 часа).

**Webhook.** Если в асинхронном запросе передан `webhook_url`, после завершения задачи (`done` или
`error`) воркер отправит на этот адрес POST с тем же телом, что отдаёт опрос статуса. Делается до
трёх попыток, перенаправления (3xx) не выполняются. Хост адреса должен быть в
`WEBHOOK_ALLOWED_HOSTS`, иначе запрос сразу отклоняется с кодом `400`. При заданном
`WEBHOOK_SECRET` в заголовке `X-Signature` приходит подпись тела `sha256=<HMAC>`, по которой RX
может проверить отправителя.

### Коды ответов

| Код | Когда | Что делать |
|---|---|---|
| `200` | Синхронный вызов выполнен | — |
| `202` | Асинхронный вызов принят | Опрашивать `poll_url` |
| `400` | Пустой текст; нет ни текста, ни `document_id`; документ без текста (скан, битый файл); `webhook_url` не разрешён | Исправить запрос. Повтор не поможет |
| `404` | Документ не найден в RX; задача не найдена или срок её хранения истёк | Проверить номер |
| `429` | Очередь асинхронного приёма заполнена (`JOB_MAX_QUEUED`) | Повторить позже |
| `500` | Ошибка классификации, в том числе недоступна LLM | Повторить; при повторении — смотреть журналы воркера |
| `502` | Не удалось получить документ из RX | Проверить адрес OData, пароль, сеть |
| `503` | Недоступна база данных | Проверить `/health`, см. [раздел 12](#12-неполадки-и-что-с-ними-делать) |
| `504` | Синхронный вызов не дождался результата | Забрать результат по `job_id` из текста ошибки |

Перед отправкой документов RX стоит проверять `GET /health`: `agent_ready: true` значит, что
воркеры готовы. Если воркеров нет, запросы всё равно принимаются: асинхронные задачи ждут в
очереди, а синхронный вызов по истечении `SYNC_WAIT_TIMEOUT_SEC` ответит `504`.

## 11. Эксплуатация

### Данные и тома Docker

Все данные — тексты обращений, результаты, проверки оператора, задачи, версии модели — хранятся
в PostgreSQL, в томе Docker `pgdata` (полное имя видно в `docker volume ls`, обычно
`<папка-проекта>_pgdata`). **Тексты обращений — персональные данные по 59-ФЗ.**

- `stop.cmd` / `./stop.sh` выполняют `docker compose stop`, а `stop.cmd docker` /
  `./stop.sh docker` — `docker compose down` **без** ключа `-v`. В обоих случаях том остаётся.
- **Никогда не выполняйте `docker compose down -v`** и `docker volume rm` для этого тома без
  резервной копии: это удалит все данные безвозвратно.
- Очередь задач — таблица `jobs` в той же базе, поэтому задачи, которые ждали в очереди в
  момент остановки, переживают и остановку, и пересоздание контейнеров.

### Резервное копирование PostgreSQL

Копия делается внутри контейнера и затем копируется на машину:

```bash
docker compose exec postgres pg_dump -U classifier -d classifier -Fc -f /tmp/classifier.dump
docker compose cp postgres:/tmp/classifier.dump ./classifier-2026-11-16.dump
docker compose exec postgres rm /tmp/classifier.dump
```

Если вы меняли `POSTGRES_USER` или `POSTGRES_DB`, подставьте свои значения. Храните копии в
защищённом месте: в них персональные данные. Восстановление в пустую базу:

```bash
docker compose cp ./classifier-2026-11-16.dump postgres:/tmp/classifier.dump
docker compose exec postgres pg_restore -U classifier -d classifier --clean --if-exists /tmp/classifier.dump
```

Перед восстановлением остановите API и воркеры.

### Журналы

| Режим | Где смотреть |
|---|---|
| `docker` | `docker compose logs -f api`, `docker compose logs -f worker-classify`, `docker compose logs migrate`, `docker compose logs postgres` |
| `all`, `api`, `worker` на Windows | Окна `classifier-api`, `classifier-worker-N`, `classifier-worker-training` |
| `all`, `api`, `worker` на Linux | Файлы `run/api.log`, `run/worker-classify-N.log`, `run/worker-training.log` |

Папка `run/` в Git не попадает: в журналах могут быть фрагменты обращений.

### Как посмотреть очередь

Быстрая сводка по задачам классификации — `GET http://localhost:8010/integration/jobs`: сколько
задач в каждом статусе (`queued`, `running`, `done`, `error`), есть ли живой воркер
(`worker_alive`) и последние задачи.

Подробнее — запросами к базе (подключение — в [DB_scheme.md](DB_scheme.md)):

```bash
docker compose exec postgres psql -U classifier -d classifier
```

Готовые запросы «Сколько задач ждёт в каждой очереди», «Какие воркеры сейчас подключены» и «Задачи
с истёкшей арендой» — в разделе 5 [DB_scheme.md](DB_scheme.md#5-полезные-запросы-только-для-чтения).

### Зависшие задачи

Обычно вмешиваться не нужно:

- задачу пропавшего воркера (процесс убит, машина выключена) через `JOB_LEASE_SEC` (60 с) берёт
  другой воркер. Если попыток уже `JOB_MAX_ATTEMPTS` (2), задача завершается ошибкой;
- дообучение пропавшего воркера завершается ошибкой «воркер дообучения пропал, запустите
  дообучение заново» — запустите его снова;
- после сбоя связи с базой задача сама возвращается в очередь и повторяется с паузой;
- завершённые задачи удаляются сами ([DB_scheme.md](DB_scheme.md#38-jobs--задачи-и-очередь)).

Задачи в статусе `queued` ждут, пока не появится воркер нужной очереди: `classify_sync` и
`classify` — воркер классификации, `training` — воркер дообучения (`--training`). Если такие
задачи больше не нужны (например, воркеров долго не было и RX уже отправил документы заново),
их можно закрыть вручную:

```sql
SELECT id, job_type, queue, created_at FROM jobs
 WHERE status = 'queued' AND created_at < now() - interval '1 hour';

UPDATE jobs SET status='error', error='отменена администратором', finished_at=now()
 WHERE status = 'queued' AND created_at < now() - interval '1 hour';
```

RX по такой задаче получит `status: error` и сможет отправить документ повторно. Интервал
`1 hour` подберите сами.

### Воркер дообучения и версии модели

**Дообучение** — дополнительная тренировка модели эмбеддингов на обращениях, проверенных
оператором. Им занимается отдельный воркер, который запускается только по ключу `--training`:
`start.cmd all --training`, `start.cmd docker --training` или `start.cmd worker --training` на
машине воркеров. Держите его только на одной машине. Без него задачи дообучения будут ждать в
очереди `training`.

Запустить дообучение можно из интерфейса (см. [User_manual.md](User_manual.md)) или командой:

```bash
venv\Scripts\python.exe src\training\auto_finetune.py            # проверит порог FINETUNE_THRESHOLD
venv\Scripts\python.exe src\training\auto_finetune.py --force    # без проверки порога
```

Одновременно может идти только одно дообучение (повторный запуск получит ответ `409`).

Каждое дообучение создаёт новую версию модели со своими векторами. Активна всегда одна версия:

- если дообучали от исходной версии 0, новая версия **никогда не включается сама** — проверьте
  качество и активируйте её вручную;
- если от дообученной версии (1 и выше) — новая включается сама, только если улучшился
  показатель recall@5.

Активация и откат — в бэк-офисе, раздел **«Модели»**, кнопка **«Активировать»** (браузер спросит
логин и пароль бэк-офиса). Воркеры переключаются на новую версию перед следующей задачей, без
перезапуска. Воркерам на других машинах нужна папка новой версии в их `MODELS_DIR`
([раздел 8.6](#86-воркеры-на-других-машинах)).

### Обновление приложения

1. Предупредите пользователей и дождитесь, пока очередь опустеет (`GET /integration/jobs`:
   `queued` и `running` равны 0).
2. Сделайте резервную копию базы (см. выше).
3. Получите новый код: `git pull`.
4. Режим `docker`: `start.cmd docker` (`./start.sh docker`). Образ пересоберётся (`--build`),
   сервис `migrate` догонит схему базы, затем стартуют API и воркеры.
5. Режимы `all` и `api`: `stop.cmd`; если менялся `requirements.txt` —
   `venv\Scripts\python.exe -m pip install -r requirements.txt`; затем `start.cmd all` (или `api`).
6. Машины воркеров: `stop.cmd worker`, `git pull`, при необходимости `pip install`, затем
   `start.cmd worker`.
7. Проверьте `http://localhost:8010/health`.

Схема базы применяется при каждом запуске, повторно — без вреда. Перенос данных из файлов
выполняется один раз: после успешного переноса в таблицу `schema_meta` пишется отметка
`files_migrated`, и следующие запуски печатают «Данные из файлов уже перенесены …» и ничего не
трогают. Повторить перенос вручную (уже перенесённое пропускается):

```bash
venv\Scripts\python.exe scripts\db\migrate_from_files.py --force
```

### Обновление стенда, где работала версия с RabbitMQ

Раньше очередь задач держал отдельный контейнер RabbitMQ, а воркеры запускались через Celery.
Новая версия его не использует. Порядок обновления такой стенда:

1. **До `git pull`** остановите старую версию её же скриптом: `stop.cmd local` (или `stop.cmd`
   для режима docker; Linux — `./stop.sh local` / `./stop.sh`). Можно и просто закрыть окна
   `classifier-*`. Новый `stop.cmd` старые процессы Celery не узнаёт и не остановит.
2. Сделайте резервную копию базы и выполните `git pull`.
3. Удалите контейнер RabbitMQ: `docker rm -f <проект>-rabbitmq-1`, где `<проект>` — имя
   папки проекта строчными буквами (например, `class-og-final-rabbitmq-1`; точное имя покажет
   `docker ps -a`).
4. Удалите из `.env` строки `RABBITMQ_URL`, `RABBITMQ_PORT`, `RABBITMQ_MGMT_PORT`,
   `RABBITMQ_BIND`, `RABBITMQ_DEFAULT_USER`, `RABBITMQ_DEFAULT_PASS`. Строки
   `BROKER_HEARTBEAT_SEC`, `WORKER_PROC_ALIVE_TIMEOUT_SEC`, `CLASSIFY_CONCURRENCY` больше не
   читаются — их тоже можно удалить. При желании добавьте новые ключи `QUEUE_POLL_SEC`,
   `JOB_LEASE_SEC`, `JOB_DELIVERED_GRACE_SEC` ([раздел 8.2](#82-очередь-и-воркеры)); без них
   действуют значения по умолчанию.
5. Обновите библиотеки: `venv\Scripts\python.exe -m pip install -r requirements.txt`.
6. Запустите сервис: `start.cmd` (теперь без аргумента это режим `all`, а не `docker`; для
   режима docker — `start.cmd docker`). Схема базы обновится сама: в таблицу `jobs` добавятся
   поля очереди, данные не теряются.

## 12. Неполадки и что с ними делать

### Движок Docker не отвечает

Сообщение `ERROR: the Docker engine does not respond` (Linux: «движок Docker не отвечает»).
Docker установлен, но движок остановлен или завис.

1. Запустите Docker Desktop. Если он уже запущен — меню **Troubleshoot → Restart**.
2. Дождитесь надписи **Engine running**. Проверка: `docker info` выполняется без ошибки.
3. На Linux: `sudo systemctl start docker`; если ошибка про права на `docker.sock` — добавьте
   пользователя в группу `docker`.
4. Повторите команду запуска.

### Порт занят

- `ERROR: port 8010 is already in use` при `start.cmd all`. Обычно уже работает режим `docker`
  или прежний запуск. Выполните `stop.cmd docker` или `stop.cmd`, либо запустите на другом
  порту: `start.cmd all --port 9100`.
- `ERROR: POSTGRES_PORT in .env: port … is busy` от установщика. Порт, вписанный вручную, занят
  чужой программой. Очистите значение (`POSTGRES_PORT=`) и запустите
  `venv\Scripts\python.exe scripts\setup_infra_env.py` — он подберёт свободный.
- `docker compose up` пишет `port is already allocated`. Порт из `.env` заняли после установки.
  Выполните `setup_infra_env.py` ещё раз и снова запустите сервис.
- `DATABASE_URL points to port …, but POSTGRES_PORT=…`. Порты в адресе и в отдельном ключе
  разошлись. Исправьте одно из значений в `.env` или очистите `DATABASE_URL`.

### В `/health` `db: false`

API не может подключиться к PostgreSQL.

1. `docker compose ps` — контейнер `postgres` должен быть `running (healthy)`. Если нет:
   `docker compose logs postgres`.
2. Режимы `all` и `api`: проверьте, что порт в `DATABASE_URL` совпадает с `POSTGRES_PORT`, а
   пароль — с `POSTGRES_PASSWORD`. Ошибка `password authentication failed` после смены пароля в
   `.env` значит, что том помнит старый пароль (см. [раздел 7.2](#72-postgresql-порт-адрес-пароль)).
3. Режим docker: если упал `migrate`, API не стартует — `docker compose logs migrate`. Код выхода
   1 у миграции значит, что сверка «файл → база» не сошлась: таблица сверки — в этом журнале.

### `agent_ready: false`

Ни один воркер классификации не подключён к базе. Задачи при этом не теряются — они ждут в
очереди.

- Режим `docker`: `docker compose ps worker-classify` и `docker compose logs worker-classify`.
- Режим `all` на Windows: посмотрите окна `classifier-worker-N`. На Linux — `run/worker-classify-N.log`.
- Режим `api`: так и должно быть, пока не запущены воркеры на других машинах (`start.cmd worker`
  там).
- Воркеры на других машинах: в их окнах или журналах ищите ошибки подключения к базе
  (`ERROR: PostgreSQL …` при запуске, `LISTEN job_queued: нет соединения с БД`) и ошибку
  `нет папки модели vN в MODELS_DIR` ([раздел 8.6](#86-воркеры-на-других-машинах)).
- Сразу после запуска это нормально: воркер загружает модель, подождите минуту.

### `start.cmd worker` пишет `ERROR: PostgreSQL …` или `ERROR: DATABASE_URL …`

Проверка базы перед запуском воркеров не прошла. В сообщении — адрес и порт базы и причина:

| Сообщение | Что делать |
|---|---|
| `DATABASE_URL is not set` | Адреса нет в `.env` этой машины. Запустите `venv\Scripts\python.exe scripts\check_db.py ask` — он спросит адрес и пароль и запишет `DATABASE_URL` |
| `DATABASE_URL must not contain ${...}` | В адресе есть `${` — замените `$` на `%24` |
| `DATABASE_URL is malformed` | Особые символы пароля не закодированы. Проще всего ввести адрес заново через `check_db.py ask` |
| `ERROR: PostgreSQL <адрес>: <причина>` | База не отвечает или не принимает пароль. На главном сервере проверьте `POSTGRES_BIND=0.0.0.0`, открытый порт и пароль ([раздел 8.6](#86-воркеры-на-других-машинах)) |

### Синхронный вызов отвечает `504`

Классификация не уложилась в `SYNC_WAIT_TIMEOUT_SEC`. Задача не потеряна — заберите результат по
`job_id` из текста ошибки: `GET /integration/jobs/<job_id>`. Если `504` повторяется:

1. Проверьте `agent_ready` в `/health` — возможно, воркеры не работают и задачи копятся.
2. Проверьте очередь: `GET /integration/jobs` или запросы из [DB_scheme.md](DB_scheme.md#5-полезные-запросы-только-для-чтения).
3. Проверьте связь с LLM кнопкой **«Проверить связь с LLM»** в бэк-офисе. Медленная LLM — частая
   причина.
4. При большой нагрузке добавьте воркеров (`CLASSIFY_WORKERS` или машины воркеров) или
   переведите RX на асинхронный вызов.

### Ответы `503`

База данных недоступна. Проверьте `/health` и действуйте по пунктам выше.

### Ответы `500` с текстом про LLM

LLM недоступна или отвечает ошибкой. Проверьте адрес, имя модели и ключ кнопкой
**«Проверить связь с LLM»**. На стенде без интернета `ario`, `groq` и `gemini` не работают —
переключитесь на `custom` или `ollama`. Если нужен прокси, проверьте `LLM_VIA_PROXY`.

### Воркеры постоянно перезапускаются

Контейнеры в `docker-compose.yml` перезапускаются автоматически (`restart: unless-stopped`),
поэтому падение выглядит как бесконечный перезапуск.

1. Посмотрите причину: `docker compose logs --tail 100 worker-classify`.
2. `Killed` или нехватка памяти — уменьшите число воркеров (`CLASSIFY_WORKERS`) либо добавьте
   памяти. В Docker Desktop на Windows память ограничена настройками WSL2.
3. Ошибки загрузки модели (`Couldn't reach huggingface.co`, `FileMetadataError`) — нет доступа к
   Hugging Face. Откройте доступ, задайте `HF_ENDPOINT` с зеркалом или подготовьте модель офлайн
   ([раздел 5](#5-установка-без-интернета)).
4. Ошибки подключения к базе — см. пункт про `db: false`.

### Изменение в `.env` не подействовало

Без перезапуска подхватываются только ключи, которые есть на вкладке **«Настройки»** бэк-офиса
(см. [раздел 9](#9-как-меняются-настройки-и-когда-нужен-перезапуск)). Для остальных перезапустите
сервис: режим `docker` — `start.cmd docker`, режим `all` — `stop.cmd` и `start.cmd all`, машина
воркеров — `stop.cmd worker` и `start.cmd worker`. Также
проверьте, что файл называется именно `.env` (а не `.env.txt`) и сохранён в UTF-8.
