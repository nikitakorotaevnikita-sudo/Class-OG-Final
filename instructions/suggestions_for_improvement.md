# Предложения по улучшению

Здесь собраны недостатки, которые нашлись при подготовке документации (ноябрь 2026). Пока их
решили не исправлять: сервис работает, но в этих местах он ведёт себя не так, как можно ожидать.
Для каждого пункта описано, в чём проблема, чем она грозит и как её можно исправить.

## 1. Бэк-офис и настройки открыты без пароля

**Что сейчас.** В `.env` задаются логин и пароль бэк-офиса (`BACKOFFICE_USER`,
`BACKOFFICE_PASSWORD`), но проверяются они только в одном месте — при активации версии модели
(`POST /api/models/{version}/activate`). Без пароля открываются:

| Адрес | Что там |
|---|---|
| `/backoffice` | страница бэк-офиса |
| `GET /api/settings` | все настройки из `.env`, включая ключи доступа к LLM и пароль RX |
| `POST /api/settings` | изменение этих настроек — записывается прямо в `.env` |
| `POST /api/settings/test-rx`, `POST /api/settings/test-llm` | проверка связи с RX и LLM |
| `GET /api/backoffice/stats` | статистика, в том числе IP-адреса клиентов |
| `POST /api/finetune`, `/api/upload-historical`, `/api/confirm-historical` | запуск дообучения и загрузка данных |

API по умолчанию слушает все сетевые интерфейсы (`API_HOST=0.0.0.0`, порт 8010). Значит,
любой, кто может открыть адрес сервиса в своей сети, может прочитать ключи, сменить адрес LLM
или RX и запустить дообучение.

**Чем грозит.** Утечка ключей и пароля RX; подмена адреса LLM, после которой тексты обращений
(персональные данные) уйдут на чужой сервер; порча модели загрузкой «плохих» данных.

**Как исправить.**
1. Закрыть паролем (тот же HTTP Basic, функция `get_current_user` в
   [api_server.py](../src/api/api_server.py)) все адреса из таблицы, а страницы `/backoffice` и
   `/static/historical.html` отдавать только после входа.
2. В ответе `GET /api/settings` не показывать секреты целиком (например, `gsk_****1234`), а
   пустое значение секрета в `POST` понимать как «не менять».
3. Адреса для RX (`/integration/...`, `/classify`) оставить без пароля бэк-офиса — у RX своя
   схема доступа; при необходимости закрыть их отдельным ключом.
4. До исправления — ограничить доступ к порту 8010 файрволом: только сервер RX и рабочие места
   операторов.

## 2. Дообучение: порог не проверяется, а задача может навсегда застрять в очереди

### 2.1. Порог в 50 записей обходится

**Что сейчас.** По правилам проекта дообучение запускается, когда накопилось
`FINETUNE_THRESHOLD` (по умолчанию 50) проверенных записей, а без порога — только с явным
`force`. На деле `POST /api/finetune` сам включает `force` для источников `historical` и
`combined` ([api_server.py](../src/api/api_server.py), функция `start_finetune`), а кнопка
«Запустить дообучение» на странице исторических данных всегда отправляет `source=combined` и
`force=true`. Порог проверяет только консольная команда `src/training/auto_finetune.py`.

**Чем грозит.** Дообучение можно запустить на нескольких записях. Новая версия модели, обученная
на малом объёме, бесполезна, а время обучения (десятки минут) тратится впустую.

**Как исправить.** Решить, нужен ли порог для исторических данных. Если нужен — убрать
принудительный `force` в `start_finetune` и отправлять `force: true` с кнопки только после
подтверждения оператора («данных меньше порога, всё равно запустить?»). Если не нужен —
поправить описание правила в CLAUDE.md, чтобы документация не обещала проверку.

### 2.2. Без воркера дообучения задача висит в очереди и блокирует новые запуски

**Что сейчас.** Задача дообучения уходит в очередь `training`. Её выполняет отдельный воркер,
который запускается только с ключом `--training` (`start.cmd all --training`,
`./start.sh all --training`, `start.cmd worker --training` на машине воркеров или профиль
`training` в docker compose). Обычный запуск —
`launch.bat` → пункт [1] — этот воркер не поднимает. Задача остаётся в статусе `queued`, а
правило «не больше одного активного дообучения» (индекс `one_active_finetune` в базе) после этого
отклоняет каждый новый запуск ответом `409 «Дообучение уже выполняется»`.

**Чем грозит.** Оператор нажимает кнопку, видит «поставлено в очередь» — и ничего не происходит.
Повторные нажатия получают 409, хотя никакого обучения не идёт.

**Как исправить.** Варианты, от простого к полному:
1. Перед постановкой задачи проверять, что в очереди `training` есть живой воркер (его
   соединение с базой видно в `pg_stat_activity` с именем `classifier-worker:training` — так же
   `/health` ищет воркеры классификации, метод `live_workers` в
   [pg.py](../src/storage/pg.py)), и если нет — сразу отвечать понятной ошибкой «воркер
   дообучения не запущен: start.cmd all --training».
2. Добавить в меню `launch.bat` / `launch.sh` пункт «Запустить сервис с воркером дообучения».
3. Помечать ошибкой задачу дообучения, которая провела в `queued` дольше заданного времени,
   чтобы она не блокировала новые запуски.
