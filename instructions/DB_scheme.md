## 1. Как подключиться

Система использует PostgreSQL 16 с расширением pgvector (оно хранит «векторы» — списки из 768 чисел, по которым ищется смысловая близость текстов). Сама база работает в Docker-контейнере `postgres`.

Параметры подключения (значения по умолчанию из `.env.example`):

| Параметр | Значение |
|---|---|
| Хост | `localhost` |
| Порт | значение `POSTGRES_PORT` из вашего `.env` |
| База данных | `classifier` (`POSTGRES_DB`) |
| Пользователь | `classifier` (`POSTGRES_USER`) |
| Пароль | `POSTGRES_PASSWORD` из вашего `.env` |

Порт зависит от того, как вы запускали систему. В `.env.example` поле `POSTGRES_PORT` пустое: установщик (`install.bat` / `install.sh`) сам выбирает первый свободный порт из ряда 5434, 5435 и так далее и записывает его в `.env`. Если поле осталось пустым, docker-compose использует 5432. Самый надёжный способ узнать порт — открыть свой `.env` и найти строку `POSTGRES_PORT=`, либо выполнить `docker compose ps` и посмотреть порты у сервиса `postgres`.

По умолчанию порт открыт только на вашем компьютере (`POSTGRES_BIND=127.0.0.1`), с другой машины подключиться нельзя. Если воркеры работают на других машинах, база должна быть открыта для них (`POSTGRES_BIND=0.0.0.0` и сменённый пароль) — как это сделать, описано в [`Setup_instruction.md`](Setup_instruction.md).

### Подключение в pgAdmin

1. Правой кнопкой по **Servers** → **Register** → **Server**.
2. На вкладке **General** задайте любое имя, например `classifier`.
3. На вкладке **Connection** введите хост `localhost`, свой порт, Maintenance database `classifier`, пользователя и пароль из `.env`.
4. Нажмите **Save**. Сервер должен появиться в дереве слева без красного крестика. Если крестик есть, проверьте порт и запущен ли контейнер (`docker compose ps`).
5. Таблицы лежат по пути **Servers → classifier → Databases → classifier → Schemas → public → Tables**.

Подключиться можно и из командной строки:

```
docker compose exec postgres psql -U classifier -d classifier
```

### Расширения

| Расширение | Зачем нужно |
|---|---|
| `vector` (pgvector) | Тип колонки `vector(768)` и поиск по близости векторов. Без него смысловой поиск не работает. |
| `pgcrypto` | Функция `gen_random_uuid()`, которая выдаёт идентификаторы обращений. |

Оба создаются автоматически при первом запуске (`deploy/db/init/001_extensions.sql` и начало `schema.sql`). Проверить: в pgAdmin раздел **Extensions** у базы `classifier` или запрос `SELECT extname, extversion FROM pg_extension;`.

## 2. Как связаны таблицы и кто в них пишет

### Связи между таблицами

Стрелка `A ──► B` читается так: «таблица A ссылается на таблицу B» (внешний ключ).

```
classifier_entries ◄── parent_code (сама на себя: дерево классификатора)
        ▲
        │ code
classifier_vectors ──► ml_model_registry      (model_version → version)

appeal_classifications  (карточка обращения)
        ▲   ▲   ▲
        │   │   └── jobs.appeal_id                  (при удалении карточки становится NULL)
        │   └────── appeal_verifications.appeal_id  (при удалении карточки удаляется)
        └────────── appeal_questions.appeal_id      (при удалении карточки удаляется)

llm_request_log.appeal_id   — просто UUID, внешнего ключа нет
historical_appeals          — ни на что не ссылается
schema_meta                 — служебная, ни на что не ссылается
```

Колонки `appeal_questions.selected_code`, `historical_appeals.assigned_code` и `appeal_verifications.operator_codes` содержат коды классификатора, но база этого не проверяет: внешних ключей на `classifier_entries` у них нет.

### Кто пишет и кто читает

| Таблица | Кто пишет | Кто читает |
|---|---|---|
| `classifier_entries` | Скрипт переноса `scripts/db/migrate_from_files.py` (при установке) | Воркер классификации, API |
| `classifier_vectors` | Перенос (версия 0), обучение (новая версия), задача `embed_annotation` | Воркер классификации (поиск кандидатов) |
| `ml_model_registry` | Перенос (версия 0), воркер обучения; активация версии через API | Воркеры, API |
| `appeal_classifications` | API создаёт карточку, воркер классификации заполняет результат | API (интерфейс оператора, статистика, ответы для Directum RX) |
| `appeal_questions` | Воркер классификации | API, обучение |
| `appeal_verifications` | API создаёт строку `pending`, оператор меняет статус | API, обучение |
| `historical_appeals` | Загрузка исторических данных (`src/training/historical_loader.py`), перенос | Обучение, API (счётчик) |
| `jobs` | API создаёт (это и есть постановка в очередь), воркеры забирают задачу, продлевают аренду и пишут результат; API и воркеры удаляют завершённые | API (статус, ожидание результата), воркеры (выбор следующей задачи) |
| `llm_request_log` | Воркер классификации (каждая попытка запроса к языковой модели) | Администратор, статистика |
| `schema_meta` | Скрипт переноса | Скрипт переноса |

## 3. Описание таблиц

«Пусто?» в таблицах колонок означает, может ли значение быть `NULL` (не заполнено). Все даты — `timestamptz`, то есть с часовым поясом; pgAdmin показывает их в вашем поясе. Примеры значений придуманные.

### 3.1. `classifier_entries` — справочник вопросов

**Для чего.** Сам классификатор: Общероссийский классификатор вопросов обращений граждан (2108 записей, четыре уровня вложенности). Одна строка — один пункт справочника. Агент выбирает для вопроса обращения пункты четвёртого уровня.

**Жизненный цикл.** Строки появляются при первоначальном переносе (`migrate_from_files.py`) из файла `data/classifier_flat.json`. При повторной загрузке строки обновляются по коду, а не дублируются. Удалять строки в обычной работе не нужно: на них ссылаются векторы.

| Колонка | Тип | Пусто? | Что значит | Пример |
|---|---|---|---|---|
| `code` | text | нет | Код пункта, первичный ключ. Формат `XXXX.XXXX.XXXX.XXXX`. | `0003.0001.0002.0004` |
| `name` | text | нет | Название пункта. | `Ремонт и содержание дорог` |
| `level` | smallint | нет | Уровень вложенности, от 1 до 5 (`CHECK`). | `4` |
| `parent_code` | text | да | Код родительского пункта. У корней первого уровня пусто (в файле там `0000.0000.0000.0000`, в базе хранится `NULL`). Ссылается на эту же таблицу. | `0003.0001.0002.0000` |
| `full_path` | text | нет | Полный путь от корня текстом. | `Раздел / Подраздел / Ремонт и содержание дорог` |
| `children_count` | int | нет | Сколько у пункта прямых потомков. По умолчанию 0. | `0` |
| `sort_order` | int | да | Порядок пункта, как в `classifier_flat.json`. Нужен, чтобы выводить справочник в привычной последовательности. | `1287` |
| `created_at` | timestamptz | нет | Когда строка создана. | `2026-11-11 10:00:00+03` |

**Важное.** Ссылка `parent_code` объявлена `DEFERRABLE INITIALLY DEFERRED`: база проверяет её не после каждой строки, а в конце транзакции. Благодаря этому справочник можно загружать пачкой в любом порядке: потомок может встретиться раньше родителя.

### 3.2. `ml_model_registry` — реестр версий модели

**Для чего.** Агент ищет кандидатов с помощью модели-эмбеддера (программа, превращающая текст в вектор из 768 чисел). Эту модель можно дообучать на проверенных операторами обращениях. Каждая версия модели — одна строка. Версия 0 — исходная модель, перенесённая при установке. Следующие номера создаёт дообучение.

**Жизненный цикл.** Версия 0 появляется при переносе. Новая строка появляется, когда воркер обучения закончил дообучение и посчитал векторы. Если дообучали от версии 0, новая версия автоматически не включается никогда — её активируют вручную. В остальных случаях она становится активной, только если качество `recall@5` улучшилось (так называют долю случаев, когда правильный код попал в пять лучших кандидатов). Активировать любую версию вручную можно через API; при этом отправляется уведомление `model_changed` (см. раздел 4). Строки не удаляются.

| Колонка | Тип | Пусто? | Что значит | Пример |
|---|---|---|---|---|
| `version` | int | нет | Номер версии, первичный ключ. Следующий номер = максимальный + 1. | `1` |
| `base_model_name` | text | нет | Из какой модели получена версия. Для версии 0 — имя исходной модели, для обученных — путь к модели, с которой начато дообучение. | `intfloat/multilingual-e5-base` |
| `model_path` | text | нет | Где лежат файлы модели. Для дообученных версий — **имя папки** внутри `MODELS_DIR` (у каждой машины с воркерами своя `MODELS_DIR`, поэтому полный путь не хранится). Старые записи с полным путём тоже понимаются: берётся последняя часть пути. Для версии 0 — имя модели Hugging Face или путь, как при переносе. | `e5-finetuned-v1` |
| `recall5_before` | real | да | Качество до дообучения (0..1). | `0.812` |
| `recall5_after` | real | да | Качество после дообучения. | `0.845` |
| `is_active` | boolean | нет | Рабочая ли это версия. По умолчанию `false`. Активной может быть только одна. | `true` |
| `training_samples_count` | int | да | Сколько обучающих примеров использовано. | `240` |
| `trained_at` | timestamptz | да | Когда закончено обучение. | `2026-11-12 18:30:00+03` |
| `report` | jsonb | да | Отчёт об обучении: `train_size`, `val_size`, `source`, `improved`, `recall5_before`, `recall5_after`, число пар из истории и из проверок оператора и др. | `{"improved": true, "train_size": 200}` |
| `adapter` | jsonb | да | Параметры адаптера (надстройки над моделью). Дообучение пишет сюда `NULL`; значение может быть только у версии 0 из переноса. | `NULL` |

**Индекс `one_active_model`.** Уникальный индекс по `is_active` только для строк, где он `true`. Простыми словами: база физически не даст сделать активными две версии одновременно. Перед активацией новой старая снимается.

### 3.3. `classifier_vectors` — векторы для поиска

**Для чего.** «Поисковый индекс» системы. Для каждого пункта классификатора хранится один или несколько текстов и их векторы. Когда приходит обращение, система превращает его в вектор и ищет ближайшие по смыслу строки этой таблицы (по косинусной близости). Для каждой версии модели набор векторов свой.

**Жизненный цикл.** Версия 0: векторы импортируются из готовых файлов (`data/vector_db_adapted_v3`) один раз при переносе и заново не считаются. Для каждой новой версии модели обучение создаёт полный набор базовых векторов. Строки типа `annotation` («аннотации») добавляются, когда оператор исправил код и оставил пояснение: сначала строка появляется с пустым вектором, затем фоновая задача `embed_annotation` считает вектор и заполняет `embedding`. Аннотации можно удалять.

| Колонка | Тип | Пусто? | Что значит | Пример |
|---|---|---|---|---|
| `id` | bigserial | нет | Номер строки, растёт сам. | `15042` |
| `code` | text | нет | Код пункта классификатора (ссылка на `classifier_entries`). | `0003.0001.0002.0004` |
| `source_type` | text | нет | Откуда текст. Допустимо: `base` (основной текст пункта: название и путь), `annotation` (пояснение оператора). | `base` |
| `search_text` | text | нет | Текст, из которого посчитан вектор. | `Ремонт и содержание дорог. Раздел / Подраздел` |
| `embedding` | vector(768) | да | Сам вектор из 768 чисел. Пусто, пока не посчитан; такие строки в поиске не участвуют. | (длинный список чисел) |
| `model_version` | int | нет | Для какой версии модели посчитан вектор (ссылка на `ml_model_registry`). | `0` |
| `created_at` | timestamptz | нет | Когда строка создана. | `2026-11-11 10:05:00+03` |

**Индексы.**

- `cv_hnsw` — индекс типа HNSW по колонке `embedding`. Простыми словами: «оглавление», которое позволяет находить ближайшие векторы быстро, не сравнивая запрос со всеми строками. Он приблизительный, поэтому поиск настроен с запасом (`hnsw.ef_search = 400`).
- `cv_code` — быстрый поиск по паре «код + версия модели».

### 3.4. `appeal_classifications` — карточка обращения

**Для чего.** Главная таблица результатов. Одна строка — одно обращение и итог его классификации в целом. Вопросы внутри обращения лежат в `appeal_questions`, решение оператора — в `appeal_verifications`.

**Жизненный цикл.** API создаёт строку, как только приняло обращение: на этот момент заполнены только `id`, `document_id`, `appeal_text`, `ip_address` и `created_at`, остальное пусто. Одновременно создаётся строка в `appeal_verifications` со статусом `pending`. Когда воркер закончил классификацию, он заполняет остальные колонки и записывает вопросы. Пока обращение в очереди (или воркер не справился), поля результата остаются пустыми. Строки удаляются только вручную; вместе с карточкой каскадно удаляются её вопросы и верификация.

| Колонка | Тип | Пусто? | Что значит | Пример |
|---|---|---|---|---|
| `id` | uuid | нет | Уникальный идентификатор обращения. Выдаётся автоматически или приходит от клиента, если это корректный UUID. | `3f2b8c1e-0a4d-4c5e-9b7a-1d2e3f4a5b6c` |
| `document_id` | bigint | да | Номер документа в Directum RX, если обращение пришло оттуда. | `12345` |
| `appeal_text` | text | нет | Текст обращения. Персональные данные. | (текст обращения) |
| `summary` | text | да | Краткое содержание, составленное языковой моделью. | `Жалоба на состояние дороги во дворе` |
| `applicant_fio` | text | да | ФИО заявителя, если модель нашла его в тексте. Персональные данные. | (ФИО) |
| `applicant_email` | text | да | E-mail заявителя, если найден. Персональные данные. | (e-mail) |
| `vid_obrascheniya` | text | да | Вид обращения. Модель выбирает из: `Жалоба`, `Заявление`, `предложение`. Ограничения `CHECK` в базе нет. | `Жалоба` |
| `tip_obrascheniya` | text | да | Тип обращения. Модель выбирает из: `Индивидуальное`, `Коллективное`, `Анонимное`. Ограничения `CHECK` нет. | `Индивидуальное` |
| `is_ustnoe` | boolean | да | Устное ли обращение (записанное со слов). | `false` |
| `overall_confidence` | real | да | Общая уверенность агента, от 0 до 1. | `0.87` |
| `needs_verification` | boolean | да | Нужна ли проверка оператором. Например, когда уверенность ниже порога `MIN_CONFIDENCE` или сработали другие причины. | `true` |
| `full_fallback_used` | boolean | да | Включился ли запасной режим: модели показали весь классификатор целиком, потому что поиск не дал подходящих кандидатов. | `false` |
| `candidates` | jsonb | да | Кандидаты, найденные поиском (список), для разбора, почему выбран тот или иной код. | `[{"code": "0003.0001.0002.0004"}]` |
| `llm_provider` | text | да | Поставщик языковой модели. | `ario` |
| `llm_model` | text | да | Название модели. | `qwen-2.5-72b` |
| `ip_address` | inet | да | IP-адрес, с которого пришёл запрос. | `10.0.0.15` |
| `elapsed_seconds` | real | да | Сколько секунд заняла классификация. | `12.4` |
| `created_at` | timestamptz | нет | Когда обращение принято. | `2026-11-11 10:15:00+03` |

### 3.5. `appeal_questions` — вопросы внутри обращения

**Для чего.** В одном обращении может быть несколько вопросов (например, про дорогу и про освещение). Агент находит каждый и выбирает для него код. Одна строка — один вопрос.

**Жизненный цикл.** Записывается воркером при сохранении результата. Если результат сохраняется повторно (например, задачу взяли заново после сбоя), старые вопросы этой карточки удаляются и записываются заново. Удаляются вместе с карточкой.

| Колонка | Тип | Пусто? | Что значит | Пример |
|---|---|---|---|---|
| `id` | bigserial | нет | Номер строки. | `501` |
| `appeal_id` | uuid | нет | К какому обращению относится (`appeal_classifications.id`). | `3f2b8c1e-...` |
| `ordinal` | smallint | нет | Порядковый номер вопроса внутри обращения. | `1` |
| `question_text` | text | да | Формулировка вопроса. | `Отремонтировать дорогу во дворе` |
| `selected_code` | text | да | Код классификатора, который выбрал агент. Может быть пусто, если код не подобран. | `0003.0001.0002.0004` |
| `predmet_vedeniya` | text | да | Предмет ведения: к чьей компетенции относится вопрос. | `Муниципальный уровень` |

### 3.6. `appeal_verifications` — решение оператора

**Для чего.** Результат проверки оператором: согласен ли он с агентом. Эти данные нужны и для статистики, и для дообучения модели.

### 3.8. `jobs` — задачи и очередь

**Для чего.** Это одновременно журнал фоновых задач и сама очередь. Очередь — место, где задачи ждут свободного воркера; воркер — отдельная программа (процесс `python -m worker.run`), которая их выполняет. Когда API принимает запрос, он не считает сам: записывает строку в эту таблицу. Воркер находит в таблице готовую задачу, забирает её себе, выполняет и пишет сюда же результат. По этой таблице API отвечает на вопрос «готово ли?». Отдельного сервиса очередей нет. Вариант с RabbitMQ развивается в ветке `Database_Rabbit`.

**Виды очередей.** Колонка `queue` говорит, какие воркеры могут взять задачу:

| `queue` | Какие задачи туда попадают | Кто берёт |
|---|---|---|
| `classify_sync` | Синхронная классификация (ответ ждут в том же запросе: `/classify`, `/integration/classify-document`) и поиск по классификатору (`search`) | Воркер классификации; такие задачи он берёт первыми |
| `classify` | Фоновая классификация для Directum RX (`/integration/classify-document-async`) и подсчёт векторов аннотаций (`embed_annotation`) | Воркер классификации |
| `training` | Дообучение (`finetune`) | Воркер дообучения (запускается ключом `--training`) |

**Жизненный цикл.**

1. API в одной транзакции создаёт карточку обращения (если есть текст) и строку задачи: статус `queued`, `queue`, `available_at` = сейчас. В той же транзакции отправляется уведомление `job_queued` с именем очереди — оно будит воркеры (раздел 4).
2. Воркер забирает задачу одним запросом: статус `running`, `attempts` + 1, `worker_id` = его имя, `locked_until` = сейчас + `JOB_LEASE_SEC` (по умолчанию 60 с). Это **аренда**: пока она не истекла, задача принадлежит этому воркеру. Два воркера одну строку взять не могут — запрос пропускает строки, которые прямо сейчас забирает другой (`FOR UPDATE SKIP LOCKED`).
3. Пока задача выполняется, воркер каждые `JOB_LEASE_SEC / 3` секунд (20 с) продлевает аренду.
4. Воркер завершает задачу: `done` (результат в `result`) или `error` (текст в `error`), ставится `finished_at`, `locked_until` очищается, отправляется уведомление `job_done`.
5. Если результат забрали (синхронный ответ, опрос `GET /integration/jobs/{id}` с конечным статусом, успешный webhook), ставится `delivered_at`.

**Что бывает при сбоях.**

- **Воркер пропал** (процесс убит, машина выключилась). Аренду никто не продлевает. Когда `locked_until` прошло, задачу берёт другой воркер, `attempts` снова растёт. Если `attempts` стало больше `JOB_MAX_ATTEMPTS` (по умолчанию 2), задача завершается ошибкой без повторной работы. Исключение — дообучение: его по истёкшей аренде не перезапускают, а сразу закрывают ошибкой «воркер дообучения пропал, запустите дообучение заново».
- **База данных временно недоступна во время работы.** Задача возвращается в `queued` с отложенным временем `available_at` (пауза 5, 10, 20, 40, 60, 60… секунд), пока `attempts` меньше `JOB_MAX_ATTEMPTS`; иначе — `error`.

**Когда строки удаляются.** Чистку делает API при постановке новой задачи и каждый воркер не чаще раза в минуту:

- задача с `delivered_at` старше `JOB_DELIVERED_GRACE_SEC` (по умолчанию 600 с) — результат забран, а 10 минут оставлены, чтобы RX мог повторить опрос после сбоя сети;
- любая завершённая (`done`, `error`) задача старше `JOB_TTL_HOURS` (по умолчанию 24 часа), даже если результат не забрали;
- задачи `embed_annotation` удаляются сразу после успешного выполнения — их результат никто не читает;
- задачи `finetune` по прочтению не удаляются, только по `JOB_TTL_HOURS`: страница исторических данных сутки показывает итог дообучения. Когда строки уже нет, статус дообучения берётся из `ml_model_registry.report`.

После удаления опрос по `id` отвечает 404. Поэтому история задач в таблице короткая; долговременные данные лежат в таблицах `appeal_*`.

| Колонка | Тип | Пусто? | Что значит | Пример |
|---|---|---|---|---|
| `id` | char(32) | нет | Идентификатор задачи: 32 символа hex (`uuid4().hex`). Его получает клиент (Directum RX) и по нему опрашивает статус. | `9a1b2c3d4e5f60718293a4b5c6d7e8f9` |
| `job_type` | text | нет | Тип задачи (см. ниже). | `classify` |
| `status` | text | нет | Состояние (см. ниже). | `running` |
| `appeal_id` | uuid | да | Карточка обращения, к которой относится задача. Для `finetune` и `search` пусто. При удалении карточки становится `NULL`, задача не удаляется. | `3f2b8c1e-...` |
| `document_id` | bigint | да | Номер документа в Directum RX. | `12345` |
| `webhook_url` | text | да | Адрес, на который отправить уведомление о завершении (webhook). Работает только для хостов из `WEBHOOK_ALLOWED_HOSTS`. | `https://rx.example.local/hook` |
| `payload` | jsonb | да | Параметры задачи. Содержит и `queue` (копия колонки `queue`); для классификации могут быть `llm_provider`, `llm_model`, `response_kind`; для дообучения — `source`, `force`; для поиска — `q`, `top_k`. | `{"queue": "classify"}` |
| `result` | jsonb | да | Результат при успехе. Для классификации — готовый ответ API. | `{...}` |
| `error` | text | да | Текст ошибки при неудаче. У задачи, которую вернули в очередь после сбоя, здесь остаётся причина сбоя. Значение `superseded` значит, что дублирующее дообучение закрыто при обновлении схемы. | `воркер дообучения пропал, запустите дообучение заново` |
| `attempts` | int | нет | Сколько раз воркер брал задачу. Больше 1 — задачу выдали повторно (воркер пропал или был сбой базы). По умолчанию 0. | `1` |
| `created_at` | timestamptz | нет | Когда создана. | `2026-11-11 10:15:00+03` |
| `started_at` | timestamptz | да | Когда воркер взял её впервые. | `2026-11-11 10:15:02+03` |
| `finished_at` | timestamptz | да | Когда завершена. | `2026-11-11 10:15:14+03` |
| `queue` | text | нет | Вид очереди: `classify_sync`, `classify` или `training` (таблица выше). По умолчанию `classify`. | `classify_sync` |
| `available_at` | timestamptz | нет | С какого момента задачу можно брать. Обычно время постановки; после сбоя базы — позже (отложенный повтор). | `2026-11-11 10:15:00+03` |

| `worker_id` | text | да | Какой воркер взял задачу последним: `имя_компьютера:номер_процесса`. Для диагностики. | `srv-workers-1:4120` |
| `delivered_at` | timestamptz | да | Когда конечный результат отдан потребителю. От этого момента отсчитывается `JOB_DELIVERED_GRACE_SEC`. | `2026-11-11 10:15:15+03` |

Допустимые `job_type` (`CHECK`):

| Значение | Что делает задача | Очередь |
|---|---|---|
| `classify` | Классификация обращения. | `classify_sync` или `classify` |
| `search` | Поиск кандидатов по произвольному тексту (без карточки). | `classify_sync` |
| `finetune` | Дообучение модели. | `training` |
| `embed_annotation` | Подсчёт вектора для новой аннотации оператора. | `classify` |

Допустимые `status` (`CHECK`): `queued` (в очереди), `running` (выполняется), `done` (успешно), `error` (ошибка). Допустимые `queue` (`CHECK jobs_queue_check`): `classify_sync`, `classify`, `training`.

**Индексы.**

- `jobs_status` по `(job_type, status, created_at)` — ускоряет подсчёт очереди и позиции задачи.
- `jobs_queue_ready` по `(queue, available_at)` только для строк `queued` — по нему воркер быстро находит следующую задачу.
- `one_active_finetune` — уникальный индекс, который действует только для задач дообучения в статусах `queued` и `running`. Простыми словами: одновременно может существовать не больше одной «живой» задачи дообучения. Вторая попытка запуска получит отказ (HTTP 409), а не создаст дубль. Для остальных типов задач ограничения нет.

**Обновление старой базы.** Колонки `queue`, `available_at`, `locked_until`, `worker_id`, `delivered_at` добавляются скриптом схемы (`init_db.py`, запускается при каждом старте) без потери данных. У старых строк `queue` берётся из `payload->>'queue'`, иначе `classify`.

## 4. Уведомления NOTIFY

В PostgreSQL есть механизм **LISTEN / NOTIFY**: один процесс подписывается на канал (`LISTEN`), другие отправляют в него короткие сообщения (`NOTIFY`), и подписчик получает их сразу, без постоянных опросов. Уведомление уходит в момент подтверждения транзакции (`COMMIT`), поэтому подписчик не увидит сообщение раньше, чем данные станут видны в таблицах. В таблицы такие уведомления ничего не пишут.

| Канал | Кто отправляет | Что в сообщении | Кто слушает и зачем |
|---|---|---|---|
| `job_queued` | API, когда поставил задачу (в той же транзакции, что и строка в `jobs`). | Имя очереди: `classify_sync`, `classify` или `training`. | Воркеры. Свободный воркер ждёт этого сигнала и сразу забирает задачу. Если сигнал потерялся, воркер всё равно проверяет таблицу каждые `QUEUE_POLL_SEC` секунд (по умолчанию 5) — так же он находит отложенные повторы и задачи с истёкшей арендой. |
| `job_done` | Воркер, когда задача перешла в `done` или `error` (в той же транзакции, что и запись результата в `jobs`). | Идентификатор задачи (`jobs.id`, 32 символа). | API. Синхронные запросы ждут именно этого сигнала вместо постоянных опросов базы; получив его, читают результат из `jobs`. Если за `SYNC_WAIT_TIMEOUT_SEC` сигнала нет, API отвечает 504. |
| `model_changed` | Любая активация версии модели через реестр. | Номер новой активной версии. | Никто из процессов проекта — это сигнал для внешних систем (например, мониторинга). Воркеры переходят на новую версию сами: перед каждой задачей сверяют активную версию в `ml_model_registry`. |

**Как API узнаёт, что воркеры живы.** Соединение, на котором воркер слушает `job_queued`, подписано именем `classifier-worker:<очереди>`, например `classifier-worker:classify_sync,classify`. `/health` ищет такие соединения в системном представлении `pg_stat_activity`: есть хотя бы одно с очередью `classify` — `agent_ready: true`. Отдельной таблицы воркеров нет.

### Сколько записей в каждой таблице


### Что сейчас в очереди и выполняется

```sql
SELECT id, job_type, queue, status, attempts, worker_id,
       created_at, available_at, locked_until
FROM jobs
WHERE status IN ('queued', 'running')
ORDER BY (queue = 'classify_sync') DESC, available_at, created_at;
```

Порядок строк — тот же, в котором воркеры берут задачи: сначала синхронные, затем по времени.

### Сколько задач ждёт в каждой очереди

```sql
SELECT queue,
       count(*) FILTER (WHERE status = 'queued' AND available_at <= now()) AS "готовы",
       count(*) FILTER (WHERE status = 'queued' AND available_at > now())  AS "отложены",
       count(*) FILTER (WHERE status = 'running')                          AS "выполняются",
       min(created_at) FILTER (WHERE status = 'queued')                    AS "самая_старая"
FROM jobs
GROUP BY queue
ORDER BY queue;
```

Много «готовых» задач при нуле «выполняются» — воркеры этой очереди не запущены или не видят базу.

### Какие воркеры сейчас подключены

```sql
SELECT application_name AS "воркер_и_очереди", client_addr, backend_start
FROM pg_stat_activity
WHERE datname = current_database()
  AND application_name LIKE 'classifier-worker:%'
ORDER BY backend_start;
```

Одна строка — один процесс воркера. `client_addr` — адрес, с которого воркер подключился: у воркеров другой машины это её адрес, у воркеров этой же машины — внутренний адрес Docker.
