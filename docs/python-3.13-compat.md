# Совместимость с Python 3.13.2

Дата проверки: 2026-08-11. Ветка: `feat/python-3.13-compat`.

## Итог

**Проект совместим с Python 3.13.2.** Единственное изменение, которое потребовалось —
снять пин `numpy<2.0`. Правок исходного кода не понадобилось.

| Проверка | Результат |
|---|---|
| Установка всех зависимостей на 3.13.2 | ✅ без конфликтов |
| Полный прогон тестов | ✅ 126 passed, 5 failed — **те же 5**, что и на 3.11 |
| Чтение существующей векторной базы (`.npy`) под numpy 2.x | ✅ `(2108, 768)`, float32 |
| Загрузка модели эмбеддингов + кодирование запроса | ✅ `(1, 768)` float32 |
| Ретривер (косинусный поиск по 2108 записям) | ✅ 50 кандидатов, top1 осмысленный |
| Импорт `api_server` (FastAPI + pydantic) | ✅ |
| **Сборка боевого образа** (`--build-arg PYTHON_VERSION=3.13.2`) | ✅ 8.78 ГБ, torch 2.13.0+cu130 |
| **Сервис из этого образа** (`/health` на отдельном порту) | ✅ `ok`, 2108 записей |
| **Живая классификация** vs прод на 3.11 | ✅ детерминированная часть совпала |
| Регресс на 3.11 после правок | ✅ нет: 126 passed, те же 5 падений |

Пять падающих тестов (`test_candidate_rerank` ×3, `test_strict_validation` ×2) —
досборочные, воспроизводятся на 3.11 на чистом HEAD и к версии Python отношения не имеют.

## Что мешало

Единственный блокер — **пин `numpy>=1.26.0,<2.0`**: колёс `cp313` для numpy 1.26
не существует, установка на 3.13 падала на этапе разрешения зависимостей.

Пин стоял из-за того, что numpy 2.0 удалил алиасы (`np.float_`, `np.int_` и т.п.).
Проверка показала, что **в коде проекта таких алиасов нет** (`src/`, `scripts/`, `tests/`),
а зависимости давно поддерживают numpy 2.x. Поэтому мажор поднимается без правок.

Отдельно проверено и **не найдено**:
- модулей, удалённых в 3.12/3.13 (`distutils`, `cgi`, `telnetlib`, `imghdr` и прочий PEP 594);
- устаревших вызовов `datetime.utcnow()`, `locale.getdefaultlocale()`.

## Внесённые изменения

**`requirements.txt`** — мажор numpy выбирается маркером окружения, чтобы прод на 3.11
остался на проверенной 1.x, а на 3.12+ ставилась обязательная 2.x:

```
numpy>=1.26.0,<2.0; python_version < "3.12"
numpy>=2.1.0; python_version >= "3.12"
```

**`Dockerfile`** — версия интерпретатора вынесена в build arg, дублирования файла нет:

```dockerfile
ARG PYTHON_VERSION=3.11
FROM python:${PYTHON_VERSION}-slim
```

По умолчанию собирается 3.11 (проверено: `Python 3.11.15`), переопределение работает
(`--build-arg PYTHON_VERSION=3.13.2` → `Python 3.13.2`). **Поведение прод-сборки не изменилось.**

**`Dockerfile.py313check`** — проверочный образ, не продуктивный. Отличия: torch ставится
CPU-only (~2 ГБ вместо ~8.8 ГБ у боевого с CUDA), ставится pytest, `tests/` монтируется при
запуске (они исключены из контекста сборки в `.dockerignore`).

**`setup.ps1`** — принимает и 3.11, и 3.13 (ищет в порядке 3.13 → 3.11). Файл остаётся ASCII-only.

**Документация** — `CLAUDE.md`, `README.md` приведены в соответствие.

## Как повторить проверку

Хостовый интерпретатор трогать не нужно — всё в контейнере:

```bash
docker build -f Dockerfile.py313check -t og-py313check .
docker run --rm -v "$PWD/tests:/app/tests:ro" og-py313check
```

Прод-образ на 3.13:

```bash
docker build --build-arg PYTHON_VERSION=3.13.2 -t classifier-py313 .
```

## Боевой образ на 3.13

Собран и проверен: `docker build --build-arg PYTHON_VERSION=3.13.2 -t classifier-py313 .`
— 8.78 ГБ, python 3.13.2, numpy 2.5.2, torch 2.13.0+cu130, sentence-transformers 5.7.0.
Поднятый из него сервис отвечает `{"status":"ok","agent_ready":true,"classifier_entries":2108}`.

Сравнение живой классификации одного и того же обращения на 3.13 и на проде 3.11: коды
детерминированной части совпали (код прекращения рассмотрения первым + тот же тематический).
Разошёлся один дополнительный код — `0001.0002.0027.0125`: regex-маркеров повтора в тексте нет,
он приходит только от флага LLM `is_repeat_appeal`, который модель выставила в одном прогоне и не
выставила в другом. Флаги в обоих контейнерах идентичны, так что это разброс LLM, а не влияние
версии Python.

### Замечание про место на диске

Сборка 8.78-гигабайтного образа отняла у C всего **0.3 ГБ** (10.03 → 9.73 ГБ). Причина:
`docker_data.vhdx` ранее разросся до 54 ГБ, тогда как данных внутри ~20 ГБ, и Docker
переиспользует уже выделенные блоки. То есть «свободное место» для образов есть внутри vhdx,
даже когда Windows показывает мало свободного на C. Переносить хранилище Docker на другой диск
для этой задачи не потребовалось.

## Что НЕ проверено

- **Python 3.12 не тестировался.** Маркеры в `requirements.txt` его покрывают
  (`>= 3.12` → numpy 2.x), но прогона не было.
- **Скорость не замерялась** — сравнение производительности 3.11 vs 3.13 не проводилось.
- Хост остался на 3.11: интерпретатор 3.13 в систему не устанавливался.
