## Дата: 2026-07-24 — Исследование #1: конкурентность обработки

### Вопрос
Возможна ли в текущем пайплайне обработка обращений параллельно, или только
синхронно, по очереди?

### Вывод (кратко)
**Сейчас обращения обрабатываются строго последовательно (одно за другим).**
Это не фундаментальное ограничение архитектуры, а следствие того, **как**
написаны эндпоинты. Устраняется малой правкой (см. «Опции»).

### Разбор по коду

**1. Эндпоинты объявлены `async def`, но внутри — синхронный блокирующий вызов**
- `src/api_server.py:303` — `async def classify_appeal_json` → напрямую
  `agent.classify(...)` (`:312`)
- `src/api_server.py:335` — `async def classify_appeal_file` → тот же путь
- `src/integration_api.py:58` — `async def classify_document` → напрямую
  `agent.classify(text)` (`:77`)
- Вызов идёт **прямо в event loop**, без `run_in_executor` / `await` /
  вынесения в threadpool.

**2. `agent.classify()` полностью блокирующий**
- `src/classifier_agent.py:598` — `self.embedder.encode(...)` —
  SentenceTransformer, CPU-блокировка (десятки мс).
- `src/classifier_agent.py:645` — `httpx.Client(...)` — **синхронный** HTTP к
  LLM. Это доминирующая задержка (секунды). При full-classifier fallback —
  два тяжёлых LLM-вызова подряд.

**3. Один воркер uvicorn**
- `Dockerfile:24` — `uvicorn src.api_server:app --host 0.0.0.0 --port 8005`,
  без `--workers` → 1 процесс = 1 event loop.

### Почему получается очередь
Блокирующий код внутри `async def` занимает **единственный поток event loop на
всё время** классификации. Пока один запрос ждёт ответа LLM (секунды), loop не
может начать следующий. Второй запрос принимается сокетом, но ждёт освобождения
loop → фактически очередь с одним «в работе» (FIFO, глубина 1 в обработке).

> Замечание: будь эндпоинт объявлен обычным `def` (не `async def`), Starlette
> сам увёл бы его в threadpool и запросы шли бы параллельно. Текущая форма
> (`async def` + блокирующее тело) — худший вариант для конкурентности.

### Опции распараллеливания (от дешёвого к дорогому)

| # | Способ | Изменение | Плюс | Минус |
|---|--------|-----------|------|-------|
| A | Убрать `async` у эндпоинтов (сделать `def`) | ~3 строки | Starlette-threadpool, LLM-ожидания перекрываются; 1 копия модели | нужен `Lock` вокруг `encode` (thread-safety модели) |
| B | `await anyio.to_thread.run_sync(agent.classify, ...)` | ~5 строк, `async` сохраняется | то же, явный контроль | тот же вопрос с локом на `encode` |
| C | `uvicorn --workers N` | 1 строка в Dockerfile | реальная параллельность процессов | ×N RAM (каждый воркер грузит модель ~сотни МБ + torch) |
| D | `httpx.AsyncClient` + `await` внутри `classify` | рефактор LLM-слоя | честная single-process конкурентность | больше кода, переписать все LLM-вызовы |

**Ориентир для нашего кейса** (интеграция с RX, поток документов): **A или B** —
минимальная правка, снимает главный простой (ожидание LLM), одна копия модели в
памяти. Лок только вокруг `encode`; HTTP к LLM параллелится свободно.
