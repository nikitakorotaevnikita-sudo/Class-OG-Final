# RX Integration Service — classify-document (MVP)

- **Дата:** 2026-07-08
- **Статус:** утверждён (дизайн)
- **Автор:** совместно с оператором

## 1. Цель

Дать Directum RX 26.1 возможность классифицировать обращение гражданина через
внешний REST-сервис. RX-процесс дёргает наш сервис, передавая **id документа**;
сервис сам вытягивает документ из RX, извлекает текст, классифицирует и
возвращает JSON: ФИО заявителя, краткую суть и список выявленных вопросов с кодами
классификатора.

Это MVP. Запись результата обратно в карточку RX в объём не входит.

## 2. Контекст

- Классификатор уже реализован: двухстадийный пайплайн (семантический поиск
  multilingual-e5 → LLM), см. `src/classifier_agent.py`. Возвращает
  `ClassificationResult` со списком вопросов (`code`, `name`, `full_path`,
  `confidence`, …).
- Извлечение текста из TXT/PDF уже есть: `src/text_extractor.py`.
- RX-стенд: OData v4 на `http://172.16.96.98/integration/odata/`, Basic-auth
  `Administrator:11111`. Документ по id читается (`IIncomingLetters(26)` →
  метаданные, версия `Id:2`). Классификатор загружен в RX нативно
  (`ISections`→`ITopics`→`IThemes`→`IQuestions`→`ISubQuestions`), код L4 проекта ==
  `IQuestions.FullCode`. Полные факты интеграции — в памяти проекта
  (`rx-integration-odata`).

## 3. Модель взаимодействия

Выбран **Вариант B (pull)**: RX передаёт только id, текст качает наш сервис.

```
RX-процесс ──POST /integration/classify-document {document_id}──▶ сервис
   сервис ──OData GET по id──▶ RX: документ → последняя версия → тело файла
   извлечение текста (PDF с текстовым слоем / TXT)
   ClassifierAgent.classify(text) → вопросы[]  (+ LLM: applicant_fio, summary)
   ◀── JSON ── { document_id, applicant_fio, summary, questions[] }
```

## 4. Контракт API

### Запрос
`POST /integration/classify-document`
```json
{ "document_id": 26 }
```

### Ответ (200)
```json
{
  "document_id": 26,
  "applicant_fio": "Иванов И.И.",
  "summary": "Краткая суть обращения, не более 250 символов.",
  "questions": [
    { "code": "0001.0002.0015.0042", "question": "Наименование вопроса текстом" }
  ]
}
```

Поля:
- `document_id` — эхо входного id (для привязки на стороне RX).
- `applicant_fio` — ФИО заявителя строго в формате «Фамилия И.О.»; `null`, если
  извлечь не удалось.
- `summary` — краткая суть обращения по итогам классификации, **≤ 250 символов**
  (жёстко обрезается при превышении).
- `questions[]` — по одному элементу на каждый выявленный в обращении вопрос:
  - `code` — код классификатора формата `XXXX.XXXX.XXXX.XXXX`
    (== `IQuestions.FullCode` в RX).
  - `question` — наименование вопроса текстом.
- Суть (`summary`) — одна на всё обращение, не на каждый вопрос.

## 5. Компоненты (новые, изолированные)

### 5.1 `src/rx_client.py` — клиент RX OData
- `get_document_text(document_id: int) -> tuple[str, str]` → `(text, filename)`.
- Шаги: документ по id → последняя версия → тело (base64 / `$value`) →
  `text_extractor.extract_text(...)`.
- Basic-auth и базовый URL — из `.env` (`RX_ODATA_URL`, `RX_USER`, `RX_PASSWORD`).
- **Точка отладки 500:** получение тела инкапсулировано в одном приватном методе.
  Порядок попыток: (a) `.../Versions(<vid>)/Body/$value`, при ошибке (b) путь через
  `/Web/api`. Публичный интерфейс метода при смене способа не меняется.
- Ошибки маппятся в доменные исключения: `DocumentNotFound`, `BodyFetchError`.

### 5.2 `src/fio_extractor.py` — нормализатор ФИО
- `normalize_fio(raw: str) -> str | None` → «Фамилия И.О.».
- Разбирает «Иванов Иван Иванович» → «Иванов И.И.»; терпим к лишним пробелам,
  уже сокращённым инициалам, отсутствию отчества («Иванов Иван» → «Иванов И.»).
- Возвращает `None`, если распарсить не удалось.

### 5.3 Расширение LLM-промпта (`src/classifier_agent.py`)
- В JSON-ответ модели добавляются два поля верхнего уровня: `applicant_fio`
  (сырое ФИО из текста) и `summary` (краткая суть). Отдельного вызова модели нет.
- `ClassificationResult` расширяется полями `applicant_fio: str | None`,
  `summary: str`. Существующие потребители (`operator_cli`, backoffice) не ломаются
  (поля со значениями по умолчанию).
- ФИО прогоняется через `fio_extractor.normalize_fio`; при `None` в ответ идёт
  `null`. `summary` обрезается до 250 символов на стороне сервиса.

### 5.4 `src/integration_api.py` — роутер
- APIRouter с эндпоинтом `POST /integration/classify-document`.
- Подключается к существующему приложению в `api_server.py`
  (`app.include_router(...)`) — сам `api_server.py` не раздувается.
- Оркестрация: `rx_client.get_document_text` → `agent.classify` → сборка ответа.

## 6. Обработка ошибок (HTTP-коды для RX)

| Ситуация | Код | Тело |
|---|---|---|
| Документ не найден в RX | 404 | `{"detail": "Документ {id} не найден в RX"}` |
| Тело не скачалось (текущая 500 от OData) | 502 | `{"detail": "Не удалось получить тело документа из RX: ..."}` |
| Текст пустой / не извлечён | 400 | `{"detail": "Документ не содержит извлекаемого текста"}` |
| ФИО не найдено | 200 | `applicant_fio: null` (ответ не роняем) |
| Ошибка классификации (LLM недоступен и т.п.) | 500 | `{"detail": "Ошибка классификации: ..."}` |

## 8. Тестирование

- **Юнит `fio_extractor`:** «Иванов Иван Иванович»→«Иванов И.И.»; «Иванов Иван»→
  «Иванов И.»; мусор→`None`; лишние пробелы; уже сокращённые инициалы.
- **Юнит `summary`:** строка >250 символов обрезается до 250.
- **Юнит `rx_client`:** замоканный HTTP — успешный документ, 404, ошибка тела →
  правильные доменные исключения.
- **Эндпоинт:** FastAPI `TestClient` с замоканными `rx_client` и агентом — проверка
  формы JSON-ответа и кодов ошибок.
- **Смоук на стенде:** сквозной прогон по документу id=26 (после устранения 500).

## 9. Вне объёма MVP (YAGNI)

- Запись результата обратно в `IRequests` / `IRequestQuestionss`.
- Аутентификация нашего эндпоинта (RX→сервис) — на MVP без неё.
- OCR сканов без текстового слоя.
- Дообучение модели по этому потоку.
- Поддержка форматов кроме PDF-с-текстовым-слоем и TXT.

## 10. Открытые риски

- **Скачивание тела через Integration OData → 500** на стенде. План:
  проверить права интеграционного пользователя; при необходимости — путь через
  `/Web/api`. Инкапсулировано в `rx_client`, на контракт API не влияет.

## 11. Деливери

После реализации предоставить оператору **адрес сервиса интеграции для отладки**
(эндпоинт `http://<host>:8000/integration/classify-document`).
