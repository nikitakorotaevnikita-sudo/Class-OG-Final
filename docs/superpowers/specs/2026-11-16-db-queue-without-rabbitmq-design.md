# Очередь задач в PostgreSQL вместо RabbitMQ — дизайн

Дата: 2026-11-16. Ветка: `Database` (локальная, без push). Ветка `Database_Rabbit` остаётся
вариантом с RabbitMQ и этой переделки не получает.

## Зачем

Руководство решило отказаться от RabbitMQ. Очередь задач должна жить в базе данных: API пишет
задачу в таблицу очереди, воркеры забирают задачи оттуда и туда же пишут результат. Отдельный
брокер — лишний сервис в установке и сопровождении; PostgreSQL уже есть и уже хранит задачи.

## Цели

1. Нет RabbitMQ и Celery: ни контейнера, ни настроек в `.env`, ни зависимостей, ни упоминаний в
   инструкциях. Установка и запуск — без брокера.
2. Одна таблица очереди для всех видов задач; вид очереди — поле записи.
3. API ставит задачу записью в таблицу; воркер забирает задачу из таблицы и пишет туда результат.
4. Завершённая задача удаляется, когда её результат забрали; незабранная — через `JOB_TTL_HOURS`.
5. Поведение для RX и операторов не меняется: те же адреса, ответы, коды (`202` + `job_id`,
   `429`, `404`, `504`, `503`), webhook, синхронное ожидание через `LISTEN job_done`.
6. Надёжность не хуже, чем с RabbitMQ: задача не выполняется дважды одновременно; задача умершего
   воркера переходит к другому; сбой БД — повтор с паузой; лимит попыток сохраняется.

## Не цели

- Масштаб на много машин и десятки воркеров. Расчёт — до 5 воркеров одновременно (изредка больше).
- Изменения в ветке `Database_Rabbit`.
- Новая очередь для чего-то, чего нет сейчас.

## Анти-цели (это провал, даже если «работает»)

- Две очереди (служебные таблицы библиотеки рядом с `jobs`).
- Постоянный частый опрос базы каждым воркером как основной механизм доставки.
- Потеря задачи при падении воркера или потеря результата, который RX ещё не забрал.
- Импорт модели/torch процессом API.

## Ограничения

- PostgreSQL 16 + pgvector — единственное хранилище. psycopg 3 (уже в проекте).
- Windows (основная машина): воркеры — обычные процессы, без fork; Linux и Docker — тоже.
- Существующие базы (стенды после миграции) должны обновиться схемой без потери данных:
  `schema.sql` идемпотентен (`ALTER TABLE … ADD COLUMN IF NOT EXISTS`), обе копии схемы
  побайтно одинаковы.
- Персональные данные по-прежнему не попадают в Git; `stop.*` не делает `down -v`.

## Подходы (выбран A)

| | Подход | Почему |
|---|---|---|
| **A** ✔ | Своя очередь на таблице `jobs`: поле вида очереди, аренда, отложенный повтор; воркер — свой процесс без Celery; пробуждение `NOTIFY job_queued` + редкий контрольный опрос; захват `SELECT … FOR UPDATE SKIP LOCKED` | Ровно ТЗ (одна таблица, вид — поле, результат там же), без новых зависимостей, убирает Celery; половина логики (claim, владение, лимит попыток) уже есть |
| B | Celery + kombu-транспорт SQLAlchemy на PostgreSQL | Свои служебные таблицы сообщений → две очереди; только опрос, без NOTIFY; транспорт экспериментальный |
| C | Библиотека (procrastinate, PgQueuer) | Своя таблица задач → две очереди; новая зависимость в офлайн-установке; асинхронные API при синхронной модели; Windows не гарантирован |

Выбор сделал пользователь: **A**. Удаление задач: **после того как результат забран**, иначе по
`JOB_TTL_HOURS` — тоже решение пользователя (вариант «удалять сразу при завершении» отклонён:
RX при опросе получил бы 404).

## Дизайн

### Таблица очереди — `jobs` (расширяется, не заменяется)

Новые поля (добавляются к существующим `id, job_type, status, appeal_id, document_id,
webhook_url, payload, result, error, attempts, created_at, started_at, finished_at`):

| Поле | Тип | Смысл |
|---|---|---|
| `queue` | `TEXT NOT NULL`, CHECK `IN ('classify_sync','classify','training')` | Идентификатор вида очереди. Для существующих строк заполняется из `payload->>'queue'`, иначе `'classify'` |
| `available_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | С какого момента задачу можно брать (отложенный повтор после сбоя) |
| `locked_until` | `TIMESTAMPTZ NULL` | Аренда: до какого момента задача принадлежит воркеру, который её взял |
| `worker_id` | `TEXT NULL` | Кто взял (`hostname:pid`) — для диагностики |
| `delivered_at` | `TIMESTAMPTZ NULL` | Когда конечный результат отдан потребителю (синхронный ответ, опрос RX, webhook) |

Индекс для выбора задачи: `(queue, available_at) WHERE status = 'queued'`. Индекс
`one_active_finetune` и CHECK на `job_type`/`status` остаются. Статусы прежние:
`queued → running → done | error`.

Соответствие видов задач очередям (как сейчас в маршрутах Celery):
`classify` синхронный → `classify_sync`; `classify` асинхронный → `classify`;
`search` → `classify_sync`; `embed_annotation` → `classify`; `finetune` → `training`.

### Постановка задачи (API)

`job_api.submit_job` в одной транзакции: создаёт карточку (если нужна) и строку `jobs`
(`status='queued'`, `queue`, `available_at=now()`), затем `NOTIFY job_queued, '<queue>'`.
Проверка `JOB_MAX_QUEUED` → `429` — как сейчас. Отправки в брокер больше нет; `DispatchError`
и `503` при недоступном брокере уходят, `503` остаётся для недоступной БД.

### Воркер

Обычный процесс Python (`src/worker/…`), запускается командой вида
`python -m worker.run --queues classify_sync,classify` или `--queues training`. Один процесс —
одна задача за раз (модель загружена один раз на процесс). Параллельность — числом процессов:
`CLASSIFY_WORKERS` (по умолчанию 2, расчёт до 5). Воркер дообучения — отдельный процесс с
`--queues training`, как и раньше запускается ключом `--training`.

Цикл воркера:

1. Отдельное соединение с `LISTEN job_queued`. Ждёт сигнала, но не дольше `QUEUE_POLL_SEC`
   (по умолчанию 5 с) — контрольный опрос ловит потерянный сигнал, наступившие
   `available_at` и истёкшие аренды.
2. Захват одной задачи одним запросом:
   `UPDATE jobs SET status='running', attempts=attempts+1, started_at=coalesce(started_at, now()),
   locked_until=now()+lease, worker_id=… WHERE id = (SELECT id FROM jobs WHERE queue = ANY(…) AND
   ((status='queued' AND available_at<=now()) OR (status='running' AND locked_until<now()))
   ORDER BY (queue='classify_sync') DESC, available_at, created_at
   FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING …`.
   Синхронные задачи берутся первыми. Задача с истёкшей арендой (воркер умер) забирается
   заново; `attempts` растёт, и при `attempts > JOB_MAX_ATTEMPTS` задача завершается ошибкой без
   запуска работы — как сейчас.
3. Пока задача выполняется, фоновый поток продлевает аренду каждые `JOB_LEASE_SEC/3`
   (`locked_until = now() + JOB_LEASE_SEC`, только если `attempts` совпадает — проверка
   владения). `JOB_LEASE_SEC` по умолчанию 60. Долгое дообучение держит аренду продлениями.
4. Работа и запись результата — существующие `run_*` из `queueing/tasks.py` (логика остаётся,
   уходят Celery-обёртки): карточка + `finish` + `NOTIFY job_done` в одной транзакции, с
   проверкой владения (`lock_owned` по `attempts`). `finish` сбрасывает `locked_until`.
5. Сбой инфраструктуры (БД) при `attempts < JOB_MAX_ATTEMPTS`: задача возвращается в `queued`
   с `available_at = now() + пауза` (5, 10, 20, 40, 60, 60… с — как сейчас), иначе — ошибка.
   Если БД недоступна и вернуть задачу нельзя, её подберёт другой воркер по истечении аренды.
6. Webhook — после commit, как сейчас (`queueing/webhook.py`).
7. `.env` и смена активной модели подхватываются перед каждой задачей (`worker_main.get_agent`
   — как сейчас). Прогрев модели — при старте процесса.
8. Остановка (Ctrl+C / SIGTERM / `stop.*`): текущая задача не обрывается намеренно; если
   процесс убит — задачу вернёт истечение аренды.
9. Аренда потеряна, а воркер жив (продление не достучалось до БД дольше `JOB_LEASE_SEC`):
   - классификация, поиск, аннотации — задачу может забрать другой воркер; работа двух копий
     допустима (лишний вызов LLM), записывает результат только владелец (`lock_owned` +
     `finish` по `attempts` — как сейчас);
   - **дообучение по истёкшей аренде не перезапускается**: задача `training` с истёкшей
     арендой не забирается повторно, а завершается ошибкой «воркер дообучения пропал, запустите
     дообучение заново» (так же, как сейчас: «повторов при сбое нет»). Захват для очереди
     `training` берёт только `queued`. Перед регистрацией версии `run_training` проверяет
     владение задачей (`lock_owned`); не владеет — не регистрирует.

### Удаление завершённых задач

- Результат «забран» (`delivered_at = now()`), когда: синхронный вызов вернул его клиенту;
  `GET /integration/jobs/{id}` (и `/api/finetune` для статуса дообучения) отдал конечный
  статус; webhook доставлен успешно. Задачи `embed_annotation` никто не читает — они
  удаляются сразу при завершении.
- Строки с `delivered_at` старше `JOB_DELIVERED_GRACE_SEC` (по умолчанию 600 с — даём RX
  повторить опрос после сетевого сбоя) удаляются.
- Конечные строки без `delivered_at` старше `JOB_TTL_HOURS` (24 ч) удаляются — как сейчас.
- Исключение — дообучение (`finetune`): его строки не удаляются по прочтению, только по
  `JOB_TTL_HOURS`, чтобы страница исторических данных показывала итог и текст ошибки сутки.
  Когда строки нет, `/api/finetune/status` показывает итог последней версии из
  `ml_model_registry.report` (если есть), иначе «дообучение не запускалось».
- Чистку делает существующий `cleanup_expired` при постановке задачи и воркеры между задачами.
- После удаления опрос `job_id` отвечает `404` — как сейчас по истечении TTL.

### Здоровье (`/health`)

- `db` — как сейчас. Поле `broker` убирается.
- `agent_ready` — есть хотя бы один живой воркер очередей классификации. Воркеры держат
  соединение `LISTEN` с `application_name = 'classifier-worker:<очереди>'`; API проверяет
  `pg_stat_activity`. Отдельной таблицы воркеров нет.
- Скрипты запуска ждут `"db":true` (и `agent_ready` — как и прежде, с выводом причины).

### Развёртывание

- `docker-compose.yml`: удаляются сервис `rabbitmq`, `deploy/rabbitmq/`, переменные
  `RABBITMQ_*`; `worker-classify` запускает `python -m worker.run --queues classify_sync,classify`
  с `deploy.replicas: ${CLASSIFY_WORKERS:-2}`; `worker-training` — `--queues training`
  (профиль `training`).
- `start.cmd/start.sh local`: окна/процессы воркеров запускают тот же модуль; RabbitMQ не
  поднимается; `stop.*` ищет процессы по новой командной строке.
- `install.*`, `scripts/setup_infra*`: выбор порта и запуск только PostgreSQL.
- `.env.example`, `core/config.py`: удаляются `RABBITMQ_URL`, `RABBITMQ_PORT`,
  `RABBITMQ_MGMT_PORT`, `RABBITMQ_BIND`, `RABBITMQ_DEFAULT_USER/PASS`, `BROKER_HEARTBEAT_SEC`,
  `WORKER_PROC_ALIVE_TIMEOUT_SEC`, `CLASSIFY_CONCURRENCY`; добавляются `QUEUE_POLL_SEC=5`,
  `JOB_LEASE_SEC=60`, `JOB_DELIVERED_GRACE_SEC=600`. `requirements.txt`: без `celery`.
- Пользовательский `.env` на этой машине: строки RabbitMQ удаляются (локально, не в Git).

### Код

- Уходят: `queueing/celery_app.py`, `queueing/warmup.py` (прогрев переезжает в старт воркера),
  `CeleryDispatcher`, Celery-обёртки в `tasks.py`, `_ping_workers` через Celery inspect.
- Появляются: модуль цикла воркера (`worker/run.py` или аналог) и методы хранилища очереди
  (`enqueue`, `claim_next`, `extend_lease`, `release_for_retry`, `mark_delivered`,
  чистка) — в обоих бэкендах (`memory` и `pg`), с тестами на обоих.
- `LocalDispatcher` (тесты, `STORAGE_BACKEND=memory`) сохраняет роль «выполнить в процессе».
- Пакет `queueing` остаётся (ожидание, webhook, задачи), меняется содержимое.

## Проверка

- Полный набор тестов: только 4 известных падения; тесты с БД — на временном контейнере.
- Нагрузочный тест очереди на PostgreSQL: N воркеров-потоков × M задач — каждая выполнена ровно
  один раз; задача «убитого» воркера (аренда истекла) выполнена другим; повтор после сбоя БД.
- Живой запуск на этой машине: `install` (без RabbitMQ) → `launch.bat` [1] → `/health`,
  поиск, синхронная и асинхронная классификация через очередь, `stop.cmd local`.
- `docker compose config -q`.

## Решения, принятые мной (можно поправить)

- Воркер — процесс на одну задачу; параллельность числом процессов (`CLASSIFY_WORKERS`), в
  Docker — `deploy.replicas`. Без собственного «супервизора» дочерних процессов.
- Значения по умолчанию: `QUEUE_POLL_SEC=5`, `JOB_LEASE_SEC=60`, `JOB_DELIVERED_GRACE_SEC=600`.
- Поле `broker` убирается из `/health`; `agent_ready` определяется через `pg_stat_activity`.
- Задачи `embed_annotation` удаляются сразу при завершении (их результат никто не читает).
- Дообучение: строки задачи живут до `JOB_TTL_HOURS` (не удаляются по прочтению); без строки
  статус берётся из `ml_model_registry.report`. Дообучение по истёкшей аренде не
  перезапускается — ошибка, как сейчас «повторов нет»; регистрация версии — только владельцем.
- Классификация при потерянной аренде у живого воркера может выполниться дважды (лишний вызов
  LLM), результат пишет только владелец — строже не делаем.
