# Агент классификации обращений граждан

Сервис читает обращение гражданина и сам определяет, к какому разделу **Общероссийского
классификатора вопросов обращений** (v4, 2108 позиций) оно относится и какой это вид обращения
по **59-ФЗ** — жалоба, заявление или предложение. Результат получает оператор: он проверяет
предложенные коды и при необходимости исправляет их. Сервис встраивается в Directum RX 25.3.

## Как это работает — в двух словах

1. Обращение приходит из Directum RX или из веб-формы.
2. Сервис находит в классификаторе несколько десятков похожих по смыслу позиций (поиск по
   «векторам» — числовым отпечаткам смысла текста, они хранятся в PostgreSQL).
3. Языковая модель (LLM) читает обращение и этих кандидатов, выделяет все вопросы обращения и
   для каждого выбирает лучший код с оценкой уверенности.
4. Оператор подтверждает или исправляет результат. Подтверждённые ответы со временем
   используются для дообучения поиска.

Внутри это несколько процессов: веб-сервис (API) принимает запросы и записывает задачи в
таблицу очереди в PostgreSQL, воркеры (отдельные процессы с моделью) забирают задачи оттуда,
классифицируют и пишут результат туда же. Отдельного сервиса очередей нет — только PostgreSQL.
Вариант с RabbitMQ развивается в ветке `Database_Rabbit`.

## Быстрый старт

Нужен запущенный Docker Desktop (Windows) или Docker Engine с compose v2 (Linux).

| | Windows | Linux |
|---|---|---|
| Установить (один раз) | `install.bat` | `./install.sh` |
| Запустить | `launch.bat` → пункт **[1]** | `./launch.sh` → пункт **[1]** |
| Остановить | `stop.cmd` | `./stop.sh` |

Воркеры можно вынести на другие машины: на главном сервере — `start.cmd api` (API без
воркеров), на машинах воркеров — `start.cmd worker`. Как это настроить — в
[Установке и настройке](instructions/Setup_instruction.md).

После запуска: веб-форма — http://localhost:8010, бэк-офис — http://localhost:8010/backoffice,
проверка состояния — http://localhost:8010/health.

## Точность

Основной замер — 56 реальных обращений с разметкой специалистов (`data/ii25_test.jsonl`).
Оператор видит основной код и 2–3 альтернативы, поэтому главная метрика — попадание среди них:

| Метрика | Значение |
|---|---:|
| Правильная тема (L3) среди трёх предложенных кодов | **75.0%** |
| Правильная тематика (L2) среди трёх предложенных кодов | **80.4%** |
| Точный код среди трёх предложенных | **51.8%** |
| Точный код первым вариантом | **26.8%** |

Заказчик на выборке из 12 типовых обращений подтвердил правильность первого варианта во всех 12.
Подробности и история улучшений — [docs/classification_quality.md](docs/classification_quality.md).

## Ветки и правила мерджей

### Рабочие ветки

| Ветка | Назначение |
|---|---|
| **`main`** | Основной проект и **наиболее готовая к пилотированию** версия. Именно её поднимают на стенде и отдают на тестирование разработчику RX. Всё, что подтвердило свою полезность, живёт здесь |
| **`research/quality-followups-68`** | Эксперименты и проверка гипотез: замеры точности, правки промпта, эксперименты с сегментацией и порогами. Ломать здесь можно |
| **`prod-pilot`** | Ветка «на всякий случай». Иногда принимает изменения, сделанные прямо на тестовом стенде. Не источник истины: если она отстала от `main`, догонять её, а не наоборот |

### Правила

**Гипотеза подтвердилась в `research/…` → переносим в `main`.** Переносим **фичу**, а не всю
ветку: `git cherry-pick <хэш>` нужных коммитов. В экспериментальной ветке остаётся много
служебного — логи прогонов, отменённые попытки, промежуточные замеры, — и в `main` это не нужно.

**Гипотеза не подтвердилась → остаётся в ветке.** Не удалять: отрицательный результат тоже
знание. Пример — LLM-сегментация вопросов (`3041c36` и его revert `2534779`): она вылечила
недобор вопросов, но взамен создала перебор, и по замеру совпадение с эталоном упало с 65 % до
49 %. В `main` не пошла, разбор сохранён.

**Новая фича идёт под флагом, по умолчанию выключенным.** Так её можно влить в `main`, не меняя
поведение прода: `ENABLE_FULL_CLASSIFIER_FALLBACK`, `ENABLE_REPEAT_DETECTION`,
`ENABLE_WITHDRAWAL_DETECTION`. Включается в `.env` на конкретном стенде. `ENABLE_QUESTION_DEDUP`
из research-ветки сделан так же, но в `main` пока не перенесён.

**Перед мерджем в `main` — прогон тестов.** Ориентир: `python -m pytest tests/ -q --ignore=tests/e2e`.
Четыре падения (`test_candidate_rerank` ×3 и `test_get_current_user_accepts_correct_credentials`,
который зависит от пароля в локальном `.env`) — досборочные; появление пятого означает регресс
от вашей правки.

**`prod-pilot` синхронизируется из `main`.** Если она отстала и не содержит уникальных коммитов,
это fast-forward: `git push origin main:prod-pilot`. Проверить перед этим:
`git rev-list --count main..origin/prod-pilot` — ноль означает, что в ветке нет ничего своего.

обращения там жёсткая, 4000 символов.
