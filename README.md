# Агент классификации обращений граждан

Автоматическая классификация обращений граждан РФ по **59-ФЗ** и **Общероссийскому классификатору** (v4, 2108 позиций) для интеграции с Directum RX 25.3.

---

## Как работает агент

Когда гражданин пишет обращение — он пишет на живом разговорном языке: «у нас не вывозят мусор уже три недели», «яма на дороге», «хочу получить субсидию на ЖКХ». Государственный классификатор написан на формальном юридическом языке: «Обращение с твёрдыми коммунальными отходами», «Ремонт автомобильных дорог», «Оплата коммунальных услуг».

**Задача агента** — автоматически сопоставить живой текст обращения с нужной записью в классификаторе, определить вид обращения по 59-ФЗ и подготовить результат для проверки оператором.

### Общая схема работы

```
Текст обращения
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 1: Сегментация обращения                        │
│  Маркеры "1.", "во-первых", "также", абзацы          │
│  → N независимых вопросов (1 или больше)             │
└──────────────────────────────────────────────────────┘
       │
       ▼ (для каждого вопроса)
┌──────────────────────────────────────────────────────┐
│  ШАГ 2: Per-question retrieval                       │
│   ┌────────────────────────────────────────────┐     │
│   │ Dense поиск (e5-base + adapter_v3)         │     │
│   │ cosine similarity по 2108 записям → top-50 │     │
│   ├────────────────────────────────────────────┤     │
│   │ Lexical поиск (token overlap по name+path) │     │
│   │ → top-30, используется как фильтр пула     │     │
│   ├────────────────────────────────────────────┤     │
│   │ Чистый dense-ранкинг → top-50 в LLM        │     │
│   │ (heuristic reranker ОТКЛЮЧЁН: он ронял     │     │
│   │  recall@10 с 41.1% до 10.7%, см. Результаты)│    │
│   ├────────────────────────────────────────────┤     │
│   │ L1-diversity guard                         │     │
│   │ Если все кандидаты в 1 разделе → впрыск   │     │
│   │ из 2 других разделов (anti-cascade-error)  │     │
│   └────────────────────────────────────────────┘     │
│   * Dynamic cap: per_q_cap = max(8, 400 // n_q)      │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 3: LLM-классификация (один вызов)               │
│  Ario Qwen3.6-35B-A3B (MoE, 128K context)           │
│  Промпт: questions_with_candidates[] —               │
│  свой пул кандидатов на каждый вопрос                │
│  Правила: L3-тема → код, разграничения веток,        │
│  портфель альтернатив, no fallback-код               │
│  → vid, тип, code + alternatives (топ-3) per question│
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 4: Strict validation                            │
│  Код LLM вне кандидатов → подмена top-1 + conf ≤0.45 │
│  Один код на N>1 разных вопросов → conf ≤ 0.5        │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 5: Карточка оператора                           │
│  Основной код + топ-3 альтернативы + уверенность     │
│  → [ Подтвердить / Исправить / Отклонить ]           │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 6: Логирование и дообучение                     │
│  → appeals_log.jsonl                                 │
│  → при 50 верификациях: fine-tuning эмбеддера        │
└──────────────────────────────────────────────────────┘
```

Архитектура «retrieve → LLM» намеренна: dense retrieval сужает 2108 классов до top-50 релевантных, LLM делает финальный осмысленный выбор из узкого пула. Эвристический реранкер между этими стадиями **отключён по замерам** (v0.2, 2026-06-10): он выталкивал правильный код из top-10 (recall@10 41.1% → 10.7%) — чистый dense-ранкинг оказался лучше. На каждом вопросе отдельный пул кандидатов — это критично для многовопросных обращений (см. ниже).

## Шаг 1 — Сегментация обращения

Гражданин часто пишет несколько вопросов в одном обращении. До классификации текст разбивается на отдельные вопросы детерминистическим сегментатором:

| Тип маркера | Примеры |
|---|---|
| Нумерация | `1.`, `2)`, `3 -` в начале строки |
| Вербальные | «во-первых», «во-вторых», «кроме того», «также прошу» |
| Маркированный список | `•`, `*`, `-` |
| Абзацы с verb-индикаторами | пустая строка + новый абзац с глаголом-просьбой |

**Конкретный пример (реальное обращение из эксплуатации):**

```
Заявитель повторно обращается!!

1.Необходима доставка лекарств на дом (инсулин).
2. О бесплатном социальном работнике для слабовидящей.
3. Об оказании помощи в настройке телефона.

Яну сняли с группы инвалидности в поликлинике № 5.
У внука даже нет проездного.
```

Сегментатор находит **5 вопросов** (3 нумерованных + 2 абзаца с verb-индикаторами «сняли» и «проездного»). Преамбула «Заявитель повторно обращается» без verb-маркера склеивается с первым вопросом.

Если в обращении нет маркеров — возвращается один сегмент. Conservative-by-default.

## Шаг 2 — Per-question retrieval

Для **каждого** выявленного вопроса отдельно выполняется гибридный поиск. Это критично: однократный поиск по полному тексту 5-вопросного обращения возвращает нерелевантные коды, потому что доминирующий контекст («Защитник Отечества», «повторно обращается») перебивает реальные темы.

### Dense (семантический) поиск

Перед первым запуском `build_vectordb.py` векторизует все 2108 записей классификатора:

```
"Ремонт автомобильных дорог"  →  [0.12, -0.43, 0.87, ..., 0.21]  (768 чисел)
"Обращение с ТКО"             →  [0.34,  0.11, 0.22, ..., -0.05]  (768 чисел)
```

При поступлении вопроса агент превращает его в вектор и сравнивает с 2108 через **косинусное сходство**:

```python
similarities = embeddings_matrix @ query_vector   # одна строка
```

Модель `multilingual-e5-base` понимает **смысл**, а не буквальные совпадения слов:

| Текст вопроса | Найдено в классификаторе |
|---|---|
| «не вывозят мусор» | «Обращение с твёрдыми коммунальными отходами» |
| «яма на дороге» | «Ремонт автомобильных дорог» |
| «пожаловаться на полицию» | «Органы внутренних дел. Полиция» |

### Lexical (BM25-like) поиск

Параллельно — токенизация русского текста с нормализацией суффиксов, поиск по `name` и `full_path` каждой записи классификатора. Лечит случаи, где dense embedding не знает специфичной классификаторной лексики («детсад» → embedding слабо матчит «Дошкольное образование. Поступление детей в МДОУ»).

### Heuristic reranker — ОТКЛЮЧЁН по умолчанию (2026-06-10)

Классификатор имеет 4-уровневую иерархию (**L1=5 разделов, L2=21 подраздел, L3=206, L4=1225, L5=651**). Ранее между retrieval и LLM работал эвристический реранкер (merge с lexical-пулом + branch agreement boost + parent similarity boost). На ранних синтетических фикстурах он давал +9 pp Top-1, но замер на реальном датасете ii25_test показал обратное:

| Метрика | Чистый dense | После реранкера |
|---|---:|---:|
| recall@10 (точный код) | **41.1%** | 10.7% |
| recall@10 (L3-тема) | **71.4%** | 30.4% |

Merge с lexical-пулом и иерархические бусты систематически выталкивали правильный код из top-10 — 56% всех ошибок пайплайна приходилось на эту стадию. Реранкер отключён флагом `ENABLE_HEURISTIC_RERANKER=false`: LLM получает чистый dense top-50, lexical-пул используется только как фильтр. Эффект: Top-1 14.3% → 21.4% одним флагом (см. Результаты).

### Опционально (по флагам, default OFF)

- **Heuristic reranker** (`ENABLE_HEURISTIC_RERANKER=true`) — вернуть старое поведение (merge + бусты), см. выше почему выключен.
- **CrossEncoder reranker** (`ENABLE_CROSS_ENCODER_RERANKER=true`) — модель `BAAI/bge-reranker-base` смотрит пары `(query, candidate)` и пересортирует top-30. Готово к использованию когда придёт расширенная разметка.
- **LLM Query Expansion** (`ENABLE_QUERY_EXPANSION=true`) — быстрый LLM-вызов переформулирует вопрос в терминах классификатора («хочу в детский сад» → «Дошкольное образование, поступление детей в МДОУ, очередь») перед retrieval.

## Шаг 3 — Классификация через LLM

Агент передаёт в **LLM** текст обращения и структуру `questions_with_candidates[]` — для каждого вопроса свой пул из топ-50 (dynamic cap при многовопросных). Модель рассматривает: что именно просит гражданин, какой код из ПУЛА ЭТОГО ВОПРОСА подходит точнее.

**4 провайдера на выбор:**

| Провайдер | Модель | Примечание |
|-----------|--------|------------|
| **Ario** (основной) | `Qwen/Qwen3.6-35B-A3B` | Корпоративный Directum360, MoE 128K |
| **Groq** | `llama-3.3-70b-versatile` | Быстрый, хороший русский |
| **Gemini** | `gemini-2.5-flash` | Бесплатно, лимит 20 req/day |
| **Ollama** | `qwen2.5-14b` | Локально, без лимитов |

**Ключевые правила в промпте (v3, 2026-06-10):**
- Двухэтапный выбор: сначала L3-тема из `l3_options`, затем конкретный код внутри неё
- Для каждого вопроса код выбирается ТОЛЬКО из его собственного пула кандидатов
- Запрещён fallback-код `0001.0002.0027.0126` («Отсутствует адресат обращения») если есть хоть один тематически подходящий кандидат
- Запрещён один код на разные темы (защита от вырождения)
- Типовые разграничения соседних веток: строительство 0096 vs благоустройство 0097; соцобеспечение 0007 vs медицина 0014; семья 0004 vs образование 0013; **ЖКХ 0005.0005.0056 vs инфраструктура поселений 0003.0009.0097** (внутри дома/УК → ЖКХ; сети поселения → 0097); **автодороги 0099 vs дворы 0097** (улицы и их расчистка → 0099; придомовые территории → 0097)
- Портфель альтернатив: сосед по той же L3-теме (страхует ошибку кода) + лучший код из другой правдоподобной L3 (страхует ошибку темы) + родитель/уточнение
- Детерминированный guard в коде: если LLM выбрала L5-уточнение — его L4-родитель автоматически добавляется в альтернативы

Пример ответа:

```json
{
  "vid_obrascheniya": "Жалоба",
  "tip_obrascheniya": "Индивидуальное",
  "questions": [
    {
      "ordinal": 1,
      "question_text": "Не производится вывоз мусора",
      "selected_code": "0005.0005.0056.1160",
      "predmet_vedeniya": "Вопрос местного значения",
      "confidence": 0.87,
      "reasoning": "Обращение касается нарушения графика вывоза ТКО управляющей компанией"
    }
  ]
}
```

### Несколько вопросов в одном обращении

Агент автоматически выявляет и классифицирует каждый вопрос отдельно с per-question retrieval:

```
"1. Доставка лекарств на дом (инсулин).
 2. О бесплатном социальном работнике.
 3. Цифровая грамотность для пенсионера.
 Сняли с группы инвалидности.
 У внука нет проездного."

→ Вопрос 1: 0002.0014.0143.0422 — Лекарственные препараты (90%)
→ Вопрос 2: 0002.0007.0073.0295 — Социальное обслуживание (85%)
→ Вопрос 3: 0003.0009.0100.0761 — Развитие цифрового вещания (80%)
→ Вопрос 4: 0002.0007.0070.0281 — Установление группы инвалидности (МСЭ) (85%)
→ Вопрос 5: 0002.0007.0074.0320 — Проезд льготных категорий граждан (80%)
```

Это реальный кейс из эксплуатации. До добавления сегментации все 5 вопросов получали один fallback-код «Отсутствует адресат обращения».

## Шаг 4 — Strict validation

После LLM-ответа агент проверяет каждый выбранный код:

| Нарушение | Действие |
|---|---|
| Код LLM вне списка кандидатов своего вопроса | Подмена на top-1 кандидата + `confidence ≤ 0.45` |
| Один и тот же код на >1 вопросов с разными темами | Принудительно `confidence ≤ 0.5` + флаг верификации |

Это защищает от двух классов LLM-ошибок: «галлюцинации» кода и «ленивого» fallback на универсальный код.

---

## Шаг 5 — Карточка для оператора

Каждый результат показывается оператору с уровнем уверенности. Если уверенность ниже 65% — появляется флаг верификации.

```
╔══ РЕЗУЛЬТАТ КЛАССИФИКАЦИИ ИИ ══
║ Вид обращения:    Жалоба
║ Тип обращения:    Индивидуальное
║ Уверенность:      87%
║ ────────────────────────────────────────
║ Код:              0005.0005.0056.1160
║ Наименование:     Обращение с твёрдыми коммунальными отходами
║ Предмет ведения:  Вопрос местного значения
║ Обоснование:      Нарушение графика вывоза ТКО управляющей компанией
╚══════════════════════════════════
   [ ПОДТВЕРДИТЬ ]  [ ИСПРАВИТЬ ]  [ ОТКЛОНИТЬ ]
```

**Предмет ведения** определяет уровень власти, к компетенции которого относится вопрос: местное самоуправление, региональные или федеральные органы власти.

## Шаг 6 — Логирование и дообучение

Каждая верификация оператора накапливается в `data/appeals_log.jsonl` и становится обучающими данными:

| Действие | Обучающий сигнал |
|---|---|
| Подтвердить | (текст, код агента) → позитивная пара |
| Исправить | (текст, код оператора) → позитивная; (текст, код агента) → негативная |
| Отклонить | исключается из обучения |

При накоплении 50 верификаций агент предлагает запустить дообучение эмбеддинговой модели.

### Механизм аннотаций (EPIC-06)

При выборе «Исправить» оператор добавляет **пояснение** — в каких случаях применяется выбранный код. Это пояснение сохраняется в `data/classifier_annotations.json` и используется при следующем fine-tuning для улучшения качества эмбеддингов.

### Загрузка исторических данных (EPIC-07)

Альтернативный путь дообучения — загрузка исторических данных от заказчика (обращения + код, присвоенный специалистом). Три источника данных:

| Источник | Описание |
|---|---|
| **Веб-интерфейс** | Загрузка через http://localhost:8000/static/historical.html |
| **Папка** | Копирование файлов в `data/historical/` |
| **Directum API** | Автоматический импорт (future) |

Поддерживаемые форматы: `.xlsx`, `.xls`, `.csv`, `.json`

После загрузки файл валидируется — коды проверяются по классификатору. Оператор видит результат и подтверждает сохранение. Сохранённые записи используются для fine-tuning:

```bash
# Fine-tuning только на исторических данных
python src/finetune_model.py --source historical

# Комбинированный (исторические + верифицированные, 3x вес для исторических)
python src/finetune_model.py --source combined
```

Автоматический импорт из папки:
```bash
python src/auto_import_historical.py              # однократная обработка
python src/auto_import_historical.py --watch     # слежение за папкой
```

## Результаты оценки точности

### ИИ25 dataset — основной бенчмарк (56 test-кейсов)

Источник: `data/ii25_test.jsonl` — 56 реальных обращений с разметкой от специалистов.  
Распределение по разделам: Раздел 1=2 | 2=24 | **3=45** | 4=6 | 5=22 (доминирует Раздел 3 — Экономика).

#### Смысловые метрики — главные (по итогам CustDev, 2026-06-10)

CustDev в 3 регионах (ПУР, ПТО, АВО) показал: заказчику не критичен точный номер вопроса —
критично смысловое попадание («Если вопросы выделены по смыслу, не критично, если они разных
номеров»). Поэтому основные метрики проекта — совпадение ветки классификатора (L2/L3) и Top-3
(оператор выбирает из основного кода + 2-3 альтернатив). Подробно: [docs/semantic_metric_report.md](docs/semantic_metric_report.md).

**Актуальный baseline v0.5 (реранкер откл. + промпт v3 + L4-parent guard):**

| Метрика | Значение | Смысл |
|---|---:|---|
| Top-1 точный код | **26.8%** | строгое совпадение |
| Top-1 L3 тема | **57.1%** | правильная тема |
| Top-1 L2 тематика | **71.4%** | правильная тематика |
| **Top-3 точный код** | **51.8%** | золото среди top-1 + альтернатив |
| **Top-3 L3 тема** | **75.0%** | оператор видит правильную тему |
| **Top-3 L2 тематика** | **80.4%** | 4 из 5 обращений |

**Валидация Заказчика (июль 2026):** на выборке из 12 обращений Заказчик подтвердил
корректность Top-1 классификации по всем 12. Выборка типовых обращений; ii25_test
содержит более сложный длинный хвост.

#### История улучшений Top-1 (end-to-end с LLM)

| Конфигурация | Top-1 | Дата |
|---|---:|---|
| Phase 0: e5+adapter_v3 + Qwen3-32B | 7.1% | 2026-05-27 |
| v0.1.minimal: RAG+LLM, без доп. техник | 14.3% | 2026-05-29 |
| v0.2: + отключён heuristic reranker | 21.4% | 2026-06-10 |
| **v0.5: + промпт v3 + L4-parent guard** | **26.8%** | 2026-06-10 |

**Выводы:** (1) все «тяжёлые» техники (section routing, CE, LtR, MQE, heuristic reranker)
на реальном датасете ухудшают результат — чистая RAG+LLM архитектура лучшая;
(2) самый большой прирост дало отключение вредного реранкера (+7.1 пп одним флагом).

#### Retrieval метрики (e5-base + adapter_v3, без LLM)

| Метрика | Значение |
|---|---:|
| **Dense recall@10** (точный код) | **41.1%** |
| **Dense recall@50** (точный код) | **69.6%** |
| Dense recall@10 (L3-тема) | 71.4% |
| Dense recall@50 (L3-тема) | 80.4% |

#### Распределение причин ошибок (v0.5, 56 кейсов)

```
      correct    │███████░░░░░░░░░░░░░░░░░ 15/56 (27%) — Top-1 правильный
retrieval_recall │████████░░░░░░░░░░░░░░░░ 17/56 (30%) — gold нет даже в dense top-50
    llm_final    │███████████░░░░░░░░░░░░░ 24/56 (43%) — gold в top-50, LLM выбрал другой
```

**Текущий bottleneck:** retrieval_recall (30%) — потолок эмбеддера, атакуется только
fine-tune (Phase 6). Зона llm_final частично компенсируется alternatives:
в 14 из 24 таких кейсов правильный код есть в Top-3 оператора.

#### Сравнение embedding-моделей (retrieval-only)

| Модель | recall@10 | recall@50 |
|---|---:|---:|
| **e5-base + adapter_v3** (domain-tuned) | **41.1%** | **69.6%** |
| BGE-M3 off-the-shelf | 33.9% (-7.2pp) | 55.4% (-14.2pp) |

adapter_v3 = 4 МБ линейный адаптер, обученный на PTO+ii25_train данных домена.  
BGE-M3 = 1.5 ГБ general-purpose, нужен LoRA fine-tune для конкуренции.

## Новые возможности (обновлено 2026-08-11)

### Full-classifier fallback — второй проход по всему классификатору (2026-07)

Если ретривер промахнулся — в пуле кандидатов нет подходящей тематической ветки — агент делает
повторный LLM-проход, показывая модели **весь классификатор** (листья L4+L5, ~61k токенов)
вместо узкого пула.

Триггер: флаг LLM `candidates_insufficient` **или** max cosine similarity топ-кандидата ниже
`FULL_FALLBACK_SIM_THRESHOLD`. Цена — один тяжёлый вызов, и только при промахе. В ответе API
появляется поле `full_fallback_used`.

Порог **модель-специфичен**: у адаптированной e5 similarity топ-1 лежит в районе 0.15–0.35
(а не 0.8+, как у «чистой» e5), поэтому в проде стоит 0.15. При завышенном пороге фоллбэк
срабатывает на каждом обращении.

### Детекция повторного обращения → код `0001.0002.0027.0125`

Если из текста видно, что гражданин обращается не впервые («обращаюсь повторно», «ответа так и
не получил», «ранее обращался»), к результату добавляется **дополнительный** вопрос с кодом
«Результаты рассмотрения обращения». Тематическая классификация сохраняется.

Флаг `ENABLE_REPEAT_DETECTION`.

### Детекция просьбы прекратить рассмотрение → код `0001.0002.0027.0131`

Просьба отозвать обращение, прекратить рассмотрение или снять с рассмотрения («Отмена
обращения», «Прошу прекратить рассмотрение», «Отзыв обращения», «Отменяю заявление») → код
«Прекращение рассмотрения обращения» ставится **первым**: процедурное решение важнее тематики,
а тематический код остаётся дополнительным вопросом.

Маркеры требуют объекта действия (обращение/заявление/письмо/жалоба/запрос), поэтому «прошу
прекратить незаконное строительство», «отозвать лицензию» и «отмена автобусного маршрута» **не**
срабатывают. Флаг `ENABLE_WITHDRAWAL_DETECTION`.

**Как работают обе детекции.** Два независимых канала, объединённых по ИЛИ: regex-маркеры по
тексту (детерминированно, по **полному** тексту — в LLM обращение уходит обрезанным до 4000
символов) и флаг LLM (`is_repeat_appeal` / `is_withdrawal_request`). Срабатывают как
пост-обработка после классификации, а код берётся **напрямую из индекса классификатора, а не из
пула кандидатов** — поэтому работают даже когда векторный поиск не поднял нужный код в топ.
Уверенность у такой карточки фиксированная (0.9), в служебные причины пишется
`repeat_appeal_detected` / `withdrawal_request_detected`.

### Точность ×1.9 за счёт отключения реранкера и промпта v3 (2026-06-10)

Диагностика по per-case eval показала: эвристический реранкер — источник 56% ошибок.
Проведён цикл из 4 замеров (v0.2–v0.5): отключение реранкера (+7.1 пп Top-1), два новых
типовых разграничения в промпте, портфель альтернатив, детерминированный L4-parent guard.
Итог: Top-1 14.3% → 26.8%, Top-3 точный код 51.8%, Top-3 L2 80.4%.
Введены смысловые метрики (L2/L3-match) как основные — по итогам CustDev.
Подробно: [docs/semantic_metric_report.md](docs/semantic_metric_report.md).

### L1-diversity guard — защита от cascade error

Если retrieval возвращает пул, где все кандидаты принадлежат одному L1-разделу, агент автоматически «впрыскивает» кандидатов из двух других разделов.

**Почему это важно:** Неправильный L1 на этапе retrieval → LLM видит только один раздел → выбирает «лучшее из плохого» вместо правильного. Пример: обращение про полёты дронов над объектами попало в «Оборона и безопасность», хотя правильный код — в «Воздушный транспорт».

### Dynamic candidate cap

```python
per_q_cap = max(8, min(TOP_K, 400 // n_q))
```

При 5 вопросах в обращении каждый вопрос получает cap 80 кандидатов (или TOP_K если меньше). Защищает контекст LLM от переполнения при любом количестве вопросов.

### Топ-3 альтернативы (портфельное правило)

LLM возвращает `alternative_codes` для каждого вопроса — 2-3 кода, покрывающих разные типы возможной ошибки: сосед по той же L3-теме + код из другой правдоподобной ветки + родитель/уточнение. Если выбран L5-код, его L4-родитель добавляется детерминированно в коде. Отображаются оператору как подсказка: в v0.5 alternatives спасают 14 из 24 кейсов, где Top-1 ошибся при правильном кандидате в пуле.

### Обновлённая LLM — Qwen3.6-35B-A3B

Ario перешёл на новую модель: `Qwen/Qwen3.6-35B-A3B` (MoE архитектура, 128K контекст). По сравнению с предыдущим `Qwen3-32B-AWQ`:
- Контекст 32K → 128K (нет переполнения при 5+ вопросах)
- MoE: active params ~3.8B при inference → примерно в 3-4x быстрее
- Устранена причина 400 Bad Request ошибок на длинных многовопросных обращениях

## Технический стек

| Компонент | Технология |
|---|---|
| Языковая модель (основная) | **Ario** — `Qwen/Qwen3.6-35B-A3B` (MoE, 128K контекст, ~3.8x быстрее Qwen3-32B) |
| Языковая модель (альтернативы) | **Groq** `llama-3.3-70b-versatile`, **Gemini** `gemini-2.5-flash`, **Ollama** `qwen2.5-14b` |

| Lexical поиск | Token overlap с нормализацией русских суффиксов |
| Reranker | Heuristic: lexical + level + hierarchy boosts (branch agreement + parent similarity) |
| L1-diversity guard | Anti-cascade-error: впрыск кандидатов из других L1-разделов при монотонном пуле |
| Dynamic candidate cap | `per_q_cap = max(8, min(TOP_K, 400 // n_q))` — защита от overflow 128K контекста |
| Alternatives | LLM возвращает топ-3 альтернативных кода с confidence для каждого вопроса |
| Сегментация | Детерминистические regex-маркеры (`1.`, «во-первых», абзацы) |
| API | FastAPI + uvicorn |
| Текст из PDF | PyMuPDF |
| Дообучение | sentence-transformers, MultipleNegativesRankingLoss |
