# Агент классификации обращений граждан

Автоматическая классификация обращений граждан РФ по **59-ФЗ** и **Общероссийскому классификатору** (v4, 2108 позиций) для интеграции с Directum RX 25.3.

---

## Как работает агент

Когда гражданин пишет обращение — он пишет на живом разговорном языке: «у нас не вывозят мусор уже три недели», «яма на дороге», «хочу получить субсидию на ЖКХ». Государственный классификатор написан на формальном юридическом языке: «Обращение с твёрдыми коммунальными отходами», «Ремонт автомобильных дорог», «Оплата коммунальных услуг».

**Задача агента** — автоматически сопоставить живой текст обращения с нужной записью в классификаторе, определить вид обращения по 59-ФЗ и подготовить результат для проверки оператором.

### Общая схема работы

```
Текст обращения
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 1: Сегментация обращения                        │
│  Маркеры "1.", "во-первых", "также", абзацы          │
│  → N независимых вопросов (1 или больше)             │
└──────────────────────────────────────────────────────┘
       │
       ▼ (для каждого вопроса параллельно)
┌──────────────────────────────────────────────────────┐
│  ШАГ 2: Per-question retrieval                       │
│   ┌────────────────────────────────────────────┐     │
│   │ Dense поиск (multilingual-e5-base)         │     │
│   │ cosine similarity по 2108 записям → top-50 │     │
│   ├────────────────────────────────────────────┤     │
│   │ Lexical поиск (token overlap по name+path) │     │
│   │ → top-30                                   │     │
│   ├────────────────────────────────────────────┤     │
│   │ Merge + Heuristic rerank                   │     │
│   │ Hierarchy boost (см. ниже) → top-10        │     │
│   ├────────────────────────────────────────────┤     │
│   │ (опц.) CrossEncoder reranker               │     │
│   │ (опц.) LLM Query Expansion                 │     │
│   └────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 3: LLM-классификация (один вызов)               │
│  Промпт: questions_with_candidates[] —               │
│  свой пул кандидатов на каждый вопрос                │
│  Правила: no fallback-код, sibling-aware, deeper>L1  │
│  → vid, тип, codes per question                      │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 4: Strict validation                            │
│  Код LLM вне кандидатов → подмена top-1 + conf ≤0.45 │
│  Один код на N>1 разных вопросов → conf ≤ 0.5        │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 5: Карточка оператора                           │
│  → [ Подтвердить / Исправить / Отклонить ]           │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│  ШАГ 6: Логирование                                  │
│  → appeals_log.jsonl                                 │
│  → при 50 верификациях: fine-tuning эмбеддера        │
└──────────────────────────────────────────────────────┘
```

Архитектура «retrieve → rerank → LLM» намеренна: hybrid retrieval (dense + lexical + иерархия) сужает 2108 классов до 10 релевантных, LLM делает финальный осмысленный выбор из узкого пула. На каждом вопросе отдельный пул кандидатов — это критично для многовопросных обращений (см. ниже).

## Шаг 1 — Сегментация обращения

Гражданин часто пишет несколько вопросов в одном обращении. До классификации текст разбивается на отдельные вопросы детерминистическим сегментатором:

| Тип маркера | Примеры |
|---|---|
| Нумерация | `1.`, `2)`, `3 -` в начале строки |
| Вербальные | «во-первых», «во-вторых», «кроме того», «также прошу» |
| Маркированный список | `•`, `*`, `-` |
| Абзацы с verb-индикаторами | пустая строка + новый абзац с глаголом-просьбой |

**Конкретный пример (реальное обращение из эксплуатации):**

```
Заявитель повторно обращается!!

1.Необходима доставка лекарств на дом (инсулин).
2. О бесплатном социальном работнике для слабовидящей.
3. Об оказании помощи в настройке телефона.

Яну сняли с группы инвалидности в поликлинике № 5.
У внука даже нет проездного.
```

Сегментатор находит **5 вопросов** (3 нумерованных + 2 абзаца с verb-индикаторами «сняли» и «проездного»). Преамбула «Заявитель повторно обращается» без verb-маркера склеивается с первым вопросом.

Если в обращении нет маркеров — возвращается один сегмент. Conservative-by-default.

## Шаг 2 — Per-question retrieval

Для **каждого** выявленного вопроса отдельно выполняется гибридный поиск. Это критично: однократный поиск по полному тексту 5-вопросного обращения возвращает нерелевантные коды, потому что доминирующий контекст («Защитник Отечества», «повторно обращается») перебивает реальные темы.

### Dense (семантический) поиск

Перед первым запуском `build_vectordb.py` векторизует все 2108 записей классификатора:

```
"Ремонт автомобильных дорог"  →  [0.12, -0.43, 0.87, ..., 0.21]  (768 чисел)
"Обращение с ТКО"             →  [0.34,  0.11, 0.22, ..., -0.05]  (768 чисел)
```

При поступлении вопроса агент превращает его в вектор и сравнивает с 2108 через **косинусное сходство**:

```python
similarities = embeddings_matrix @ query_vector   # одна строка
```

Модель `multilingual-e5-base` понимает **смысл**, а не буквальные совпадения слов:

| Текст вопроса | Найдено в классификаторе |
|---|---|
| «не вывозят мусор» | «Обращение с твёрдыми коммунальными отходами» |
| «яма на дороге» | «Ремонт автомобильных дорог» |
| «пожаловаться на полицию» | «Органы внутренних дел. Полиция» |

### Lexical (BM25-like) поиск

Параллельно — токенизация русского текста с нормализацией суффиксов, поиск по `name` и `full_path` каждой записи классификатора. Лечит случаи, где dense embedding не знает специфичной классификаторной лексики («детсад» → embedding слабо матчит «Дошкольное образование. Поступление детей в МДОУ»).

### Hierarchy-aware reranking ⚡

Классификатор имеет 4-уровневую иерархию (**L1=5 разделов, L2=21 подраздел, L3=206, L4=1225, L5=651**). Reranker использует три структурных сигнала:

1. **Branch agreement boost** — если в пуле несколько кандидатов из одной L2-ветки, их «масса похожести» суммируется и буст распределяется пропорционально. Это поднимает в top-10 правильный leaf-код даже когда сам он не сильно похож на запрос, но соседи по ветке похожи.

2. **Parent similarity boost** — если родительский код (L3 для L4-leaf) тоже найден в пуле с высоким score → буст. Сигнал «модель уверена в ветке».

3. **L1-pruning (опционально)** — если 1-2 раздела составляют ≥70% массы похожести, отсекаем кандидатов из других разделов.

**Эффект на eval:** ex06 (детский сад) — раньше правильный код вообще не попадал в top-50 dense. После branch agreement ветка «Дошкольное образование» подтянулась в top-10 и LLM выбрал правильный leaf. **Top-1 +9 pp.**

### Опционально (по флагам)

- **CrossEncoder reranker** (`ENABLE_CROSS_ENCODER_RERANKER=true`) — модель `BAAI/bge-reranker-base` смотрит пары `(query, candidate)` и пересортирует top-30. Готово к использованию когда придёт расширенная разметка.
- **LLM Query Expansion** (`ENABLE_QUERY_EXPANSION=true`) — быстрый LLM-вызов переформулирует вопрос в терминах классификатора («хочу в детский сад» → «Дошкольное образование, поступление детей в МДОУ, очередь») перед retrieval.

## Шаг 3 — Классификация через LLM

Агент передаёт в **LLM** текст обращения и структуру `questions_with_candidates[]` — для каждого вопроса свой пул из топ-10. Модель рассматривает: что именно просит гражданин, какой код из ПУЛА ЭТОГО ВОПРОСА подходит точнее.

**4 провайдера на выбор:**

| Провайдер | Модель | Примечание |
|-----------|--------|------------|
| **Groq** (основной) | `llama-3.3-70b-versatile` | Быстрый, хороший русский |
| **Gemini** | `gemini-2.5-flash` | Бесплатно, лимит 20 req/day |
| **Ollama** | `qwen2.5-14b` | Локально, без лимитов |
| **Ario** | `Qwen/Qwen3-32B-AWQ` | Корпоративный Directum360 |

**Ключевые правила в промпте:**
- Для каждого вопроса код выбирается ТОЛЬКО из его собственного пула кандидатов
- Запрещён fallback-код `0001.0002.0027.0126` («Отсутствует адресат обращения») если есть хоть один тематически подходящий кандидат
- Запрещён один код на разные темы (защита от вырождения)
- Sibling-aware: если в пуле несколько кодов с одинаковым родителем — внимательно прочитать `name` каждого и выбрать ТОЧНО соответствующий формулировке
- Предпочтение deeper leaf (L4-L5) над общим (L1-L3) при прочих равных

Пример ответа:

```json
{
  "vid_obrascheniya": "Жалоба",
  "tip_obrascheniya": "Индивидуальное",
  "questions": [
    {
      "ordinal": 1,
      "question_text": "Не производится вывоз мусора",
      "selected_code": "0005.0005.0056.1160",
      "predmet_vedeniya": "Вопрос местного значения",
      "confidence": 0.87,
      "reasoning": "Обращение касается нарушения графика вывоза ТКО управляющей компанией"
    }
  ]
}
```

### Несколько вопросов в одном обращении

Агент автоматически выявляет и классифицирует каждый вопрос отдельно с per-question retrieval:

```
"1. Доставка лекарств на дом (инсулин).
 2. О бесплатном социальном работнике.
 3. Цифровая грамотность для пенсионера.
 Сняли с группы инвалидности.
 У внука нет проездного."

→ Вопрос 1: 0002.0014.0143.0422 — Лекарственные препараты (90%)
→ Вопрос 2: 0002.0007.0073.0295 — Социальное обслуживание (85%)
→ Вопрос 3: 0003.0009.0100.0761 — Развитие цифрового вещания (80%)
→ Вопрос 4: 0002.0007.0070.0281 — Установление группы инвалидности (МСЭ) (85%)
→ Вопрос 5: 0002.0007.0074.0320 — Проезд льготных категорий граждан (80%)
```

Это реальный кейс из эксплуатации. До добавления сегментации все 5 вопросов получали один fallback-код «Отсутствует адресат обращения».

## Шаг 4 — Strict validation

После LLM-ответа агент проверяет каждый выбранный код:

| Нарушение | Действие |
|---|---|
| Код LLM вне списка кандидатов своего вопроса | Подмена на top-1 кандидата + `confidence ≤ 0.45` |
| Один и тот же код на >1 вопросов с разными темами | Принудительно `confidence ≤ 0.5` + флаг верификации |

Это защищает от двух классов LLM-ошибок: «галлюцинации» кода и «ленивого» fallback на универсальный код.

## Шаг 5 — Карточка для оператора

Каждый результат показывается оператору с уровнем уверенности. Если уверенность ниже 65% — появляется флаг верификации.

```
╔══ РЕЗУЛЬТАТ КЛАССИФИКАЦИИ ИИ ══
║ Вид обращения:    Жалоба
║ Тип обращения:    Индивидуальное
║ Уверенность:      87%
║ ────────────────────────────────────────
║ Код:              0005.0005.0056.1160
║ Наименование:     Обращение с твёрдыми коммунальными отходами
║ Предмет ведения:  Вопрос местного значения
║ Обоснование:      Нарушение графика вывоза ТКО управляющей компанией
╚══════════════════════════════════
   [ ПОДТВЕРДИТЬ ]  [ ИСПРАВИТЬ ]  [ ОТКЛОНИТЬ ]
```

**Предмет ведения** определяет уровень власти, к компетенции которого относится вопрос: местное самоуправление, региональные или федеральные органы власти.

## Шаг 6 — Логирование и дообучение

Каждая верификация оператора накапливается в `data/appeals_log.jsonl` и становится обучающими данными:

| Действие | Обучающий сигнал |
|---|---|
| Подтвердить | (текст, код агента) → позитивная пара |
| Исправить | (текст, код оператора) → позитивная; (текст, код агента) → негативная |
| Отклонить | исключается из обучения |

При накоплении 50 верификаций агент предлагает запустить дообучение эмбеддинговой модели.

### Механизм аннотаций (EPIC-06)

При выборе «Исправить» оператор добавляет **пояснение** — в каких случаях применяется выбранный код. Это пояснение сохраняется в `data/classifier_annotations.json` и используется при следующем fine-tuning для улучшения качества эмбеддингов.

### Загрузка исторических данных (EPIC-07)

Альтернативный путь дообучения — загрузка исторических данных от заказчика (обращения + код, присвоенный специалистом). Три источника данных:

| Источник | Описание |
|---|---|
| **Веб-интерфейс** | Загрузка через http://localhost:8000/static/historical.html |
| **Папка** | Копирование файлов в `data/historical/` |
| **Directum API** | Автоматический импорт (future) |

Поддерживаемые форматы: `.xlsx`, `.xls`, `.csv`, `.json`

После загрузки файл валидируется — коды проверяются по классификатору. Оператор видит результат и подтверждает сохранение. Сохранённые записи используются для fine-tuning:

```bash
# Fine-tuning только на исторических данных
python src/finetune_model.py --source historical

# Комбинированный (исторические + верифицированные, 3x вес для исторических)
python src/finetune_model.py --source combined
```

Автоматический импорт из папки:
```bash
python src/auto_import_historical.py              # однократная обработка
python src/auto_import_historical.py --watch     # слежение за папкой
```

## Быстрый старт

### Шаг 1 — Получить бесплатный ключ Groq

Groq — облачный сервис для запуска языковых моделей. Ключ бесплатный и не требует банковской карты.

1. Перейди на https://console.groq.com/keys
2. Зарегистрируйся (через Google или email)
3. Нажми **«Create API Key»** → задай любое имя
4. Скопируй ключ — он начинается с `gsk_...`

> ⚠️ Ключ показывается только один раз. Сохрани его сразу.

> Альтернатива — Google Gemini (бесплатно, но лимит 20 req/day). Ключ: https://ai.google.dev/ — затем переключи `LLM_PROVIDER=gemini` в `.env`.

### Шаг 2 — Установка (один раз)

Двойной клик по **`install.bat`** — скрипт сам проведёт по всем шагам:

1. Проверит Python 3.11
2. Создаст виртуальное окружение (`venv`)
3. Установит зависимости
4. **Запросит `GROQ_API_KEY`** и сохранит его в `.env` автоматически
5. Построит векторную базу (~5–15 минут при первом запуске)

```
[4/5] Checking .env configuration...
   GROQ_API_KEY not configured.

   Get your free key at: https://console.groq.com/keys
   Sign up via Google or email -- no credit card needed.
   The key looks like: gsk_xxxxxxxxxxxxxxxxxxxx

   Enter GROQ_API_KEY: █
```

> Если `.env` уже содержит валидный ключ — шаг с запросом пропускается автоматически.

Или через PowerShell:
```powershell
cd "C:\путь\до\папки\Class OG Final"
.\setup.ps1
```

### Шаг 3 — Запуск

Двойной клик по **`launch.bat`** → выбрать режим:

```
[1] Run tests          — проверить что агент работает
[2] Classify manually  — ввести текст обращения вручную
[3] Start API server   — REST API на порту 8000
[4] Operator mode      — верификация + дообучение
[5] Select LLM model   — выбор провайдера LLM (Groq/Gemini/Ollama/Ario)
```

## Требования

- **Python 3.11** (не 3.12+, не 3.14)
- Файл `.env` с ключом `GROQ_API_KEY` (бесплатно: https://console.groq.com/keys)
- ~500 МБ дискового пространства (модель эмбеддингов + векторная база)

## Технический стек

| Компонент | Технология |
|---|---|
| Языковая модель | **Groq** — `llama-3.3-70b-versatile` (основной), **Gemini** `gemini-2.5-flash` (альтернатива), **Ollama** `qwen2.5-14b` (локальный), **Ario** `Qwen/Qwen3-32B-AWQ` (корпоративный Directum360) |
| Эмбеддинги | `intfloat/multilingual-e5-base` (локально) |
| Векторный поиск | numpy cosine similarity |
| Lexical поиск | Token overlap с нормализацией русских суффиксов |
| Reranker | Heuristic (lexical + level + hierarchy boosts) + опц. CrossEncoder `BAAI/bge-reranker-base` |
| Сегментация | Детерминистические regex-маркеры (`1.`, «во-первых», абзацы) |
| API | FastAPI + uvicorn |
| Текст из PDF | PyMuPDF |
| Дообучение | sentence-transformers, MultipleNegativesRankingLoss |

Переключение провайдера: `LLM_PROVIDER=groq`, `gemini`, `ollama` или `ario` в `.env`.

### Конфигурация retrieval/rerank (опционально в `.env`)

```bash
# Размеры пулов
RETRIEVAL_POOL_SIZE=50        # dense top-N
LEXICAL_POOL_SIZE=30          # lexical top-N
TOP_K_CANDIDATES=10           # финал — что уходит в LLM
MIN_CONFIDENCE=0.65           # ниже — флаг верификации

# Веса в combined_score reranker
LEXICAL_RERANK_WEIGHT=0.12    # вклад lexical
HIERARCHY_BRANCH_WEIGHT=0.05  # branch agreement (L2)
HIERARCHY_PARENT_WEIGHT=0.04  # parent similarity

# Опциональные тяжёлые техники (default OFF)
ENABLE_CROSS_ENCODER_RERANKER=false
CROSS_ENCODER_MODEL=BAAI/bge-reranker-base
ENABLE_QUERY_EXPANSION=false  # LLM-переформулировка перед retrieval
ENABLE_HIERARCHY_PRUNING=false # отсечение по доминирующим L1-разделам
```

```
# Пример .env для каждого провайдера
LLM_PROVIDER=groq        # Groq (по умолчанию)
LLM_PROVIDER=gemini      # Google Gemini
LLM_PROVIDER=ollama      # Ollama локально
LLM_PROVIDER=ario        # Ario Directum360 (корпоративный)

# Ario (корпоративный) — дополнительные параметры
ARIO_API_KEY=100111ac-d413-4721-9357-5d04aaf7386d
ARIO_BASE_URL=https://gpt.ario.directum360.ru/v1
ARIO_MODEL=Qwen/Qwen3-32B-AWQ
```

## Веб-интерфейс

Демо для оператора — работает прямо в браузере, без установки дополнительных инструментов.

**Запуск:**

```
launch.bat → [3] Start API server
```

Открыть в браузере: **http://localhost:8000**

### Форма ввода

- Выпадающий список с 10 готовыми примерами обращений (вывоз мусора, ремонт дороги, субсидии и др.)
- Текстовое поле для ввода своего обращения
- Кнопка загрузки файла — поддерживаются TXT и PDF (до 5 МБ); текст извлекается на сервере через PyMuPDF

### Результат классификации

После нажатия «Классифицировать» отображается карточка:

```
Вид обращения:   Жалоба           Тип: Индивидуальное
Уверенность:     81%

Вопрос 1:  0005.0005.0056.1160
           Обращение с твёрдыми коммунальными отходами
           ЖКХ → Коммунальные услуги → ТКО → ...
           Предмет ведения: Вопрос местного значения | 81%

Вопрос 2:  0005.0005.0056.1161
           Несанкционированная свалка мусора, биоотходы
           81%

[ ✓ Подтвердить ]  [ ✎ Исправить ]  [ ✗ Отклонить ]
```

При выборе «Исправить» появляется форма:
- Поле для ввода правильного кода классификатора
- **Поле «Пояснение к коду»** — оператор описывает, в каких случаях применяется этот код
- После сохранения показывается: «Всего к этому коду: N аннотаций»

Аннотации сохраняются в `data/classifier_annotations.json` и используются при следующем fine-tuning для улучшения качества эмбеддингов.

## Бэк-офис (метрики использования)

**URL:** http://localhost:8000/backoffice
**Доступ:** по логину и паролю (Basic Auth)

| Параметр | Значение |
|----------|---------|
| **Логин** | `admin` |
| **Пароль** | `password` (изменить в `.env`!) |

На странице бэк-офиса:
- **4 KPI-карточки:** всего классификаций, верификаций, доля подтверждённых, средняя уверенность
- **График распределения уверенности** (Chart.js bar chart)
- **График топ-10 кодов** (Chart.js horizontal bar)
- **График использования по дням** (Chart.js line chart, 30 дней)
- **Таблица IP-адресов** — с каких адресов были запросы

Статистика собирается автоматически при каждом запросе к `/classify`. IP-адреса сохраняются в `data/request_log.jsonl`.

**Как изменить пароль** — добавьте в `.env`:
```
BACKOFFICE_USER=admin
BACKOFFICE_PASSWORD=<новый_пароль>
```

## API — примеры запросов

```bash
# Классифицировать текст (JSON)
curl -X POST http://localhost:8000/classify \
  -H "Content-Type: application/json" \
  -d '{"appeal_text": "Прошу провести ремонт дороги по улице Ленина, 15"}'

# Классифицировать файл TXT или PDF
curl -X POST http://localhost:8000/classify/file \
  -F "file=@обращение.pdf"

# Верифицировать результат (confirm / correct / reject)
curl -X POST http://localhost:8000/verify \
  -H "Content-Type: application/json" \
  -d '{"log_id": "uuid-из-ответа", "action": "confirm"}'

# Исправить — указать правильный код + пояснение
curl -X POST http://localhost:8000/verify \
  -H "Content-Type: application/json" \
  -d '{"log_id": "uuid-из-ответа", "action": "correct", "operator_codes": ["0005.0005.0056.1160"], "annotation": "Жалобы на некачественный ремонт дорог, когда заявитель требует устранить нарушения"}'

# Загрузить исторические данные (XLSX/CSV/JSON)
curl -X POST http://localhost:8000/api/upload-historical \
  -F "file=@historical_data.xlsx"

# Статистика верификаций и прогресс дообучения
curl http://localhost:8000/stats

# Бэк-офис: метрики использования (требует Basic Auth)
curl -u admin:password http://localhost:8000/api/backoffice/stats

# Проверить работоспособность
curl http://localhost:8000/health
```

Полная документация API (Swagger): **http://localhost:8000/docs**
