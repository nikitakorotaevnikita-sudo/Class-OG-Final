## 1. Общее описание

ИИ-агент автоматической классификации обращений граждан по Федеральному закону № 59-ФЗ и Общероссийскому классификатору вопросов обращений граждан (версия 4, 2108 позиций). Предназначен для интеграции с Directum RX 25.3.

Система реализует двухэтапный пайплайн:
- **Этап 1:** Семантический векторный поиск (multilingual-e5-base, cosine similarity) — топ-10 кандидатов из 2108 позиций классификатора.
- **Этап 2:** LLM-классификация (Groq llama-3.3-70b-versatile или Google Gemini) — определение вида/типа обращения, выбор кодов, обоснование.

### Ключевые сущности

| Сущность | Описание |
|----------|----------|
| Обращение | Текст обращения гражданина (до 5000 символов после обрезки) |
| Классификатор | 2108 позиций, 4-уровневая иерархия, код формата XXXX.XXXX.XXXX.XXXX |
| Вид обращения | Жалоба / Заявление / Предложение (59-ФЗ) |
| Тип обращения | Индивидуальное / Коллективное / Анонимное |
| Предмет ведения | Российской Федерации / Субъекта РФ / Местного значения / Совместный |
| Верификация | pending / confirmed / corrected / rejected |

## 2. Функциональные требования (FR)

### 2.1. Классификация обращений

**FR-1.1** Система принимает текст обращения в формате JSON (`POST /classify`) и возвращает результат классификации в JSON.

**FR-1.2** Система принимает файл TXT или PDF (`POST /classify/file`, макс. 5 МБ), автоматически извлекает текст и классифицирует.

**FR-1.3** Для каждого обращения определяются:
- Вид обращения (Жалоба / Заявление / Предложение)
- Тип обращения (Индивидуальное / Коллективное / Анонимное)
- Флаг устного обращения (`is_ustnoe`)
- Один или несколько вопросов с кодами классификатора

**FR-1.4** Для каждого вопроса возвращаются:
- `code` — код классификатора (XXXX.XXXX.XXXX.XXXX)
- `name` — наименование позиции классификатора
- `full_path` — полный путь в иерархии
- `predmet_vedeniya` — предмет ведения
- `confidence` — уверенность (0.0–1.0)
- `reasoning` — обоснование выбора (1–2 предложения)
- `alternatives` — до 2 альтернативных кодов с их названиями и путями

**FR-1.5** Для каждого обращения вычисляется `overall_confidence` как среднее уверенностей по вопросам. Если `overall_confidence < 0.65`, устанавливается `needs_verification = true`.

**FR-1.6** Если текст обращения превышает 5000 символов, он обрезается; в ответе возвращается `was_truncated = true`.

**FR-1.7** Результат классификации записывается в `data/appeals_log.jsonl` и возвращается `log_id` для последующей верификации.

> **Примечание:** Время ответа при пустом кэше LLM: 3–10 сек. При повторном запросе (кэш Groq) — 1–3 сек. Это приемлемо для пилотной демонстрации, но должно быть отражено в UI как индикатор загрузки.

### 2.2. Поиск по классификатору

**FR-2.1** `GET /classifier/search?q=<текст>&top_k=5` — семантический поиск по классификатору. Возвращает топ-K кандидатов с кодами, названиями и similarity score. Предназначен для отладки и ручного поиска.

---

### 2.3. Верификация оператором

**FR-3.1** `POST /verify` — верификация результата классификации. Поддерживает три действия:
- `confirm` — подтвердить классификацию агента
- `correct` — исправить код(ы), обязателен параметр `operator_codes` (список кодов)
- `reject` — отклонить обращение (некорректное, спам)

**FR-3.2** Для действия `correct` параметр `annotation` (пояснение оператора) записывается в `data/classifier_annotations.jsonl` и связывается с `log_id` и кодами.

**FR-3.3** После верификации статус обращения в `appeals_log.jsonl` обновляется на `confirmed` / `corrected` / `rejected`.

**FR-3.4** `GET /stats` — возвращает статистику верификаций: pending, confirmed, corrected, rejected, verified (confirmed + corrected), progress_percent к порогу fine-tuning.

---

### 2.4. Демо-примеры

**FR-4.1** `GET /examples` — возвращает 10 заранее подготовленных демо-примеров из `data/test_appeals.json`. Каждый пример содержит `id`, `title`, `text`, `expected_code`, `expected_vid`.

**FR-4.2** Фронтенд реализует dropdown-выбор примера с подстановкой текста в поле ввода.

---

### 2.5. Загрузка исторических данных

**FR-5.1** `POST /api/upload-historical` — загрузка файла исторических данных (XLSX, XLS, CSV, JSON). Поддерживаемые форматы: `.xlsx`, `.xls`, `.csv`, `.json`. Лимит — 50 МБ.

**FR-5.2** Система валидирует коды классификатора в загруженном файле и возвращает статистику: total, valid, invalid + список ошибок.

**FR-5.3** `POST /api/confirm-historical` — подтвердить валидные записи и сохранить их в `data/historical_verified.jsonl`.

**FR-5.4** `GET /api/historical-count` — возвращает количество записей в `historical_verified.jsonl`.

### 2.6. Бэк-офис (Backoffice)

**FR-6.1** Маршрут `GET /backoffice` — страница метрик использования системы.

> **ВАЖНО:** Бэк-офис **не реализован** в текущей кодовой базе. Это ключевое отсутствующее требование. Разработчик должен реализовать эндпоинт `/backoffice` и соответствующий HTML-шаблон.

**FR-6.2** Бэк-офис содержит следующие KPI-карточки (KPI Cards по design_guide.md):
- Общее число классификаций (всего запросов к `/classify`)
- Число верификаций (confirmed + corrected)
- Доля подтверждённых (confirmed / verified)
- Средняя уверенность (по всем обращениям)

**FR-6.3** Бэк-офис содержит следующие графики (Chart.js):
- **Распределение уверенности** — гистограмма confidence score (0.0–1.0 с шагом 0.1) по всем классификациям
- **Топ-10 кодов классификатора** — горизонтальный bar chart наиболее частых кодов (по верифицированным обращениям)
- **Частота использования** — line chart числа классификаций по дням (последние 30 дней)

**FR-6.4** Бэк-офис отображает IP-статистику: список уникальных IP-адресов, с которых поступают запросы, с количеством запросов (без персональных данных, только агрегация).

**FR-6.5** Бэк-офис доступен по адресу `/backoffice` с Basic Auth (логин/пароль из `.env`).

**FR-6.6** Эндпоинт `GET /api/backoffice/stats` — агрегированная статистика для бэк-офиса:

## 3. Нефункциональные требования (NFR)

### 3.1. Производительность

| Метрика | Требование | Условие |
|---------|-----------|---------|
| Время классификации | < 10 сек | p95, при пустом LLM-кэше |
| Время векторного поиска | < 500 мс | 2108 embeddings @ query_vector |
| Время загрузки страницы | < 2 сек | /backoffice, локальная сеть |
| Throughput API | > 5 req/min | при 1 параллельном LLM-запросе |

### 3.2. Масштабируемость

**NFR-2.1** Система должна поддерживать одновременную работу 5–10 операторов (50–200 пользователей на пилоте).

**NFR-2.2** При росте числа верификаций (> 10 000) логирование в JSONL работает без деградации; индексация не требуется.

### 3.3. Надёжность

**NFR-3.1** При недоступности Groq API — retry до 5 раз с экспоненциальной задержкой (max 60 сек). После исчерпания попыток — ошибка 500 с описанием.

**NFR-3.2** При недоступности Gemini API (fallback) — аналогичная retry-логика.

**NFR-3.3** При ошибке извлечения текста из PDF (скан без OCR) — ошибка 422 с описанием: «PDF является сканом без текста. Используйте OCR перед загрузкой.»

### 3.4. Безопасность

**NFR-4.1** Загрузка файлов — валидация расширения и MIME-типа (только .txt, .pdf). Лимит — 5 МБ для `/classify/file`, 50 МБ для `/api/upload-historical`.

**NFR-4.2** Защита от path traversal: safe random filename через `uuid.uuid4().hex` при сохранении загруженных файлов.

**NFR-4.3** Бэк-офис (`/backoffice`) защищён Basic Auth. Логин/пароль — из переменных окружения `.env`.

**NFR-4.4** API не раскрывает внутренние ошибки (stack trace); возвращает `detail` с обобщённым описанием.

### 3.5. Совместимость

**NFR-5.1** Python 3.11 (обязательно). Python 3.12+ несовместим с `sentence-transformers` и ML- зависимостями.

**NFR-5.2** numpy < 2.0 (numpy 2.x убирает `np.float_`, используемый старыми зависимостями).

**NFR-5.3** Браузеры: Chrome 90+, Firefox 90+, Safari 15+. Edge не поддерживается.

### 3.6. Развёртывание

**NFR-6.1** Docker + docker-compose: `Dockerfile` собирает образ, `docker-compose.yml` поднимает сервис и пробрасывает порт 8000.

**NFR-6.2** Запуск из корня проекта (не из `src/`). Все скрипты используют `sys.path.insert(0, 'src')`.
